# タグ台帳

Articles のタグ統制語彙。クリップ時はここから選んで付与する。

## ルール

- **`topic/` を1〜2個 + 必要なら形式の `type/` を1個**。批判的な記事にはさらに `type/批評` を重ねてよい(スタンスタグ、下記参照)
- 親子関係にあるタグは**子だけ付ければよい**(例: `topic/アクセシビリティ/WCAG` があれば `topic/アクセシビリティ` は不要。親での検索に自動的に含まれる)
- 語彙は原則この台帳から選ぶ。新語を足すときはこのノートにも追記する
- 所属に迷ったら**浅い方に付ける** or 複数タグで表現する(深追いしない)
- どれにも当てはまらなければ `未分類` を付けておき、あとで振り直す

## type/ — 記事の性質

**形式**(記事のかたち、原則1つ)と**スタンス**(論調、形式に重ねる)の2軸に分かれる。

### 形式(原則1つ)

| タグ | 意味 |
| --- | --- |
| `type/事例` | 特定組織の取り組みの経緯・結果が具体的に語られる報告(導入記・構築記・振り返り)。**組織名を伏せたら価値が消えるもの** |
| `type/概論` | 入門・全体像・What is X |
| `type/実装` | how-to・技術解説 |
| `type/運用` | ガバナンス・プロセス・運用論(一般方法論。素材が自社でも主眼が横展開可能な仕組みならこちら) |
| `type/リソース` | リンク集・ギャラリー・リファレンス |

### スタンス(原則形式タグに重ねる。論説・エッセイは単独可)

| タグ | 意味 |
| --- | --- |
| `type/批評` | 通念・ベストプラクティス・現状の実践への異議が主張の核にある記事 |

**批評を付けるかの判定**:

- 「この記事は何かに反対・懐疑しているか?」
- 「著者の主張を削ったら記事が成立しなくなるか?」→ Yes なら付ける。説明の中に軽い批判が混ざる程度なら付けない
- 読後効果の目安: 概論は「Xが**わかる**」、批評は「Xへの**見方が変わる**」
- 併用の型: `事例×批評` = 組織の経験からの批判的リフレクション / `概論×批評` = 概念の説明を通した通念の問い直し
- **単独の型**: 経験や調査に裏打ちされた**論説・エッセイ**(主張そのものが本体で、組織の経緯も概念の解説もない記事)は `批評` 単独。経験は権威付けにすぎないものを `事例` に入れない(例: 元Material Design責任者の「破られた約束」は事例ではなく批評単独)

## 付け方の例

```yaml
Tags: [topic/デザインシステム/デザイントークン, type/事例]  # 他社のトークン導入事例
Tags: [topic/ツール/Storybook, topic/技術/テスト, type/実装] # StorybookのVitest統合手順
Tags: [topic/アクセシビリティ/WCAG]                          # WCAG達成基準の解説ノート
Tags: [topic/デザインシステム, topic/AI]                     # AI×デザインシステム論
Tags: [topic/デザインシステム, type/事例, type/批評]         # 導入失敗の批判的リフレクション(形式+スタンス)
```

## 本文中の `#` が偽タグになったら

クリップ記事の本文にSNSハッシュタグ等が含まれると Obsidian がインラインタグとして解釈し、タグペインが汚れる。気づいたら Vault ルートで以下を実行(該当箇所を `\#` にエスケープする。表示は変わらない):

```bash
node .scripts/escape-inline-tags.mjs        # 適用
node .scripts/escape-inline-tags.mjs --dry  # 対象確認のみ
```

## Bases ビューとの関係

`Bases/` の各ビューは `file.hasTag()` の AND 条件。子孫タグを持つ条件は OR 展開してあるので、親タグのビューは配下の記事もすべて含む(例: `デザインシステム.base` はトークン・配信基盤なども表示)。新しい組み合わせのビューは既存ファイルをコピーして filters を書き換えれば増やせる。
