# Q. デザインシステム運用の泥臭さとコミュニケーションはなぜ本体なのか

質問の文脈: デザインシステムの運用面の泥臭さ・調整・コミュニケーションの重要性についてのまとめ。[[デザインシステムの浸透]]・[[デザインシステムのガバナンス]]・[[デザインシステムの強制と例外]]・[[デザインシステムと組織構造]] を「運用の泥臭さ」という軸で束ね直した合成。結論は「運用とは、説得の反復・例外の誠実な文書化・拒否の作法・巻き込みの仕掛けという地道なコミュニケーション労働の総体であり、それ自体が DS の本体である」。

## 大前提: 失敗も成功も「技術」ではなく「人とプロセス」で決まる

- デザインシステムは制作効率化の道具ではなく「**判断を事前に固定するための制度装置**」。例外の承認主体が曖昧な組織では例外が政治になり、現場はシステムを迂回する。機能する組織には加速装置、そうでない組織には歪みを照らす照明装置（出典: [[デザインシステム導入が失敗する会社の構造は最初から決まっている｜Plato Design]]。詳細: [[デザインシステムと組織構造]]）
- 87チーム規模の失敗事例の結論は「**問題は悪い人ではなく、悪いプロセス**」。承認6週間・却下率40%が、影のコンポーネント73個と燃え尽きを生んだ（出典: [[Design System Governance That Doesn’t Kill Momentum]]。詳細: [[デザインシステムのガバナンス]]）
- 「『システム』だけでカバーしようとせず、『ルール』だけで回そうとしない。**作っているのは人**」（出典: [[デザインシステム疲れからの再出発：持続可能な運用への実践的アプローチ｜ishigakijunichi]]。詳細: [[デザインシステムの浸透]]）

## 泥臭さの実相 — 説得・我慢・治安維持

- **売り込みの努力を過小評価しない**: Foursquare は PM・エンジニア・幹部との賛同獲得会議に膨大な時間を要し、「デザインシステムは専任の仕事。ボランティアの時間提供はいつまでも続かない」と結論（出典: [[翻訳記事：デザインシステムチームなしでデザインシステムを構築する｜Nobuya Sato]]。詳細: [[デザインシステムの立ち上げ]]）
- **組織は巨大タンカー**: Cisco では年間1,000万ドル超の節約効果を提示しても誰も動かず、専任エンジニア獲得に3年。「人は会話の50%しか覚えず1週間後には10%」——**一貫したビジョンの反復**と相手のペインを正確に語れるパートナーシップが要る（出典: [[翻訳記事：石油タンカーを方向転換する難しさ｜Nobuya Sato]]。詳細: [[デザインシステムと組織構造]]）
- **「対話とは我慢である」**（Yahoo 水野直）: DS は構築より浸透・説得に課題がある。合わない意見に出会ったら自分を正当化せず一度我慢して違いを理解する——「正義を押し付けず、相手の意見を聞き、相手を信じて提案する」（出典: [[デザインシステムがなぜ必要なのか？ 〜共通言語のコミュニケーションで円滑なプロジェクト推進を〜  NIJIBOX BLOG]]。詳細: [[デザインシステムの浸透]]）
- 地道な調整業務の例: enechain は台本つき「株主総会」が準備コストで持続不能と分かり**ステークホルダーの元へ直接出向くカジュアル対話へ転換**（出典: [[デザインシステム浸透の取り組み：目安箱の運用とデザインシステム株主総会 - enechain Tech Blog]]）。KARTE は Figma マスターファイルの「**治安**」維持——ゴミが1つでもあると利用が不安になる（出典: [[デザインシステム疲れからの再出発：持続可能な運用への実践的アプローチ｜ishigakijunichi]]）。Loglass は Po/PdM・エンジニアとの**優先度設計の議論**を自治権獲得の5活動で「一番重要」と位置づける（出典: [[デザインシステム開発優先度の「難しさ」と「対策」｜hikaru-takase -Loglass｜note]]。詳細: [[デザインシステムの投資対効果]]）

## 調整の制度化 — 「警察」にならずに秩序を保つ

- **拒否の作法「Yes, And…」**: 単なる No を言わず常に前進の道を示す（非推奨化を先に承認して3ヶ月後に再審査／チーム固有実装を支援して5チーム採用で再検討／条件つき承認＋ペアプロ提供）。却下率は40%→15%へ、「承認」が「設計の対話」に変わった（出典: [[Design System Governance That Doesn’t Kill Momentum]]。詳細: [[デザインシステムのガバナンス]]）
- **公開意思決定ログ**: 却下を含む全決定を理由・代替案つきで公開。透明性が信頼を築き、**同じ議論の蒸し返しを防ぐ**（出典: 同上）
- **例外のハイパードキュメンテーション**（Doctolib）: 例外を潰すのではなく、なぜ許されるか・どこで使えないかを徹底文書化する。「自分たちの決定の健全性を説明できなければ、他者を導く立場を失う」（正当性問題）。厳しすぎる規制は回避ハックを生み、統制と可視性を両方失う——「静かな違反が数十件起きるより、文書化されたパターンを」（出典: [[デザインシステム：文書化された妥協の芸術｜ジェローム・ブノワ著｜Doctolib｜Medium]]。詳細: [[デザインシステムの強制と例外]]）
- **命令による統一は静かな迂回を生む**: Adobe Spectrum「デザインシステム警察にはなれない」——誰も書きたがらない CSS のような価値提供で引き込む（出典: [[Garth Braithwaite on Design Tokens, Governance, and Scaling Spectrum at Adobe  Knapsack]]）。SmartHR は自らを「**妥当な意思決定を早めるための補助線であって、法律ではない**」と定義（出典: [[SmartHRのプロダクトデザインの生産性を高める“デザイン”のためじゃないデザインシステムとは（Schema2022）｜wentz｜note]]。詳細: [[デザインシステムの強制と例外]]）
- **ゲートキーピングより支援**: 週2回のオフィスアワー・非同期ヘルプチャンネル・セルフサービス資料でサポート負荷を6割減。承認会議より効く（出典: [[Design System Governance That Doesn’t Kill Momentum]]。詳細: [[デザインシステムのガバナンス]]）

## コミュニケーションは付随物ではなく本体

- **DS はコミュニケーションツール**: 多数の部署との合意形成では、ルールの一人歩きによる認識齟齬を防ぐ一元管理と「何のため」の啓蒙こそが機能。「与えられたルール」にせず本質的議論の土台を作る（出典: [[ウェブガバナンス推進にデザインシステムを活用する ｜ ひらくデザイン ｜ 株式会社コンセント]]。詳細: [[デザインシステムのガバナンス]]）
- **共通言語の効果**: 「DS が中心にあると、エンジニアも遠慮せず同じテーブルでデザインを議論できるようになった」（Figma Japan 谷拓樹。出典: [[デザインシステムの構築と運用そしてその本質 - Spectrum Tokyo]]）。バイセルも導入の最大の効果を「デザイナーとのコミュニケーションが密になったこと」と総括（出典: [[デザインシステムを導入してみて(導入編) - バイセル Tech Blog]]。詳細: [[デザインシステムの立ち上げ]]）
- **巻き込みの仕掛け**: kintone はワーキンググループと「利用チームが PR を出す」体制で半年でコントリビューター30名超——DS チームの役割は「ビジョンと場所の提供」（出典: [[デザインに関わる全ての人たちでエベレスト登頂を目指すために取り組んでいること｜amishiratori]]）。enechain は目安箱の起票者を「コントリビューターとして参加しませんか」と誘う。m3.com の第一原則は「**作る側 vs 使う側の構図にしない**」（出典: [[33万人以上の医師が登録する大規模サービス「m3.com」での、使われるデザインシステムのつくり方｜Cocoda]]。詳細: [[デザインシステムの浸透]], [[デザインシステムの立ち上げ]]）
- **「警察になるな」より「フィードバックサイクルの中心に根づかせる」**（DMM 河西紀明）: 警察は発生するし必要でもある。重要なのは組織全体が「より良い議論の基盤として DS を運用しよう」という志向性に至ること。DS をプロダクトと捉えるなら「ユーザーから愛されているか」の評価が要る（出典: [[デザインシステムの構築と運用そしてその本質 - Spectrum Tokyo]]。詳細: [[デザインシステムの浸透]]）
- 根っこにある誤想定への警告: 負のサイクルの根因は「**全員が優先して使うだろう**」という想定。チーム間コミュニケーションに課題があるなら、UI ライブラリの充実より **DS チームが繋げ役になる**方が利用の契機になる（出典: [[デザインシステムは最優先にはならないです]] = [[長谷川恭久]]。詳細: [[デザインシステムの浸透]]）
