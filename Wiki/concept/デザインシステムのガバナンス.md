# デザインシステムのガバナンス

## 概要

ガバナンスのジレンマ: 構造がなければシステムは混沌に向かい、構造が過剰なら官僚制が勢い（momentum）を殺す。「50件の未処理コントリビューション、3ヶ月のバックログ、そしてチームは勝手に独自コンポーネントを作っている」が典型的症状で、結論は「**良いガバナンスはデザインシステムを遅くではなく、速くする**」（出典: [[Design System Governance That Doesn’t Kill Momentum]]）。ガバナンス不在がもたらすスナップショット化は [[デザインシステムと組織構造]]、規範の機械的強制は [[デザインシステムの強制と例外]] を参照。

ガバナンスが管理する対象は**3方向の構造的緊張**である: デザインは柔軟性を、エンジニアリングは安定性を、プロダクトは速度を求める。一貫性 vs 柔軟性・採用 vs 自律・速度 vs 品質という3つの緊張は解消できず、ガバナンスによってのみ管理できる（出典: [[The Design System Designer Career Ladder Roles, Skills, and Growth Paths in Design Systems]]）。また「デザインシステムは Figma ファイルではなく**社会契約**」であり、創業者のカリスマ（暗黙の権威）で回っていたシステムはその退任で化石化する——ガバナンスの再生は暗黙の権威を「合意された契約」へ書き換えることで機能する（出典: [[What Actually Happens to a Design System When the Founder Leaves]]）。

## 中央集権承認はスケールしない

以下すべて出典: [[Design System Governance That Doesn’t Kill Momentum]]（Roberto Moreno Celta）

- 「コアチームがすべて承認する」モデルは利用者20人未満なら機能する（リクエストが少なく、文脈を全部知っていて、即日判断できる）が、50人超で**死のスパイラル**に入る: バックログがレビュー容量より速く育つ → 待ち時間4〜6週 → チームは苛立って貢献をやめる、**または影のシステム（shadow systems）を作る** → コアチームは燃え尽きる
- 事例の定量値（従業員500人・87プロダクトチームの SaaS）: 平均承認6週間、却下率40%、影のコンポーネント73個（15チーム）、コアチーム満足度3.2/10。「**問題は悪い人ではなく、悪いプロセス**」
- 専任チーム化にはもう一つの病理がある: チームは採用率などの**代理指標を自己目的化**し、プロダクトチームの利害から構造的に乖離していく（インセンティブ問題）。統治の過剰はプロセスの遅さだけでなく、設計判断そのものを殺す（出典: [[Your Design System Is Slowing Your Team Down, Not Speeding It Up]]。組織構造への帰結は [[デザインシステムと組織構造]] を参照）

## 3層コントリビューションモデル

以下すべて出典: [[Design System Governance That Doesn’t Kill Momentum]]

- **Tier 1: Small（セルフサービス、全体の約70%）**: 2時間未満・影響最小の変更（typo修正、既存パレットへの色トークン追加、既存コンポーネントのサイズバリアント、明白なバグ修正）。PR → 自動チェック（テスト・Axe による a11y・Percy/Chromatic によるビジュアルリグレッション・ドキュメント・チェンジログ）→ **人間の承認なしで self-merge** → Slack で透明性のため告知
- **Tier 2: Medium（週次カウンシル、約25%）**: 2〜8時間・複数コンポーネントに影響（新しいインタラクションを持つバリアント、API 変更、移行パスつき破壊的変更、トークン構造変更）。RFC → 48時間の非同期レビュー → 週次30分の同期討議 → 決定。3〜5日で回る。**カウンシルは4〜6人（デザイナー2-3+エンジニア2-3）、6ヶ月任期のローテーション**、async-first
- **Tier 3: Large（RFC+ステークホルダー合意、約5%）**: 8時間超・システム全体に影響（新規大型コンポーネント、アーキテクチャ変更、リブランド）。pre-RFC で問題合意 → 詳細 RFC（ビジネスケース・成功指標・リスク込み）→ ステークホルダーレビュー → **1〜2チームでパイロット** → 反復 → 段階的ロールアウト。4〜8週間をプロジェクトとして計画

同じ原理（**リスクに比例した摩擦**）が2026年の複数ソースで独立に反復されており、収斂が見て取れる:

- **blast radius × 可逆性**の2軸で変更カテゴリを分類し、追加的・可逆的な変更は単独メンテナーの即日非同期承認で通す。リスク非対称を無視した一律プロセスこそが速度を殺す（出典: [[Your Design System Is Slowing Your Team Down, Not Speeding It Up]]）
- 「**比例した摩擦**（proportional friction）」: 小変更は48時間の非同期レビュー、委員会にかけるのは基盤変更のみ（出典: [[Building a Design System That Survives Contact with Reality]]）
- 軽量 RFC を **lazy consensus**（期限までに異議がなければ承認）で回し、破壊的変更・廃止・アーキテクチャ変更など**不可逆な決定のみ**をコアチームに留保する（出典: [[Your Design System Isn’t Just a Component Library. It’s a Community.]]）

## 判断フレームワーク — 3つの C

出典: [[Design System Governance That Doesn’t Kill Momentum]]

- **Consistency（30%）**: 既存パターンに整合するか（Button と Input に outlined があるなら Card の outlined は 3点）/ **Coverage（40%）**: 何チームが必要とするか（10+で3点、1〜2チームなら1点＝チーム固有コンポーネントとして作る判断）/ **Cost（30%）**: 保守負担（Rich Text Editor は複雑・エッジケース多で1点＝却下してサードパーティ推奨＋統合ガイド提供）
- スコアカード: 9点=自動承認、6〜8=議論の上おそらく承認、3〜5=強い正当化が必要、1〜2=代替案つきで却下
- 別系統の4基準フレームワーク: (1) 実在する課題を解くか (2) システムの哲学に適合するか (3) 保守可能か (4) 今がそのタイミングか（出典: [[Building Your Design System Workflow — Rituals and Templates]]）

## Design System Council の設計

- Tier 2 の週次カウンシルを独立した統治機関として設計する型が複数ソースにあり、共通するのは**小さく・短く・権限を限定する**こと
- 創業者退任後の再生事例: **3〜5人・隔週45分・提案の評価のみ**を行い、コンセント（同意）制——「賛成か」ではなく「重大な異議があるか」を問う——で決定し、**決定後は議論を再開しない**。あわせて「Sacred and Whim マトリクス」（技術的複雑性 × ユーザー価値の2軸）で、根拠なく神聖視されてきた創業者の気まぐれ由来の仕様を特定し廃止した（出典: [[What Actually Happens to a Design System When the Founder Leaves]]）
- Condé Nast の Design System Council を参照した運営型: 4〜6人が上記4基準で評価し、**1提案10分・結果は当日中に通知**する。応答速度そのものが信頼を作る（出典: [[Building Your Design System Workflow — Rituals and Templates]]）

## ワークフローの設計 — 6本柱

以下すべて出典: [[From Proposal to Release Designing Your Design System Workflow]]（Stuart Robson）

- デザインシステムの失敗の多くはワークフローの失敗。**Contribution / Review and Approval / Documentation / Communication / Iteration / Versioning and Deprecation** の6本柱でプロセス全体を設計する
- 複雑度別タイムラインが計画可能性を作る: 単純な変更1〜2週・中規模4〜6週・複雑な提案8〜12週
- 開始方法: 直近のコンポーネント1つが Ideation から Release までどう流れたかを**30分でマップ**し、摩擦点（提案が止まる場所・誰も答えられない質問）を特定する。ワークフロー不在の人的コストは提案の停滞・信頼の喪失・コアチームの燃え尽きとして現れる

## 組織モデルの選択

- **Centralized**（〜50人）: コアチーム2〜4人がすべてを所有。品質一貫・高速だがスケールしない / **Federated**（50〜500人）: コアが方向を定め、プロダクトチームの貢献者が実装、カウンシルがローテーション。オーナーシップ感が生まれるが調整コストと品質分散 / **Hybrid**（500人〜）: 中央プラットフォームチーム＋**ギルド**（アクセシビリティ・パフォーマンス・コンテンツ・モバイルの専門レビュー）＋連合型貢献（出典: [[Design System Governance That Doesn’t Kill Momentum]]）
- エンタープライズ実務からの推奨も同型: 20人超の規模では**ハブ&スポーク型**（中央集権のボトルネックと完全連合のフォーク乱立の中間）を採り、ガバナンス文書は**1ページ**に収める（出典: [[Design System Mistakes That Cost Enterprises Millions in 2026]]）
- ただし連合型には提唱者自身の撤回と失敗証言が積み重なっている: [[Nathan Curtis]] は2024年に「連合型を優先したことは間違い」と撤回（80超のシステムで中央投資なしの連合型成功は「ゼロパーセント」。出典: [[翻訳記事：連合型デザインシステムの誤り｜Nobuya Sato]]）。Spotify では9年間で2度失敗（平均再利用1.2回 vs 中央型200回・1,500超のコンポーネント膨張・「連合型を機能させる投資を中央チームに費やした方が良い結果では」。出典: [[翻訳記事 連合型デザインシステムが失敗し続ける理由｜nobsato]]）。Cisco でも専任エンジニア不在のまま推進され続け3年を要した（詳細は [[デザインシステムと組織構造]]）。神話の解体・成立条件を含む総覧は [[連合型デザインシステム]] を参照。モデル名より「誰が実装リソースを持つか」が効く
- 成功例もある: [[kintone Design System]] は**専任チームを持った上で** Centralized → Federated へ移行し、半年でコントリビューター30名超・PM のロードマップ記載に至った。「ビジョンと場所を提供する」専任コアの存在が連合型の前提条件と読める（出典: [[デザインに関わる全ての人たちでエベレスト登頂を目指すために取り組んでいること｜amishiratori]]）。詳細は [[デザインシステムの浸透]]

## 拒否の作法と公開意思決定ログ

出典: [[Design System Governance That Doesn’t Kill Momentum]]

- **「Yes, And…」フレームワーク**: 単なる No を言わず、常に前進の道を示す。(1) 良い案・時期が悪い → 非推奨化を先に承認し3ヶ月後に削除を再審査 (2) 良い案・特殊すぎる → チーム固有コンポーネントとして作ることを支援し、5+チームが採用したら再検討 (3) 良い案・実装が悪い → 変更条件つき承認＋ペアプロとレビューの提供
- **公開意思決定ログ**: 却下を含む全決定を理由・代替案つきで公開する。透明性が信頼を築き、過去の決定を参照でき、**同じ議論の蒸し返しを防ぐ**。[[デザインシステムのドキュメンテーション]]の意思決定記録、Doctolib の例外ハイパードキュメンテーション（[[デザインシステムの強制と例外]]）と同型
- 却下率は40%→15%へ。承認ではなく設計の対話に変わる
- 「**速い Yes**」を出せる組織が成功する——Zalando や GOV.UK の運用が示すように、貢献への応答速度そのものがガバナンスの品質指標になる（出典: [[Design Systems as Brand Ops Tokens, AI and Stopping Brand Drift]]）

## ゲートキーピングより支援

- **オフィスアワー > 承認会議**: 週2回のドロップイン（デザイン回・エンジニアリング回）。「これは Small か Medium か」「RFC のスコープを手伝って」「却下の理由を知りたい」に答える。非同期チャンネル（#help は4時間以内応答・#contributions・#announcements は読み取り専用）と GitHub Discussions、セルフサービス資料（貢献ガイド・決定ログ・FAQ・過去例）でサポート負荷を6割減らす（出典: [[Design System Governance That Doesn’t Kill Momentum]]）。Adobe Spectrum も同様にオフィスアワーを支援の中核に置く（詳細は [[Adobe Spectrum]]）
- **壁の庭から舗装路（paved road）へ**: 門番型ガバナンスは**心理的リアクタンス**（統制されるほど反発する）を招き、野良実装を生む。貢献の経路を閉ざす「壁の庭」ではなく、正規ルートが最も速く楽になるよう舗装する貢献型ガバナンスが、影のシステムを構造的に減らす（出典: [[The Component Library Trap Why Your Design System is Failing Your Team]]。DeShawn Harris——「品質検証」節の再構築記事と同著者）
- **サポートには線引きが要る**: [[長谷川恭久]] は窓口（チャット／問い合わせフォーム／オフィスアワー／勉強会）を複数用意して敷居を下げつつ、「要件定義に関わる部分は関与しない」といった**範囲の線引き**をしないと仕事が際限なく広がり「忙しくしているのに反発の声が出る」と警告する——「持続がすべて」（出典: [[デザインシステム浸透に欠かせないサポートについて]]。詳細は [[デザインシステムの浸透]]）
- 87チーム事例の6ヶ月後: 承認6週→3日（95%減）、影のコンポーネント73→8、貢献3件/月→18件/月（6倍）、双方の満足度8点台。副次効果として品質向上（自動チェックの早期検出・カウンシルローテーションによる多くの目・承認要件としてのドキュメント）と燃え尽きの解消（出典: 同上）

## Design System Ops — 運用の専門職能

以下すべて出典: [[Design System Opsの表と裏]]（UXPin。元 Shopify Polaris の Kaelig Deloumeau-Prigent の講演に基づく）

- Design System Ops = コンポーネントをデザインからリリースへ運ぶ**プロセスと基準の最適化**。目的は「決断疲れ」の軽減——「エンジニアがより早くリリースを出せるように、いかにして意思決定を減らすか」。「これはどうすれば？」「どこにある？」という質問を消すことを目指す
- 背景には Nathan Curtis の「**デザインシステムはプロジェクトではなく、製品であり、サービスである**」（2016）
- 担当者はデザインと開発の両経験＋デザインシステムの知識が必須（DesignOps とも DevOps とも違い、両分野にまたがる）
- 支援例: アセットのハンドオフ標準（PNG→WebP 変換・ロード方法・CDN か build 時か）、開発体験（ローカル環境の即時セットアップ・linter 構成・「新コンポーネントはどう作るか」の手順・ボタン1つのリリース）、テスト（ローカルテストの所要時間査定・ビジュアルリグレッション・a11y テスト自動化）
- 進め方: ユーザー調査（チームのツールとスタック）→ 問題の特定（プロセスの問題か、トレーニングの問題か）→ 実施 → 測定（ビルドタイム・MTTR・エラー/手戻り率、DS サイトの利用分析）
- Kaelig の原則: 「**成功は、配置したツールではなく、解決した問題によって測られるべき**」——壊れていないものを直さない

## オーナー（PO）の必要性

- **「プロジェクトの罠」**: 6ヶ月で納品→チーム解散→劣化→3年後に「今度こそ本物を」と再出発するサイクルが最大の失敗モード。デザインシステムは完成させるプロジェクトではなく**継続的に所有する機能（function）**であり、委員会ではなく**名前を持つ一人の責任者**を組織図に置き、システムの健全性で評価する（出典: [[Owning the Design System]]。健全性指標は [[デザインシステムの投資対効果]]、報告ラインの配置論は [[デザインシステムと組織構造]] を参照）
- 規模の下限はごく小さい: 小チームなら「**週に一度の午後 × 1人**」でも足りる——重要なのは工数ではなく**説明責任（accountability）の所在**で、オーナー不在のシステムは必ず崩壊する（出典: [[When You Actually Need a Design System]]）
- デザインシステムは成長するもので、「作ることだけが目的になると、最初の『完成』をもってメンテナンスされない」。持続的成長には専属チームとともに**責任を持つオーナー（PO）**が必要で、特に構築段階でのオーナーの有無が完成度とその後の運用を左右する（出典: [[デザインシステム構築におけるオーナーの重要性｜sakito｜note]]）
- PO の仕事: 目指す姿の明確化（**含める/含めないの判断基準と根拠**になる）→ 1年目標とクォーター分解のロードマップ（意図を伝え続ければ PO 不在でも理想に沿って進む）→ バックログと優先度。kintone の Mantle チームの実践は [[kintone Design System]] を参照（出典: 同上）
- 「デザインシステムを1つのプロダクトのように運営するオーナー」——Curtis のプロダクト論・Vilariño の「生きたプロダクトとしての投資」（[[デザインシステムと組織構造]]）と同じ結論に収斂する
- 役割定義の実務的な雛形: **デザインシステムオーナー**（ビジョン・ロードマップ・KPI 設定・優先順位・リソース配分・プロダクト戦略との整合）／**デザイナー**（ブランドガイドライン・コンポーネントデザイン・トークン設計・原則策定・ドキュメント）／**フロントエンドエンジニア**（実装・Storybook・技術ガイドライン・パフォーマンス）。役割分担だけでなく役割間の連携（定例・Slack での密な情報共有）も要る（出典: [[価値あるデザインシステムを構築するための7つのポイント｜こぎそ]]）
- 裏面の証言: 専任チームなしの Foursquare は「誰もフルタイムでない」体制でボタン1つの設計に3週間・開発に8週間超を要し、「**デザインシステムは専任の仕事。ボランティアの時間提供はいつまでも続かない**」と結論した（出典: [[翻訳記事：デザインシステムチームなしでデザインシステムを構築する｜Nobuya Sato]]）。詳細は [[デザインシステムの立ち上げ]]
- ただし**専任・オーナー必須論にも反例がある**: [[SmartHR Design System]] は特定のオーナーを置かず、各開発チームの担当者が課題ベースで反映を主導する分散運用で4年以上回っている。SmartHR UI の兼任開発者は「課題感を感じている張本人が速度を保ったまま開発できる。専任なら課題感を伝えるだけで労力と時間を失う」とまで言う（出典: [[SmartHR UI を中心としたエコシステムのすすめ - SmartHR Tech Blog]]）。成立条件の違いに注目すべきで、SmartHR には「デザイナー＝開発者」という体制・テンプレートや Figma ブランチなど運用コストを下げる仕組み・使うこと自体が貢献になるエコシステムがある。専任（kintone・KARTE）／有志＋仕組み（SmartHR・enechain）／ボランティア頼み（Foursquare、破綻）の3類型で見ると、**分かれ目は専任の有無そのものではなく「継続的な実装リソースと課題の近さが両立しているか」**

## 品質検証 — 沈黙は検証の代替にならない

以下すべて出典: [[I Rebuilt Every Button In Our Design System. No One Noticed.]]（DeShawn Harris）

- 全ボタンの全面再構築が誰にも気づかれなかった経験からの教訓: 「見えないデザイン」（意図した不可視性）と「**検証されていないデザイン**」は別物。判定質問は「**もしこれが改悪だったら、それを捕捉できたか？**」——答えが No なら、静かなのは品質の証明ではなく検証の欠如
- 沈黙を信号として信頼しないための装置: ビジュアルリグレッションテスト、自動コントラスト監査、四半期ごとのドリフト監査（Shopify Polaris・Atlassian に先行例）
- 「目に見える失敗の不在こそが成果物」という構造は、デザインシステムが慢性的に予算不足になる理由と直結する（[[デザインシステムの投資対効果]] を参照）

## 拡張 — ウェブガバナンスの道具としてのデザインシステム

以下すべて出典: [[ウェブガバナンス推進にデザインシステムを活用する ｜ ひらくデザイン ｜ 株式会社コンセント]]

- ウェブガバナンス = 複数サイトの個別運営が生む「運営コスト増加・ブランド価値毀損・機会損失」への継続的取り組み。重要なのは**組織**（状況に応じ拡張できる柔軟さ。外部パートナー活用は「実行を任せる」か「社内人材育成を頼む」の2パターン）・**仕組み**（方針・横断的情報設計・業務フロー・CMS 基盤）・**ルール**（方針の共通認識と実行支援文書。世のガイドラインの大半はここ）の3観点で、この3つを集約したものを「ウェブガバナンスにおけるデザインシステム」と定義できる
- コーポレートサイト運営では多数の部署との合意形成が要るため、デザインシステムは**コミュニケーションツール**として働く。スタイルガイドだけでなく方針・ガイドライン・データ類を一元管理し、「一部のルールの一人歩きによる認識齟齬」を防ぐ
- MVV・ブランドコンセプト・「何を/どのように伝えるか」を記載して「何のため」を啓蒙し続ける——「何を良いデザインとするか」の基準を一緒に提供することで、**「与えられたルール」にせず**「なぜやるのか」の本質的議論の土台を作る。ブランド（らしさ）を動機の中心に据える系譜は [[ブランドとデザインシステム]] を参照
- 公共セクターの実証が **USWDS**（米国 Web デザインシステム）: 連邦政府だけで約26,000サイトが個別デザインでリソースを浪費していた状況に対し、2013年の Healthcare.gov の失敗を機に 18F と USDS が2015年に構築。47コンポーネント（デザイン例・サンプルコード・「礼儀正しく」「やり過ぎない」等のガイドライン付き）が94機関・160サイト・**年間約11億ページビュー**を支える。「一貫性の欠如は、ユーザビリティ調査に明確に表れなくても感じられる」「必ずしも完璧でなくとも、より良いものを作ろうと努力する」（出典: [[MIT Tech Review 米政府系サイトの常識を変えた「デザインシステム」革命]]）
