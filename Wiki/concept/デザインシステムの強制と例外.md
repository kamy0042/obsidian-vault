# デザインシステムの強制と例外

## 概要

デザインシステムの規範をどう守らせるか（enforcement）と、規範から外れる判断をどう制度化するか（例外処理）という運用の中核問題。「ルールを書いて従うことを祈る」だけのシステムは機能しない、という批判が複数ソースで一致する。逸脱は悪意なく起きる: 同じライブラリを使っていても解釈は分裂しており、「今回だけ」の調整や仕様が沈黙するエッジケースの独自実装が複利で蓄積してドリフトする（「整合の幻想」。出典: [[Why Design systems Fail]]。詳細は [[デザインシステムのドキュメンテーション]]）。

## 「インフラではなく希望」— validation 層の欠如

以下すべて出典: [[Your design system has opinions. They’re just not being enforced]]（[[Murphy Trueman]]）

- モーダルには「ヘッダー・ボディ・アクション」が必要と docs にも Figma にもコンポーネント定義にも書いてあるのに、アクションボタンのないモーダルがPR承認・QA通過して本番に出る。「ほとんどのデザインシステムはインフラのようには機能しない。**希望（hope）のように機能する**」
- 欠けているのは documentation と adoption の間の **validation（検証）層**。契約を強制しないデザインシステムはインフラではなく「人々が好きに解釈するライブラリ」であり、「正しい」の意味を巡って延々と議論することになる
- **インフラ思考**: バックエンドチームは「与えられたものを受け取ってベストを尽くす」APIを絶対に出荷しない。入力を検証し、DBは制約を強制し、不正なリクエストは被害が出る前に拒否される。UIだけが、バックエンドなら決して許容しない曖昧さを許容している
- 締めの原則: 「**文書化する価値があるなら、強制する価値がある**（If it's important enough to document, it's important enough to enforce）」。デザインシステムを「好きに使えるライブラリ」ではなく「契約を強制し、入力を検証し、挙動を保証するインフラ」として扱う時期に来ている
- 関連して: 「誰もマニュアルを読まない。パターンはコードに落とし込まれていないため、本来の目的を果たさないただの死んだテキストになっている」（未読の小説、出典: [[翻訳記事：デザインシステムの破られた約束；なぜルールに従っても優れた製品が得られないのに従うのか｜Nobuya Sato]]）
- 同じフレーミングは批判言説への反論側からも出ている: デザインシステムは「**権威（authority）ではなくインフラ**」——全決定を先回りする権威として使うから軋轢が生まれるのであり、実証済みパターンを支える基盤と位置づければ強制の問題の多くは消える（出典: [[“Design systems kill product innovation.”]]。詳細は [[デザインシステム批判論]]）

## validation の実装パターン

以下すべて出典: [[Your design system has opinions. They’re just not being enforced]]

- **3つの検証ポイント**（目的は同一: ユーザーより先に問題を捕まえる）: ① Design-time（Figma linting、specs-as-data、構造化コンポーネント定義）② Build-time（TypeScript 制約、ESLint ルール、CI でのスキーマ検証）③ Runtime（開発時のみのガードレール + 人間可読なエラー）
- **必須の子要素（required children）**: `Modal` は `ModalHeader` / `ModalBody` / `ModalActions` を要求する、と docs に埋めるのではなくコードにエンコードし、構造が誤っていれば dev-time エラーを投げる。「**composable contracts**」= 必須パラメータを持つ RESTful API のように、コンポーネントが自らの関係性を記述する
- **禁止された組み合わせ**: `loading` と `disabled` の同時指定など、意味をなさない prop の組は TypeScript の `never` 型で表現し、コンパイラに捕まえさせる。「制約は誰かの頭の中ではなく型システムに住む」
- **状態制約**: ナビゲーションの最大項目数、フォームは入力1つ以上、破壊的アクションには確認パターン必須——現状は「トライバルナレッジ」（誰かが覚えているか、いないか）であり、validation がそれを契約に変える
- **小さく始める**: 誤用が繰り返される3〜5個の高頻度コンポーネントから。最初のルールの例は「システムコンポーネントへのインラインスタイル禁止」（ESLint `no-restricted-syntax` / `react/forbid-component-props`）。**エラーメッセージはルールと同じくらい重要** — 挙動をブロックするだけでなく代替案を教える。「メッセージはプロダクトの一部」
- **禁止ルールの逆効果に注意（Adobe Spectrum の教訓）**: 「ハードコード値の禁止」だけを lint すると、エンジニアは「2px に等しい最初のトークン」を掴んでセマンティクスを迂回し、後日そのトークンの値変更が予期せぬ破壊を生む。欲しいのは禁止ではなく「より意味的な候補を提案する」linter であり、前提として「彼らはトークンエンジニアではない」とエンジニアを責めない姿勢（出典: [[Garth Braithwaite on Design Tokens, Governance, and Scaling Spectrum at Adobe  Knapsack]]）。詳細は [[Adobe Spectrum]]
- **国内実例（enechain）**: 「暗黙のコード規則はチーム外からのコントリビュートを難しくする」ため ESLint カスタムルールで機械的に統制——ダークモード対応の props にはデザイントークン以外を渡せない、i18n の全 namespace で key の抜け漏れを検査。バレルファイルは手運用をやめて自動生成し（`@ignoreExport` で除外指定）、「ヒューマンエラーを仕組みで防ぐ」方針を徹底。機能追加と同時にルールを導入するのが運用のコツ（出典: [[デザインシステムの成長。そして、これからどう向き合うか - enechain Tech Blog]]）
- **デザイン層での検証**: Nathan Curtis の「components as data」（anatomy・props・variant 挙動を YAML/JSON で表現したコンポーネント定義。スペックになれば検証できる）と Anova プラグイン（Figma アセットを解析し `invalidVariantCombinations` を導出。「システムは何が invalid かをすでに知っている。その出力を強制に使っていないだけ」）、TJ Pitre の FigmaLint。エラーは下流に流れるほど複合するため早期に捕まえる
- **契約とスキーマを分ける**: 良いコンポーネント契約は well-typed / normalized / platform-independent / verifiable / deterministic / efficient / evolvable である。同じ決定を複数箇所へ記述すると契約自身が矛盾して裁定能力を失うため、契約内容は一度だけ記述し、表現能力を定めるスキーマは別に版管理する。スキーマ変更はADRで理由と下流影響を残す（出典: [[Component Contracts and Schemas]]）
- **デザイン層 validation の国内実例（タイミー）**: 自社製 Figma Normalizer Plugin が「検査して直す」までを一発で行う——旧トークンの自動置換、スタイル未適用のテキストを赤字化、トークン外の色を紫化、**Notion のユビキタス言語 DB と照合する用語チェック**（意味論の統制の機械化として [[存在論的負債]] とも接続）。「限界費用をゼロにできるがゆえに初めて運用可能になるレギュレーションがある」（出典: [[タイミーでは先鋭的なDesignDataOpsを構築した｜Yasuhiro Yokota]]）。詳細は [[デザイントークンのツールチェーン]]
- **品質ごとに検査方法を分ける国内実例（[[relay Design System]]）**: 狩野モデルの当たり前品質（ハードコード禁止・a11y等）はhooksで機械的に遮断し100点を求める。一元的品質（意図に合うコンポーネント選定・表現）は固定課題のevalsで採点し、改善対象とする。指摘が増えて当たり前になった基準はDESIGN.mdの「譲れない原則」へ移し、検査も決定的な層へ引き上げる——**ルールの重要度だけでなく不確実性に応じて強制手段を変える**実装である（出典: [[AIネイティブを目指した「これまで」と「これから」｜agu  relay（リレイ）]]）
- 効果: PRレビュー高速化（`CardFooter` に `ButtonGroup` を入れてよいかの bikeshedding が消える）、リグレッション減（不要なQAサイクルの削除）、エージェント出力の品質向上

## トークンの契約層 — interface と implementation の分離（Dow Jones）

以下すべて出典: [[Design Tokens Aren’t a Contract]]（[[Kevin Muldoon]]、Dow Jones Index Design System）

- 18ブランド×6プラットフォームの「build once, theme anywhere」が静かに破綻: あるブランドが自分のトークンファイルに新トークンを足しても他ブランドには存在せず、Figma プラグインは欠損トークンに**エラーを出さず何もしない**——見た目は正常のままドリフトが不可視に蓄積した
- 欠けていたのは interface（宣言と実装の分離）: ほとんどのシステムでは「トークン＝契約」だが、それは interface と implementation を同じクラスに書くようなもの。必要なのは「有効なトークンセットが**どのキーを・どの型で・どの制約で**含まねばならないか」の独立した宣言であり、値は含まない——「各ブランドは数字で塗り絵をしていたが、誰も番号付きのキャンバスに合意していなかった」
- 実装: マニフェストを Style Dictionary に埋め込んだが「契約が実装ツールに閉じ込められる」限界に当たり、DB 化して API として公開。500+ エントリ（うち222はパレット色: 30ランプ×最大22ウェイト）、9ポジションのタクソノミー（Danny Banks の CTI と [[Nathan Curtis]] の命名フレームワークの系譜）。組み立て済みトークン名は持たず、消費側が自分の規約（CSS はハイフン、iOS は camelCase）で名前を組み立てる
- 効果: ブランドドリフトが停止し、新トークン提案は「全ブランドが実装すべきか」を問う質の高い会話になった。制約の明示によってブランドはむしろ**自由になった**（暗黙の破壊リスクからの解放）
- 「**モードはまだ名付けていないブランドである**」: 単一ブランドでもダークモード・高コントラスト・密度を持つなら、同じ interface を満たすべき複数実装が既にある。契約層は後付けより早期構築が圧倒的に安い
- [[DTCG]] 仕様との関係: 仕様が標準化するのは表現（文法）であって義務（どのトークンが存在すべきか）ではない——「仕様は文法を、契約は各ブランドが埋めるべき語彙リストを与える」。相補的であり、仕様の安定を待つ理由はない。DTCG format 共同編者の James Nash も値を持たない「design token interface」を独立に提唱しており、構造的必然性を示唆する
- 実践手順: 契約を独立に定義（提案者・時期・理由つきの意思決定記録として）→ API として公開（Airtable / Notion / リポジトリ内の versioned JSON でよい）→ パイプライン最上流（Figma エクスポート、ビルド、pre-commit）で検証し、欠損を名指しする失敗ログを出す。「誰も検証しない契約はただのドキュメント」

## 例外の制度化 — 「文書化された妥協」（Doctolib）

以下すべて出典: [[デザインシステム：文書化された妥協の芸術｜ジェローム・ブノワ著｜Doctolib｜Medium]]

- アクセシビリティ原則（可視ラベル必須）と業界標準UX（ラベルなし検索は Slack/Linear/WhatsApp の事実上の標準）の板挟み。W3C自身がWCAG 3.3.2 の理解文書で「虫眼鏡アイコンが検索フィールドの可視ラベルとして機能する」パターンを明示的に認めていることを確認し、アイコン=ラベル案を採用した
- ただし例外には4条件を課す: (1) 視覚的文脈から目的が自明 (2) フォーム等の複数入力文脈では絶対不可・文書化されたパターンコンポーネントの一部に限定 (3) プログラム的ラベル（aria-label）必須 (4) **例外のハイパードキュメンテーション**（なぜ準拠か / どこで使えるか / どこで使えないか / 通常入力との違い）
- **正当性（legitimacy）問題**: 「自分たちの決定の健全性を説明できなければ、他者を導く立場を失う」。デザインシステムチームが自ら例外を作るなら、なぜそれが許されるかを説明できない限り、ガイドラインを課す資格を疑われて当然
- **ドミノ効果**: 説明なき例外は正常化し、ガイドラインの重みを失わせる。「今日の許容パターンは明日の誤用ハックになる」
- **善意の警察**: 役割は禁止ではなく教育。ブロッカーとガーディアンの差はこの教育姿勢にあり、その線は非常に細い
- 制限しすぎの逆効果: 厳しすぎる規制は回避策（CSSでラベルを隠す等のハック）を生み、統制と可視性を両方失う。「静かな違反が数十件起きるより、文書化されたパターンで明確なガイドラインを提供する方がよい」
- 結論: 信頼性は厳格なルールからではなく「**精密さと誠実さ**」から生まれる。WCAGの実際の要求と業界標準が許容される場面を知り、理由を文書化し、適用範囲を限定する

## 例外は情報 — シャドウライブラリとフォークの扱い

- 「**例外は失敗ではなく情報**」: 3つのチームが同じ variant を独自に作ったなら、それは違反が3件ではなく**カバレッジの穴が1つ**あるというシグナル（出典: [[Your Design System Is Slowing Your Team Down, Not Speeding It Up]]）
- シャドウライブラリは「公式システムの失敗の地図」であり**次バージョンのロードマップ**。作った者を罰するのではなく研究し、優れたものは公式へ昇格させる（出典: [[What Actually Happens to a Design System When the Founder Leaves]]。[[デザインシステムのガバナンス]] の影のシステム論と同型）
- フォーク要求への3分岐: (1) 小さいギャップなら**1週間でパッチ**を出す (2) 大きければ**期限付きの公認フォーク**を認める (3) 既存機能で満たせるならリダイレクトする。健全性指標があればフォークへの対応は道徳的非難から診断的対応に変わる（出典: [[Owning the Design System]]）
- **「妥協の博物館」は機能している姿**: 成熟したシステムの例外・変種の一つひとつは、法的要件・パフォーマンス予算・待てないアクセシビリティ修正といった現実の制約下でなされた**意思決定の化石記録**であり、3年運用して例外ゼロのシステムはむしろ誰にも使われていない兆候。優れたチームは例外と戦わず3つの実践で受け止める——①what だけでなく **why を文書化**する ②廃止（deprecation）を失敗ではなく**機能**として公開の記録付きで行う ③**ドリフトを予算化**し早期検知のガバナンスを設計する。これから始めるなら想像上の最終形ではなく最小の使えるコアを作り、**例外の発生箇所を計測**する。「システムの仕事は成長するプロダクトの混沌をユーザーに転嫁せず吸収すること」（出典: [[Your Design System Isn’t Broken. It’s Just Honest.]]、Shiva Padival）

## 「見た目は似ているが機能が違う」問題

出典: [[翻訳記事：デザインシステムのジレンマ：見た目は似ているが、機能が違う｜Nobuya Sato]]

- Badge（静的なメタデータ表示）と Pill（操作可能な選択の表示）、Button と ActionButton、Select（単一選択）と Dropdown（複数選択）のように、見た目がほぼ同じで機能が違うコンポーネントは誤用が頻発する
- それでも統合しない理由: (1) プロパティの組合せ爆発を避ける（インタラクション・状態・フィードバックの必要オプションが大きく異なる） (2) 片方だけ独立に進化させられる (3) UIに階層を導入できる
- 文書化の限界: 「私たちは問題がある時だけ文書を見て、その時でさえ答えより疑問が増える」。対策は開発前のデザイン+エンジニアレビュー、デザインファイルへの注釈とコンポーネントへのリンク（注釈の体系化は [[デザインシステムとアクセシビリティ]] を参照）、そして文書化と教育への継続投資。Nathan Curtis「適切な文書化は無料ではない。計画、努力、プロセスを要する」
- スタートアップがスケールし始める時期につまずきやすい（明文化がなく、投資の余裕もない）。参考リソースとして [[Home  The Component Gallery 2|The Component Gallery]]（https://component.gallery/）

## 強制の副作用

- 出来合いコンポーネントの押し付けは「あなた方が適切な判断を下せるとは思えない」というメッセージに映り、採用を阻害する。ルールとガイドラインを提供する宣言的アプローチは支配性が低い（代償は精緻さと習得コスト）。詳細は [[宣言的デザインシステム]]（出典: [[宣言的デザインシステム（翻訳）]]）
- Trueman 自身もこの緊張を認めている: デザインシステムチームは歴史的にゲートキーパーではなくヘルパーとして振る舞ってきたし、「硬直的な強制は反感と回避策を生む」。ただし validation は取り締まり（policing）に感じさせない設計ができる——「良い validation は野球の**ストライクゾーン**のようなもの。明確な境界、一貫した判定、時間を無駄にする論争の減少」（出典: [[Your design system has opinions. They’re just not being enforced]]）
- **Escape hatches（公認の逃げ道）**: 機能要求に「実装まで1ヶ月」としか返せないシステムは、チームを独自実装へ走らせ、利用の分析可能性と復帰の動機を失わせ、「デザインシステムを無視する文化」を定着させる。一時解決の逃げ道を恐れず提供する——ただしスタイルオーバーライドではなく **composition として**提供する（API の一部なので DS チームが利用実態を把握できる）（出典: [[Building Durable Component APIs for Design Systems – Blog – Supernova.io]] = Booking.com の Dmitry Belyaev。API 設計の全体は [[コンポーネント設計]] を参照）。[[デザインシステムのガバナンス]] の影のシステム論・Doctolib の「静かな違反より文書化されたパターン」と同じ結論。escape hatch は「**穴ではなく看板付きの扉**」——どこが公認の出口かを明示し、通った形跡を観測できるようにする（出典: [[Most Design Systems Don’t Break Because of Buttons]]）
- 強制しない側の設計例: [[SmartHR Design System]] は自らを「**妥当な意思決定を早めるための補助線であって、法律ではない**」と定義する。“デザインシステム警察”は存在せず、ガイドライン通りでなくてもリリースでき、提供スピードとのトレードオフで「後から反映」「対応しない」も開発チームが判断する（出典: [[SmartHRのプロダクトデザインの生産性を高める“デザイン”のためじゃないデザインシステムとは（Schema2022）｜wentz｜note]]）。Trueman の validation 論とは「何を機械で保証し、何を人の判断に残すか」の線引きが対照で、SmartHR は文言・パターン選択のような文脈判断を人に残し、実装済みコンポーネント（SmartHR UI）が下限品質を担保する構図
- 利用する「チーム」が人間・AIエージェント・その両方になる時代には、解釈に委ねる運用は成立せず、契約の機械的強制が前提になる（出典: [[Your design system has opinions. They’re just not being enforced]]）。関連: [[AI時代のデザインシステム]]

## ツール層の「管理された柔軟性」 — Figma Slots の教訓

以下すべて出典: [[Slots! Finally. Also… not quite.]]（ネイティブ Slots の1.5ヶ月実運用批評）

- Instance Swap が提供してきたのは「**境界内の自由**」（システムが許した選択肢の中で交換する）だったのに対し、ネイティブ Slots は「**制約なしの合成**」——スロット内に何でも置ける。管理された柔軟性の喪失は目に見える破壊ではなく**静かなシステム崩壊**（ドリフト）として現れる。validation 層の議論（前述）がデザインツール層にもそのまま必要になることを示す事例
- 仕様上の欠陥も確認済み: バリアントごとに異なるスロット構成を組むと、利用側の最初の編集で全バリアントのスロット構成が上書き破壊される（サポート回答で仕様と確認）——ブレークポイント別カードのような基本ユースケースが成立しない
- 結論として「ガバナンスなき合成」が既定になった現状での Slots 前提のシステム再設計は時期尚早
