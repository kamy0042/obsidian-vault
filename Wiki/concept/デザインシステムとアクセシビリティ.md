# デザインシステムとアクセシビリティ

## 概要

「アクセシブルなコンポーネントを揃えればアクセシブルなデザインになる」は、成熟したデザインシステムを持つ組織ほど陥りやすい誤解（出典: [[デザインシステムの注釈、パート1 アクセシビリティ]]）。アクセシビリティはデザインシステムにおいて**曖昧さのコストが最も高い領域**であり（出典: [[Why Design systems Fail]]）、コンポーネント品質・ドキュメント・注釈（annotations）の3点で支える必要がある。

## 静かに蓄積する失敗モード

以下すべて出典: [[Why Design systems Fail]]

- a11y の失敗は宣言的には起きない。ドキュメントの小さな曖昧さがチームごとの実装差になり、欠けたインタラクション状態が別々のエンジニアに別々に補われ、フォーカス管理がシステムでなくローカルに決められて、静かに蓄積する
- 問題はチームが a11y を軽視していることではなく、システムが「**正しい選択を簡単に、誤った選択を可視化**」できていないこと。アクセシブルなパターンの理由が説明されていなければ、理由を知らない誰かがそれを改変する
- 曖昧さの帰結は法的にも重大で、既に十分なサービスを受けていないユーザーに不均衡に降りかかる。a11y ドキュメントを第一級で扱わないシステムは、ライブラリがどれだけ充実していても成熟しているとは言えない

## アクセシブルなコンポーネント ≠ アクセシブルなデザイン

以下すべて出典: [[デザインシステムの注釈、パート1 アクセシビリティ]]（GitHub Accessibility Design チーム）

- アクセシブルなコンポーネントを並べても、ページの**見出し階層**は自動では正しくならない（アクセシブルなカードが H4 を持ち、H2 の直下でレベルスキップして構造を壊す例）
- コンポーネントの利用は文脈依存: 同じ画像でも置かれる場所で alt テキストは変わる。同じ入力コンポーネントで作ったフォームでも必要なエラーバリデーションメッセージは違う。ガイドラインが想定しないレイアウト・ズームレベル・画面向きで機能や文脈が失われうる
- したがって**デザインシステムの採用は監査指摘をゼロにしない**
- アクセシビリティは二値ではない: 「完全にアクセシブル」はほとんどの場合誤称であり、残る作業がどれだけあるかの問題。WCAG は基盤だが、その Success Criteria は「あなたのユーザー」固有のニーズまでは捕まえられない。Primer の品質は支援技術（AT）常用ユーザーの直接参加と実ユーザーテストによる

## 認知アクセシビリティはジャーニーから創発する

- 個々のコンポーネントでコントラスト、ラベル、ARIAが正しくても、中断で入力が失われる、エラーから回復できない、製品ごとにナビゲーションが変わるといったサービス全体の挙動は認知アクセシビリティを損なう。これはコンポーネントの属性ではなく、**ジャーニー全体から創発するシステム特性**である（出典: [[People are the point Why cognitive accessibility needs to be part of your design system]]）
- DWPは長時間の離席可能性を考慮するsession timeoutを、UK Home Officeは保存の有無と再ログイン後の復帰位置まで文書化している。見た目だけでなく、作業を中断・再開できる**復帰可能性**をパターン化する（出典: 同上）
- タイムアウトやアップロードの設計は技術・インタラクション・コンテンツ・リサーチの一職種に閉じない。認知障害のある人と、ステップ単位でなくチャネルをまたぐエンドツーエンドのジャーニーを共同検証する（出典: 同上）
- WebAIM Million 2026では95.9%のホームページに自動検出可能なWCAG違反があり、平均エラー数は前年比10.1%増の56.1件だった。原典はAI支援コーディングを単独原因とはせず、複雑化や第三者ライブラリと並ぶ潜在要因としている（出典: [[People are the point Why cognitive accessibility needs to be part of your design system]], https://webaim.org/projects/million/）

## 注釈（annotations）という補完

以下すべて出典: [[デザインシステムの注釈、パート1 アクセシビリティ]]

- 注釈 = **視覚的に表現されないデザイン意図を明示する**ノート。AT のナビゲーション経路、ラベルのない要素の代替テキスト、ビューポート・画面向き・ズームでのコンテンツ変化、モバイルの仮想キーボード種別、フォーカス管理などに答え、コミュニケーションギャップ・監査指摘・高価な手戻りを防ぐ
- GitHub は CVS Health の旧 Inclusive Design チームによる OSS 注釈キット（Figma Community で最も使われる部類）を土台に **GitHub Annotation Toolkit** を構築（公開予定）。a11y 専門家でなくても使えるようゼロから再構築し、インライン文書を追加——「同僚のいる場所で会う」方針
- 注釈はオーバーヘッドにもなる: 専門家だけがデザインと技術仕様を解釈する体制はハンドオフを遅らせる。対策は (1) コンポーネントに作り込み済みの a11y（見出しレベル・セマンティクス・ランドマーク・装飾アイコン等）は再注釈しない (2) インスタンスごとに変わる詳細だけを注釈する
- **Preset annotations**: コンポーネント固有の「空欄を埋めるだけ」の注釈。アコーディオンなら、任意タイトルの有無と各項目の見出しレベルだけを Stamp + Details の2つで指定する。Figma のコンポーネントプロパティからは分からない詳細（リンクかボタンか＝LinkButton か Button か、視覚的に隠すテキスト、データ送信属性の要否）を推測任せにしない
- **Primer A11y Presets**: 実装時に詳細が欠けると監査指摘（ラベル欠落・エラーバリデーション・HTML/ARIA 属性）に繋がりやすい頻出10コンポーネント向けの Preset セット。各 Preset はコンポーネント docs と Storybook デモへリンクし、記入ガイダンスを内蔵——デザイナーが Figma を離れずに支援を得られる

## コンポーネント・トークン単位の品質保証

- メルカリ Design System Web は各コンポーネントを **WCAG 2.1 AA** に到達するよう実装し、「利用者は正しく設置するだけでページの大部分がアクセシブルになる」ことを保証する。検証は @open-wc/testing による機械検査＋コントラストは Lighthouse / Storybook addon-a11y＋**キーボードとスクリーンリーダーの実機検証**の三層。i18n は逆に「ライブラリ側は何もしないことを徹底」し、alt / aria-label まで attribute 提供で利用者設定を必須にする（出典: [[新しいメルカリDesign System Web  メルカリエンジニアリング]]）
- enechain はプロダクト要件になる前に DS 側で a11y ガイドライン＋チェックリストを整備し全コンポーネントで完遂——「デザインシステムレベルで達成しておけば、プロダクトはコンポーネントを使うだけで一定の要件を守れる」（出典: [[デザインシステムの成長。そして、これからどう向き合うか - enechain Tech Blog]]）
- Ubie の言語化: 「**アクセシビリティを主語にしてしまうと動きにくい場面もある**」ため、「デザインシステムを使うと a11y に十分配慮したプロダクトが作れます、という状態」を目指す——a11y を説得の主語ではなく、デザインシステムの内蔵品質にする戦略（出典: [[Rebooting Ubie Vitals Design Systems]]）。DTx（医療）が Ameba Accessibility Guidelines を土台に医療観点を足した例も含め、公開ガイドラインが業界を越えて再利用されている（出典: [[DTx事業部のデザイン基盤整備のこれまでとこれから｜kay｜note]]）
- Yahoo! JAPAN の Riff は、スタイルガイドで定めたコントラスト比 4.5:1 を**全テキスト色×背景色の組み合わせで機械計算**し、OK / NG の一覧表として提供——利用者はスタイルガイドに載っていないパターンでも問題ない組み合わせを一目で選べる（出典: [[フロントエンドから取り組むデザインシステムの改善 UI - Yahoo! JAPAN Tech Blog]]）
- パレット番号やOKLCHのL値はアクセシビリティ適合の代替にならない。同じLでも色相・彩度で相対輝度が変わるため、実際の使用時の前景・背景ペアで検証する（出典: [[Stop using OKLCH lightness for your color scale]]）
- Wantedly は hover / focus 等の状態変化（Reaction）の実装に React Aria を内部利用——「自分で実装するとアクセシビリティ観点などで考慮漏れするのが目に見えている」。a11y を自前実装せず専門ライブラリに寄せる判断（出典: [[React でデザインシステムを正しく実装する - コンポーネントカタログを超えて  Wantedly Engineer Blog]]）
- モーショントークンに **reduced motion を最初から組み込む**: Figma とコードで同時に存在する共有命名のトークンとして設計し、動きの a11y を後付けオプションではなく既定にする（出典: [[Why Design Systems Need a Shared Language, Not Just Documentation.]]）
- [[relay Design System]] は、高齢者が主要利用者で自治体とも連携する事業特性からa11yを「当たり前品質」と定義する。WCAG 2.2の各基準とコンポーネントについて、**デザインシステムが担保する機能**と**プロダクト／AIエージェントが実装時に必ず行う対応**を分け、たとえばIcon Buttonではフォーカス可視化をシステム側、文脈に応じた`aria-label`を実装側の責任として明記する（出典: [[AIネイティブを目指した「これまで」と「これから」｜agu  relay（リレイ）]]）
- 同システムを使った本体サイトの置換では、スクリーンリーダー対応、フォーカスリング、キーボード操作、強制カラーモード等を約150箇所改善したと報告する。修正を個別対応で終わらせず、コンポーネントや責任分界へ戻してAIが同じ失敗を繰り返さない仕組みにした（出典: 同上）

## a11y ドキュメンテーションの要件

- 完全な a11y ドキュメントが含むもの: 期待されるキーボード挙動とフォーカス順序 / ARIA のロール・状態・プロパティと**その理由**（rationale）/ 必須・任意のインタラクション状態 / スクリーンリーダーの読み上げ内容 / 既知の制限と推奨回避策（出典: [[Why Design systems Fail]]）
- a11y 原則（可視ラベル必須）と業界標準 UX が衝突した場合の例外処理と「例外のハイパードキュメンテーション」は [[デザインシステムの強制と例外]] を参照（Doctolib の事例）
- 専任エンジニア不在の組織では、ボタンの a11y 修正ひとつに5プラットフォームのエンジニアへの個別依頼が必要になり、機能開発に常に劣後する（Cisco の事例。詳細は [[デザインシステムと組織構造]]）

## 法規制の時代 — EAA 施行と APCA への移行

以下、断りのないものの出典: [[Design Systems in April 2026 The Infrastructure Is Here. Most Teams Still Aren’t.]]

- **欧州アクセシビリティ法（EAA）が2025年6月に完全施行**。規制当局の監査が始まっており、EN 301 549 を満たさないデジタル製品は市場からの排除や10万ユーロ超の罰金がありうる。EU ユーザー向けに展開する製品にとって a11y は「設計品質の問題」から「**法的責任の問題**」に変わり、組織内で誰がリスクを負うかが変わる
- WCAG 2.1 のコントラスト比計算は数学的欠陥が広く認識されている（現代のディスプレイ・特にダークモードで、視覚疲労やハレーションを起こす色を合格にしてしまう）。業界はフォントの太さ・サイズ・周囲の明るさを考慮する **APCA**（Advanced Perceptual Contrast Algorithm）へ移行しつつある——実務は「**WCAG 2.1（法的最低基準）と APCA（体験の現実）の両方に同時準拠**」
- 2026年の標準構成は CI/CD パイプラインへの自動リンティング組込み: AI が生成したコンポーネントがどちらかに違反したら**ビルドを落とす**。なければスプリントごとにコンプライアンス負債が積もる（強制の実装論は [[デザインシステムの強制と例外]]。APCA の先行採用例は [[カラーシステムの設計]] の Gaudiy 事例）
- **トークンは法務隣接アーティファクト**になった: EAA のコントラスト要件や訴訟の先例（Target の600万ドル和解）を踏まえると、色トークンの定義・変更は法的リスクの管理点であり、デザインの裁量だけでは動かせない（出典: [[Design Systems as Brand Ops Tokens, AI and Stopping Brand Drift]]）
