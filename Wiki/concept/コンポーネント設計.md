# コンポーネント設計

## 概要

UI を独立した再利用可能な部品に分割し組み合わせる設計論——ソフトウェア工学の「分割統治」の UI への適用で、関心の分離・問題の局所化・並行開発・テスト容易性をもたらす（出典: [[デグレと手戻りを減らす。今こそコンポーネントの話をしよう  レバテックラボ（レバテックLAB）]]）。ただしこのテーマの記事群を貫くのは「**再利用・共通化は無条件の善ではない**」という警告で、ドメイン知識の混入・見た目だけの共通化・時期尚早の抽象化が、かえってデグレードと手戻りを生む。カタログ・実装配布の実務は [[コンポーネントカタログ]] を参照。

## ドメイン知識の境界

- **UI コンポーネントにドメインを入れない**: 「単一の数値を見せる UI」に API のデータモデル（Calorie、Grade）をそのまま受けさせると、同型コンポーネントの量産地獄になる。正解はドメイン中立な `Stat`（label / value / unit）に抽象化し、必要ならその上にデータモデルのマッピング層を重ねる——依存関係が正しく目に見えるようになる。「システムの根幹となる UI を抽象化しないのは設計を怠ったも同然であり、バックエンドで DB 接続から API 出力までを一纏めに書く行為と同じくらい重大」（出典: [[UIコンポーネントにドメインを入れるな]]）
- 同記事の3段階の基準: **絶対に含めない**（Button / Table / Avatar——UI ライブラリにある系統）／**なるべく含めない**（Timeline / MediaCard——業務ロジックと関連するが複数画面で横断的に使われる）／**含めて良い**（UserGradeDashboard / UserProfile——特定業務ロジック専用の画面級）（出典: 同上）
- 逆方向の失敗もある: 階層を分けず全部を「コンポーネント」一枚看板にすると（[[SmartHR Design System]]・デジタル庁が代表例とされる）全パーツの抽象度が上がり、**ドメインロジックに紐づいた再利用可能コンポーネントの不在**を生む。コンポーネントの組み合わせ方が毎回各画面の設計に委ねられ、「コンポーネントは同じなのにレイアウトが微妙に違う画面」が増殖する（出典: [[デザインシステムの議論はデザイナーとエンジニアで分岐した？ 抽象度の高いコンポーネントライブラリの弊害]]）

## 再利用の幻想と共通化のアンチパターン

- 「再利用可能になるように設計すべきだ」への反論（2016年、Elm/React 文脈）: アプリケーションを知らない疎結合部品は、引数の爆発（バケツリレー——`model` 1個で済んだものが `isEditMode, saveEnabled, flags.colors…` と増殖）と状態の重複（DatePicker が予定をキャッシュすると全体状態と二重化）を生む。部分的なモデルとビューは8割一致するが、**残り2割のために疎結合の前提が崩壊する**。共通化したい実体は「見た目」なので、データを表示するだけのシンプルな関数としてのビューを共有すれば足りる。「再利用可能なコンポーネントは幻想であり、多くの場合アンチパターン。YAGNI」（出典: [[再利用可能なコンポーネントはアンチパターン - ジンジャー研究室]]）
- **ユースケースを無視した共通化**: フォーム送信ボタンとリンクボタンは見た目が同じでも、入力（リンク先の要否）も出力（button 要素 vs a 要素）も違う。共通化しても条件分岐が増えるだけで旨みがなく、唯一の共通点であるスタイルだけを共通変数として扱うのが正しい（出典: [[デグレと手戻りを減らす。今こそコンポーネントの話をしよう  レバテックラボ（レバテックLAB）]]）
- **無理なカスタマイズは時限爆弾**: 共通リンクボタンをある画面だけ緑背景に上書き → 数ヶ月後のダークモード対応で共通側が色反転（白背景+青文字）した結果、「緑背景+青文字」の見づらいボタンが生まれる。大胆な色変更は別コンポーネント化を検討すべき（出典: 同上）
- **false reusability と useful duplication**: 「同じに見える」は統合の理由にならない——見た目が同じでも**変更理由が違う**なら別コンポーネントであり、20個の boolean フラグを持つコンポーネントは「複数のコンポーネントであることを認めていないだけ」。共有すべきでないものの共有（false reusability）より**有用な重複**（useful duplication）の方が健全で、プロダクト固有の文脈はコアに吸わせず上位層のラッパーコンポーネントに置く（出典: [[Most Design Systems Don’t Break Because of Buttons]]）。ドメイン境界論（前節）・レシピ層（[[デザインシステムの階層化]]）と同型の結論

## 品質・振る舞い・パターンから設計する

- 再利用先の数ではなく、**Clarity**（目的・状態の明瞭さ）／**Constraint**（誤用を防ぐ境界）／**Composition**（他部品との調和）の3軸で品質を評価する。公開前には実データを入れた複雑な画面で、周辺部品とともに検証する（出典: [[Reusable Does Not Mean Good The Hidden Trap of Design System Components]]）
- 外観からでなく、選択・確認・移動などの**動詞から始める**。入力・出力・制約・状態・遷移を先に契約化し、状態機械をデザインと実装の共同成果物にしてから視覚表現を設計する（出典: [[The Appearance Trap Why Components Must Be Designed Around Behavior 1]]）
- **Same action, different context test**: 破壊的操作の確認など同じ行為が製品内でどう実装されているかを横断的に並べ、差異が文脈に基づく意図か、担当チーム由来の偶発かを分類する（出典: [[Your Component Library Is Not a Design System]]）
- 単体部品の次には、余白・見出し・フォーム構造を扱う**レイアウトパターン**と、送信後のfeedback・遷移など複数ステップの行動を扱う**ワークフローパターン**を分けて整備する。初期チームでは実製品の開発を通じ、コンポーネント→パターン→ワークフローの順で育てる（出典: [[How We Built a “Functional” Design System in an Early-Stage Product Team 1]]）
- 企業横断では、画面や既存部品の類似から始めると誤ったものを標準化しうる。同じ見た目でも異なる仕事を支え、違う見た目でも同じ行動を支えることがあるため、**実ワークフロー→ユーザー課題→反復する相互作用**の順で共通性を判定する（出典: [[Beyond the Design System-Designing a Shared Enterprise Ecosystem]]）
- コンポーネントは特定のUI要求への解、パターンは反復する相互作用への解、原則は既存パターンで答えられない状況の判断基準である。将来の未設計製品を支えるには、過去のコンポーネント収集より、適応可能なパターンと原則を共有基盤に置く（出典: 同上）
- [[Adobe Spectrum]] の structural templates は、ラベル・説明・visual・affordance・group・container・list といった反復構造をトークンとコンポーネントの中間に置く同系統の実践である（出典: [[Design tokens need more than semantics]]）。

## モノリシック vs 合成（Compound Components）

- Stat を props 完結型（モノリシック）で作ると「数字だけ色を変えたい」「ラベル無し版が欲しい」のたびに内部実装へ手を入れることになる。**合成タイプ**（`Stat.Label` / `Stat.Value` / `Stat.Unit` の名前空間や分割コンポーネント）はマークアップ構造を可視化して単一責務にし、「スタイルだけ受け継いだ HTML」を組み立てる——実装は長くなるが堅牢性と柔軟性に優れる。構造の強制（Label が Root の外に置ける問題）は Context で対応できる（出典: [[UIコンポーネントにドメインを入れるな]]）
- API 設計側にも同型の結論がある: 逃げ道はスタイルオーバーライドではなく composition で提供せよ（後述の escape hatches）

## 階層モデル — Atomic Design とその代替

- デザインシステムの議論はエンジニア（React アーキテクチャ視点の Atomic Design 論——「Atoms のボタンにセマンティックな意味を与えるアイコンをどう渡すか」）とデザイナー（ブランド理念を各領域へ伝播させる意味での"システム"論）で分岐しており、コンポーネントライブラリの階層論はその断層に落ちた（出典: [[デザインシステムの議論はデザイナーとエンジニアで分岐した？ 抽象度の高いコンポーネントライブラリの弊害]]）
- 同記事が推す Heavyweight（2017）の6階層は、Atomic Design の便宜的命名（Atoms / Molecules）をブランド接続の語彙に置き換えたもの（以下すべて出典: 同上）:
	1. **Identity** — 今で言うデザイントークン。ブランドガイドラインとの繋ぎ込みが起こる最小単位で、コンポーネントではなく設定ファイル / CSS で定義する層
	2. **Elements** — Atoms 相当。ドメイン禁止。文脈や意味を与える「セマンティックなアイコン」はテキストと同じ扱いでダミーを置く
	3. **Components** — 汎用コンポーネント。「再利用ライブラリとしてデザイナーが実務メリットを感じられるのはここまでかもしれない」
	4. **Compositions** — ドメインロジックとマイクロレイアウトを注入し、ユースケース別の使い方（登録フォームは中央ボタン、サーベイは右下「次へ」）と具体的文言を定義する。Figma で Atoms と Molecules しか作れず放棄されがちな断層は、この層の不在としてプロダクトの一貫性を蝕む
	5. **Layouts** — Heavyweight 独自の概念。グリッドは「概念的な存在に見えるが、コード上は1つのコンポーネント」であり、その再利用がレイアウト一貫性の鍵
	6. **Pages / Screens** — 初めて実データ（商品情報・ログインユーザー）を流し込む層。デザイナーもダミーデータをやめてリアルに近いデータで作ると良い

## API・プロパティ設計

以下すべて出典: [[Building Durable Component APIs for Design Systems – Blog – Supernova.io]]（Booking.com principal FE・Reshaped 作者・Design System Checklist 管理者の Dmitry Belyaev）

- **Dream-driven development**: 実装を始める前に、利用者視点の理想のコードスニペットを書く。レガシーと技術制約から出発すると「作者視点のコンポーネント」になる。「The best design is no design」に倣えば「**The best API is no API**」（framer-motion 初期の magic prop が好例）——理想を定義してから、制御性・性能の必要に応じて複雑さを意図的に戻す
- **プロパティの体系的一貫性**: バリエーション制御の名前が type / mode / variant / style と混在するのを避ける。新しい見た目は「variant の値追加か、既存 variant 全体に掛かる新プロパティか」をシステム単位で判断。large の button と large の text field は同じ高さにし、スロットに収まる組合せを設計する。**「システムが許す使い方は、必ずどこかでその通りに使われる」**——未サポートのプロパティ組合せを最小化する（禁止 prop 組合せの型表現は [[デザインシステムの強制と例外]]）
- **props ドリフトの実測**: 88コンポーネント・200超 props の棚卸しで10件の語彙ドリフト（type と variant の混在、outline / outlined / bordered、sm / small / s）——一貫性は名前でなく**値レベル**から綻ぶ。また variant は「見た目の選択肢」ではなく **state のフィードバックの視覚形**であり、見た目でなく状態で命名する（danger は帰結を、success は結果を伝える）（出典: [[Building language for design systems]]）
- **Escape hatches**: 将来要求は予測しきれない。「実装まで1ヶ月」と言われたチームは独自実装に走り、移行の動機も利用の分析可能性も失われ、「デザインシステムを無視する文化」が定着する。一時解決の逃げ道を恐れず提供する——ただし**スタイルオーバーライドではなく composition で**（API の一部なので、どこで何が起きるか DS チームが把握できる）
- **Platform-first properties**: プラットフォーム統一のための新語を作らない。Figma では image variant、Web ライブラリでは src。Swift は starting/leading、CSS は start/end——各プラットフォームの母語に合わせる方が全員に使いやすい
- 決定ログを「チームレベルのコードコメント」として残す（1年後の新メンバーの「なぜ」に答える）。最初から理想の API は作れない——破壊的変更の戦略と段階的廃止を前提にする
- **API 設計は2つの想像上のノブを回す仕事**——柔軟性のノブと使いやすさのノブ。「何でもできるコンポーネントは使うのが難しすぎ、使いやすすぎるコンポーネントは他のユースケースのために再設計が要る」。悪くて不格好な API 判断は紙の切り傷（papercut）で、切り傷が積もるとシステムは死ぬ。ビジュアルリグレッションテストは「ほぼ無料で書けて金の価値がある」（出典: [[Design System Wisdom 2023]]）
- 同記事より「**作るべきでないコンポーネント**」: 自前の select menu・date picker・data table を作る商売に本当に入りたいか？——「あなたのコンポーネントライブラリのコードは、数千人のコントリビューターを持つ数十の OSS と競争している」。組織として**ボックスモデルの語彙を1つに決めて文書の最上部に置く**（100×100の画像に padding 5px・border 2px——最終寸法は？ 答えは2つある。「私は半年ごとにこれを忘れる」）。定期的な剪定も忘れない——「最後にコンポーネントを削除したのはいつ？」。1つのコンポーネントに機能要求が集中したら API が柔軟でないサイン、書き直しを恐れない（出典: 同上）

## レイアウトモデルによる統合 — Uber Base の再設計

以下すべて出典: [[Design Systems That Spark Joy Rethinking Layout For Scalability  by Maria Christopher  Design Systems For Figma]]（Uber Base）

- カタログの広さを成熟の証と信じてコンポーネントを増やした結果、**プラットフォームあたり60〜70個**で冗長性と不整合が効果を蝕み始めた（[[デザインシステムの過剰設計]] の「幅ではなく深さ」と同じ帰結）。転機は「Figma では共通ベースを持つ入力系コンポーネント（Text field・Select・Search…）が、**コードでは共有コードをまったく持っていなかった**」という発見
- 再出発の4原則: **自己完結**（他チーム管理のコンポーネントに強い意見を持たない）／**保守性**（レガシーフレームワーク上のリスクになる複雑なカスタム解を避ける）／**持続可能な採用フロー**（移行コストが管理可能でユースケースが一貫していると確信できるときだけ作る）／**規模と健全性のバランス**
- **カスタマイズ3手法の使い分け**: variants（複数文脈で一貫した機能が要るとき。ただし急速に複雑化する）／custom content slots（時間とともに進化するコンポーネント向けの柔軟性）／overrides（特例専用。過剰なカスタマイズを制限して安定を守る）。柔軟すぎるコンポーネントは「使うのが難しい複雑なフレームワーク」になる（card で実証済み）——high-utility なコンポーネントは機能を、情報表示系は適応性を優先する
- **「遠くない従兄弟」の統合**: List Item と Accordion、Message Card と Card は差分がほぼ様式のみと判明。**コンポーネントトークンでは順序や状態マップは扱えない**（トークンは視覚的統一には効くが構造・機能の複雑性には届かない）ため、**再利用可能なレイアウトモデル**を導入——Label＋入力コンテナ＋Hint text という共通構造を root class → 汎用コンテナ → 特化クラス（Text / Select / PIN…）の継承で実装し、共有プロパティを標準化しつつ必須のカスタマイズは許す
- 効果: File Uploads や DateTime Selects など複雑コンポーネントの開発が加速／カスタムスクリーンリーダー対応が類似コンポーネントへ**自動で**波及／浮いたサイクルで状態理解を助けるマイクロアニメーションを探索

## コンポーネント命名

- **fun は名付けた本人だけの fun**: Pinterest Gestalt のカラーパレット「Matchacado」は clever で creative で horrible な命名の代表例（筆者自身の最大の後悔）。「緑を塗るたびに Matchacado と打つの？ なぜ green と呼ばない？」というエンジニアの問いに答えられなかった（出典: [[デザインシステムにおける命名―そしてそれがなぜ最悪なのか]]（元 Pinterest Gestalt の PJ Onori））
- 同記事の経験則（出典: 同上）: 名前は自己記述で成功する（「Dishwasher は史上最高の名前——何をするものか誰も聞かない」）／**1つのものに1つの名前**（Web の list と iOS の table のようなプラットフォーム間齟齬も、システムとしては1つに決める）／短く単純な少数の語で（Loading Spinner は回転をやめた途端に破綻する）／**頭字語になったら命名は失敗**（Floating Action Button → FAB）／形・機能が違うのに音が近い名前を避ける（Tag と Tab は1タイポで入れ替わる）／タクソノミーを扱える人材は多くのチームにいない——名付ける前に二度考える
- 実在デザインシステム横断のコンポーネント名・別名リファレンスとして The Component Gallery がある（Accordion の別名9種、Button 135例など、「一般名」と同義語を調べる統制語彙づくりの実務リソース）（出典: [[Home  The Component Gallery 2]]）
- トークン命名の抽象性の問題（smedium・数値ストップ）は [[デザイントークンの命名]] を参照

## プラットフォーム間の一貫性 — Parity vs Specific

以下すべて出典: [[クロスプラットフォーム設計：チャレンジャーバンクのモバイルアプリケーションを考察]]（Scott Logic、2019。英チャレンジャーバンク3社の比較）

- クロスプラットフォーム戦略は **Platform Parity**（iOS / Android で同一の機能と視覚言語。必要ならカスタムコンポーネントを作る）と **Platform Specific**（各プラットフォームの HIG / Material Design のネイティブコンポーネントと慣習に従う）を両端とするスケール上の位置取り
- **一貫性の相対性**: ユーザーは同じ OS を長期間使い続けるため、「自社の iOS 版と Android 版の間の一貫性」より「**同じプラットフォームの他アプリとの一貫性**」の方が重要になりうる
- カスタムコンポーネントは高コスト・高リスク（開発工数・追加テスト・UX/技術両面の失敗リスク）。一方、ネイティブ完全準拠は独自の体験・デザイン言語を作りたい企業には窮屈——「なぜその判断か（UX 起点か、単にガイドライン追従か）」を説明できる程度にプラットフォーム自体を理解することが前提
- Parity 志向では iOS が「メイン」に偏る構造要因がある: iOS ユーザーの収益性の高さと、デザインツールの iOS サポート優位。Android が後付けになりがち
- 事例の位置取り: **Monzo** はネイティブ活用+似た見た目（検索は iOS が検索バー・Android が FAB。機能も iOS が先行し、コミュニティが差分を追跡）、**Starling** はカスタム多め（独自スライダー等、視覚言語の統制を優先）、**Revolut** はパリティ寄り（Android にも iOS 風の見た目。ただしタイトル配置やボタン位置は各プラットフォーム慣習に合わせる）
- コンポーネント API 側の結論と合わせると、**機能・コンポーネント名はシステムとして1つに統一し、表現・プロパティ・操作慣習はプラットフォームの母語に合わせる**という分業に収斂する（Belyaev の platform-first properties、PJ Onori の1物1名。前節参照）
- **consistency ではなく cohesion、cross-platform ではなく multi-platform**（[[Style Dictionary]] 作者 Danny Banks）: 「一貫性」は合致/不合致の偽の二分法を招くが、実際には一貫性には層がある——プラットフォーム固有のコンポーネントと慣習を使いながら「良きプラットフォーム市民」としてまとまり（cohesion）は保てる。顧客は同一デバイス上でプラットフォームを切り替えず**デバイスをまたいで移動する**（Netflix は TV・スマホ・PC で違う振る舞いを期待される）。「cross-platform」は全プラットフォームで同一の見た目・機能という荷物を背負った語であり、multi-platform は「実装や体験は異なってよい」を含意する。公開デザインシステムのうち Web 以外をサポートするのは10%未満（2020年時点）で、Lightning・Polaris・Backpack・Cedar・Fluent・Material・Spectrum 等が数少ない例（出典: [[An Introduction to Multi-Platform Design Systems]]）
- 同記事のまとまり（cohesion）の3層: (1) **基盤**——原則・Voice & Tone・ブランドに加え、**通知・メールを横断編成する統一コミュニケーション戦略**（プッシュ通知と Web の通知一覧とメールが噛み合わないと体験は分断される）(2) **トークン**——プラットフォーム非依存に見た目を定義する視覚的まとまり（「トークンは multi-platform の一部にすぎない」と作者自身が釘を刺す）(3) **共有コンポーネント定義**——名前・API・ドキュメントは共有し、実装はプラットフォーム別（web component / Kotlin / Swift で同名同プロパティ）。**分岐は意図的であれ**: 同じ目的の Alert（web）と Banner（mobile）、variant と type、error と danger という無意図の分岐は「仮説ではなく自分のシステムの実話」。Lyft は**デザインと実装を並行で進めて**実装中の議論を両プラットフォームで一緒に消化する。対策としての **documentation driven development**——コードを書く前にドキュメントとサンプルコードを書き、収斂/分岐を意図的に選ぶ
- 同記事の「efficiency ではなく **autonomy**」: フレームワーク（React Native / Flutter / WebView）は常には答えにならない（Lightning は代わりにプラットフォーム別トークンパッケージを配る）。むしろ障壁を removal する——コンパイル不要・全コードベース不要・ネイティブツールチェーン不要でシミュレータ上の UI コードを書ける開発環境、「**意図を表現できる最低の忠実度**」でモックアップ依存を減らし、デザイナーと開発者のペアリングで「数週間の往復ではなく数時間で本番 UI」。ゴールは「consistency と efficiency ではなく **cohesion と autonomy** を耕す」こと（出典: 同上）

## CSS・レイアウト分類（mizchi 流）

以下すべて出典: [[コンポーネントベースで開発する時の CSS の書き方とコンポーネントの分類 (自己流)]]

- React コンポーネントの管理単位と CSS レイアウトの管理ポリシーを**完全一致させる**前提での4分類: **ロジック**（Provider / hooks のみ。CSS・DOM 実体なし）／**レイアウト**（grid / flex で自領域の分割のみが責務。レスポンシブもここ。分割領域に置けるブロックは1つか0）／**ブロック**（width / height 100% で与えられた領域を埋める——どのブロックも交換可能になる）／**インライン**（コンテンツでサイズが決まる）
- 結果として Layout → Block → (Layout → Block → …) の繰り返し構造になる。利点は配置変更・画面モード追加への強さと、高さの事前確定によるスケルトンスクリーン・クリティカルレンダリングパス最適化。弱点はリキッドレイアウトでの height 継承ポリシーと overflow 事故
