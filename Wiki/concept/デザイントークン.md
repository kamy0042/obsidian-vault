# デザイントークン

## 概要

色・タイポグラフィ・余白などのスタイル属性（＝デザイン上の決定）に名前を付け、あらかじめ定義された構造で保存する手法。デザインシステムを構成する最小単位とされ、デザインと各プラットフォーム実装が共通で参照する Single Source of Truth になる（出典: [[Design tokens 101]], [[デザイナーと開発者の連携を効率化するデザイントークンとは何か？  アドビUX道場 UXDojo]]）。Salesforce Lightning Design System の Jina Anne が提唱。本人は「デザイントークンは方法論であり、ただ変数化することではない」と強調する（出典: [[デザイントークンって何？｜seya｜note]], [[Design tokens 101]]）。

## トークンの解剖学 — 名前と値の疎結合

- 構成要素は **Name / Type / Meta / Data** の4つ。Name は用途が即座に伝わること。Type は使い方の制約（color トークンは塗れるが animation の duration には使えない）であり、ツールが扱える安定したインターフェースを型ごとに保つ。Meta は作者・説明・導入/更新日など（ドキュメント自動生成に使える）。Data は技術非依存フォーマットの実値（色なら RGBA 等。text-style なら family/size/weight/line-height/letter-spacing と修飾の複合）（出典: [[The Anatomy of a Design Token]]）
- 原型は Apple の **Space Gray**: 覚えやすい固有名を実際の色と疎結合にしたことで、2013年の初出以来何度も値を変えながら名前は不変を保てた。「名前がもっとも重要な部分」（出典: [[The Anatomy of a Design Token]]）
- 変数との違いは**用途情報**: `$blue-400` は値を構造化するが「どこで使うべきか」を伝えず、デザイナーに判断を残す。`$button-cta-background-color = $blue-400` は名前が判断を代行する（出典: [[デザイナーと開発者の連携を効率化するデザイントークンとは何か？  アドビUX道場 UXDojo]]）

## 階層 — プリミティブ / セマンティック / コンポーネント

- 「値を表すもの」（Primitive / Global / Brand）と「意味を持つもの」（Semantic / Alias / Application）の2層に分けるのが基本形。さらに用途特化の Component トークンを置く場合もある。呼称は揺れており、2022年時点では Global / Alias が優勢（出典: [[デザイントークンって何？｜seya｜note]]）。国内の公開例では SmartHR がプリミティブ＋セマンティクスの2種のみを提供し、SLDS と Spectrum を参照文献に挙げる（出典: [[デザイントークン  プロダクト  SmartHR Design System]]）。Adobe Spectrum の Global / Alias / Component-specific と使用指針は [[Adobe Spectrum]] を参照
- **文脈とユースケース・カバレッジの逆相関**: プリミティブは設計意図を持たずどこでも使える（カバレッジ最大・文脈ゼロ、単独では視覚言語を作る価値がない）。セマンティックは文脈を持ち、一般的なほど広く特殊なほど狭い（`text-color-default` は全域、`title-color-default` は title のみ）。コンポーネントトークンは最も特定的で再利用性が最小（出典: [[デザイントークンに詳しくなれるスクラップ]]）
- プリミティブ（Global）の直接使用は避ける——名前が目的を語らないため。Alias が参照する Global を差し替えるだけでテーマ切替（ダークモード等）が実現する（出典: [[デザイントークンって何？｜seya｜note]]）
- Material Design の md.ref / md.sys / md.comp 3階層が参照モデルの代表例。詳細は [[Material Design]]
- 用語の別系統: **option**（what＝選択肢。primitive / base / core / foundation / reference とも）/ **decision**（how＝適用方針。semantic / system とも）/ **component**（where＝適用先）という3つの問いによる整理（Samantha Gordashko の用語）。大規模システムでは2〜3層が一般的。3層は DX が最良だがトークン数と保守が増えるため、主要な決定が安定しているなら option + decision の2層で始めて必要時に第3層を足すのがよい——1層だけでも「CSS の長さ単位は最大43種」のような日常判断を大きく減らせる（出典: [[トークンベースのUIアーキテクチャを設計する]]）
- **フラットな1層構造の罠**: 値に名前を付けただけの単層トークンは「名前が変わっただけ」で、UI と具体値の結合は残ったまま——参照の階層があって初めて交換可能性（テーマ・リブランド耐性）が生まれる（出典: [[The Token Structure That Survives Five Products (Google Uses It Too)]]）
- 意味層の適正抽象度（ゴルディロックス・ゾーン）、過剰抽象化の認知コスト、コンポーネントトークンの損益は [[セマンティックトークン]]、命名の体系は [[デザイントークンの命名]] を参照

## 成熟度の3段階

いずれも出典: [[Design tokens 101]]

1. **トークンなし**: スタイルがハードコード。一元管理の場がなく、リデザインは全ファイル捜索、テーマ設定はほぼ不可能
2. **非構造化トークン**: 一元管理はされているが命名が非一貫（最も一般的な状態）。値ベースの名前は `babyBlue: orange` という矛盾を生み、変更のたびにリネームを強いる
3. **構造化トークン**: デザイナーと開発者がトークンの形と命名規則に**積極的に合意**している状態。共通語彙（`primary1`）で会話でき、リデザイン・テーマ設定が自明になる

## 何をトークン化するか

- 対象プロパティ: color / typography（複合）/ border-radius / space / size / shadow（elevation）/ animation（duration + easing）/ z-index。全部を定義する必要はなく、プロダクトごとに一貫させたいものを優先する（出典: [[デザイントークンって何？｜seya｜note]]）
- 基準を決める: 「X回使われている」は単純だが効果的。1箇所でしか使われないスタイルにトークンは不要（出典: [[デザイナーと開発者の連携を効率化するデザイントークンとは何か？  アドビUX道場 UXDojo]]）
- 出発点はインターフェイスインベントリ（Brad Frost）や CSS Stats による現状監査——ほぼ同じ色の統合候補が見える（出典: 同上）
- **モーションのトークン化**: duration / easing を Figma とコードに同時に存在する共有命名で定義し、reduced motion 対応を最初から組み込む。前提として「不可視であるべき」functional motion と「ブランドの人格を運ぶ」expressive motion の区別があると、トークンがモーションを議論する語彙として機能する（出典: [[Why Design Systems Need a Shared Language, Not Just Documentation.]]）

## 効用

- **共通語彙**: デザイナーと開発者が同じ名前でスタイルを参照し、推測とやり取りが減る（従来は開発者が hex 値を聞き返して終わっていた）（出典: [[Design Tokens An Introduction]], [[デザイナーとエンジニアの共通の語彙を持つために  第1回 デザイントークンとは]]）。「12px と 14px の2種類あるのは意図的ですか？」という数値確認の Slack 往復が消えた事例（出典: [[【デザイン】新規サービス開発でデザイントークンを導入してみました！ Design - Qiita]]）
- **一括更新とテーマ設定**: 中央の1箇所を変えれば全消費者に伝播する。重複の排除は安全性でもある（出典: [[Design Tokens An Introduction]]）。Atlassian の定義では**テーマ＝トークンの集合を特定の値へマッピングしたもの**（ライト／ダーク／ホワイトレーベルはすべてテーマ）であり、「1つのテーマでデザインすれば残りは無料で手に入る」。ただし「色が合って見えるから」でトークンを選ぶと他のテーマで体験が壊れる（出典: [[Design tokens - Foundations - Atlassian Design System]]）
- **技術非依存**: JSON で著述し SASS/Swift 等の各形式へ変換。スタイリング技術の移行（SASS→CSS-in-JS）も容易になる。NPM 配布ならリリースノート付きのバージョニングができ、トークン削除が消費者への事前告知になる（出典: [[Design Tokens An Introduction]], [[The Anatomy of a Design Token]]）
- **作り手の迷いを減らす**: デザインシステムは使い手の迷いを減らすと語られるが、選択肢の限定は作り手の意思決定も速める（フォントサイズを1pxずつ試す作業が、調和が担保された数パターンからの選択になる）（出典: [[【デザイン】新規サービス開発でデザイントークンを導入してみました！ Design - Qiita]]）
- デザイン/UX 側にスタイルのオーナーシップが移る（出典: [[Design Tokens An Introduction]]）
- **ブランドガバナンスのインフラ**: トークンは個別制作物のスタイル指定を超え、ブランド逸脱（ドリフト）を構造的に防ぐ統治装置と再定義されつつある（出典: [[Design Systems as Brand Ops Tokens, AI and Stopping Brand Drift]]）。詳細は [[ブランドとデザインシステム]]

## 導入戦略

- **ミニマムスタート**: 全構成要素を一度にトークン化しない。新しい仕組みはエンジニアに認知負荷を伴い、一度に多く導入すると生産性が下がる。困ることが多い高頻度要素（色・スペーシング・タイポグラフィ）から始める。レコチョク P!TNE はこの3種＋2階層（グローバル/セマンティック）で開始し、チームの納得感を保った（出典: [[【デザイン】新規サービス開発でデザイントークンを導入してみました！ Design - Qiita]]）。規模が小さければトークン自体が過剰でもある——「よく命名された CSS 変数で足りる」。詳細は [[デザインシステムの過剰設計]]
- **モジュラースケール**: スペーシングをフィボナッチ由来の6パターン（0/4/8/16/24/40px、デジタル庁デザインシステム参照）に限定、フォントサイズは調和数列——法則で選択肢を絞ると、全体の調和と意思決定の速さを両立できる（出典: [[【デザイン】新規サービス開発でデザイントークンを導入してみました！ Design - Qiita]]）。数学的スケールと光学調整の使い分け・関係ベースの余白設計は [[スペーシングシステム]] を参照
- **管理者を任命する**: 提案は誰でも・判断は責任者、というワークフローで命名の一貫性をレビューで守る（出典: [[デザイナーと開発者の連携を効率化するデザイントークンとは何か？  アドビUX道場 UXDojo]]）
- **エンジニアを設計に巻き込む**: 最も悩むのは命名であり、トークンは「命名されるより読まれる・参照される機会の方が多い」。実装観点を初期段階から入れる（出典: [[【デザイン】新規サービス開発でデザイントークンを導入してみました！ Design - Qiita]]）
- アクセシビリティ: カラートークン選定時に WCAG コントラスト基準（通常テキスト 4.5:1、大テキスト 3:1）を検証し、ドキュメントにも記載する（出典: [[デザイナーと開発者の連携を効率化するデザイントークンとは何か？  アドビUX道場 UXDojo]]）
- **採用判断の基準**: マルチプラットフォーム / 複数アプリ・頻繁なデザイン変更・大人数チーム・CI/CD に慣れた環境では効果が高い。小規模で変更速度や一貫性に課題がなければ管理オーバーヘッドが見合わない（出典: [[トークンベースのUIアーキテクチャを設計する]]）

## 標準とツール

- 仕様の標準化: W3C の Design Tokens Community Group がフォーマット仕様を策定中。共通仕様がないとツール間移行（Tokens Studio→Anima 等）でデータ構造の不整合が起きる。詳細は [[DTCG]]（出典: [[デザイントークンに詳しくなれるスクラップ]]）
- 変換・配信: JSON のトークンを各プラットフォーム向け（CSS/SASS/Swift/Kotlin…）に生成するビルドシステムの代表が [[Style Dictionary]]。デザイン側は Figma Variables / Tokens Studio プラグインで定義し、GitHub 連携で各コードベースへ流す。詳細は [[デザイントークンのツールチェーン]]（出典: [[デザイントークンって何？｜seya｜note]], [[Design Tokens An Introduction]]）
- マルチアプリ企業では共有トークン仕様が、テーマ可能なフロントエンド・仕様を認識するコンポーネントライブラリ・Figma→コードの自動化をもたらす（出典: [[Design tokens 101]]）
