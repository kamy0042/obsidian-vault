# カラーシステムの設計

## 概要

デザインシステムにおける色は「基準色（base colors）から生成される tint / shade の体系」として設計する。物理的なデザインと違い、UI は状態・テーマ・文脈の表現に大量の色調を要する——Apple HIG は一見ミニマルだが、実際にはテーマ・モード別に4倍の色調と24種のグレーを持つ（出典: [[デザインシステムのためのカラーパレットの作成：改訂版]]）。多くの色調を持つこと自体は悪ではなく、問題はそれを体系化できるかにある（出典: 同上）。

## 良いパレットの要件

以下すべて出典: [[デザインシステムのためのカラーパレットの作成：改訂版]]（imperavi。旧版 [[How to create a color palette for design systems  Blog]] の改訂）

- **広い色調域**: パレットが仕事を制限してはならない。アラートの淡い背景に合う色がないのは、デザイン案が悪いのではなくパレットの柔軟性不足
- **基準色を持つ**: アルゴリズム生成だけのパレットは「黄のボタンは 400？青は 400 だと薄すぎるから 600？」という迷いを生む。基準色（アクセントやデフォルト状態に最も使う色）が全色相で**常に同じインデックス**にあれば、判断はシステムが肩代わりする
- **アクセシビリティ**: コントラストの階段に加えて「バランス」——特にダークテーマでは、明るすぎるテキストやアクセントが眩しい斑点になり全員にとって読みにくい
- **自動化**: プログラム生成でき、ライト/ダークの**ミラー対称**（ライトの `a5` に対応するダークは `b5`）を持つとテーマ構築が自動化される
- **完全な制御**: 「5年前に退職した1人しか知らない複雑な数式」や不透明なプラグインのアルゴリズムに依存しない。誰でも仕組みを理解して色を足せること

## ベースカラーの選定

以下すべて出典: [[デザインシステムのためのカラーパレットの作成：改訂版]]

- **brand / primary**: 実コンポーネント上で検証し、最初からコントラスト検査を通る色を選ぶ
- **black / white**: 純黒・純白でもよいが、primary を黒に混ぜると全体が調和する
- **Night と Smoke**: ダークテーマの背景は黒より少し明るい「Night」、白テキストは光暈（ハロー）が出るため少しグレーの「Smoke」を使う。Smoke を使うなら背景は純黒でも均衡する
- **状態色は5種**: informative（青系）/ focus（明るめの青。後から tint として導出可）/ negative（「error」では狭すぎる——破壊的操作・下降トレンドも含む）/ positive（同じく「success」より広い）/ notice（「warning」より広い）。hover / pressed は色ではなく shade の違いなので専用色は不要
- **透明スケール**: グレーの要素は色付き背景の上で破綻するが、7% の透明黒はどんな背景でも機能する。black / white / night / smoke の透明スケールを `black-a60` 形式で命名する（Figma で「a+数字」と打つだけで候補が絞れる）
- ほかに secondary / tertiary、プロダクト固有色、グラデーション用、チャート用（暖色・寒色の2スケールを hue を刻んで作る）、イラスト用。最初に全部揃える必要はなく、設計しながら足してよい

## 色調（tint / shade）の生成方法

- プラグイン任せは不透明なアルゴリズムと固定の値数が問題（8値生成のツールで12値欲しければ行き止まり）。コントラスト値基準の生成は手調整が膨大。手作業は毎プロジェクトでは非効率（出典: [[デザインシステムのためのカラーパレットの作成：改訂版]]）
- コントラスト基準の自動化ツールとして **Leonardo**（leonardocolor.io、[[Nate Baldwin]] 作の OSS）がある: 必要なコントラスト比を制約として入力してカラーシステムを生成する。UI 色以外に大量の識別可能な色が要るデータ可視化（Celery・Coral のような拡張色）で特に有効で、WCAG 基準の担保に使われる（出典: [[Garth Braithwaite on Design Tokens, Governance, and Scaling Spectrum at Adobe  Knapsack]]）
- **カラービルダー方式**: 白背景への透明度重ねで tint、暗背景（Night）への透明度重ねで shade を作る事前定義セット。基準色を差し替えるだけで全値が再生成され、値数は自由（著者は17値）、ライト/ダーク対称、基準色は常に同じインデックス。色グループ（ニュートラル / 白前景の色 / 黒前景の明色）ごとに透明度セットを変える。補正: 緑は彩度を上げ、黄・橙のダーク shade は濁るので hue を赤方向へシフト（出典: 同上）
- **トーンベースの生成（M3）**: キーカラーごとに白黒含む13トーン（0〜100）を生成し、UI ロールへマッピングする。トーン値の差でコントラストを保証する設計——**40以上離れれば 3:1、50以上で 4.5:1**——のため、動的な配色変更やテーマ切替でもコントラスト比が保たれる。カスタム色も自動調和され、「設定した色そのものがスキームに含まれない」ことさえある（出典: [[Material Design 3 要点まとめ 7 Color - Color system｜パジェロ｜COMPASS]]）。詳細は [[Material Design]]

## 知覚科学ベースの再設計 — Adobe Spectrum Colors v6.0

以下すべて出典: [[Adobe Spectrumのカラーバリエーションを再発明]]（Spectrum のカラーシステムリードによる、100超プロダクトを支える色の7ヶ月がかりの刷新。2013年以来の大改定）

- 方式は**アダプティブカラーパレット**: 静的なスウォッチではなく「色生成を導く制約」を定義する
- **WCAG コントラスト比 ≠ 知覚コントラスト**: 旧グレーは WCAG 最低値を満たしていたが、テキストが disabled 状態に見えた。新システムはテキスト/アイコンは高コントラスト・背景は低コントラストへ最適化
- ダークテーマはライトの反転では作れない: 同時明度対比の影響で一様なコントラスト増加は破綻（最明部が白に張り付く）。解は **target contrast ratio を「各テーマで利用可能なコントラストのパーセンテージ」として計算**し、単一の完全適応型テーマから light / dark / darkest を生成すること
- 色相は HSL の等分割をやめ、知覚均等色空間 **CIECAM02-UCS** で全色を再評価。lightness scale（黒→キーカラー→白の補間）の「カーブの滑らかさ」で判断し、[[Nate Baldwin]] の **Leonardo** を同時進化させながら hue / 彩度を精密に調整
- **Bezold–Brücke シフト**（光が強いほど色相が暖色へ寄る物理現象）を適用すると、UI 要素が「色のついた物理オブジェクト」として自然で調和した見えになった
- **Stevens のべき法則**: 数値的に均等な明度分布は知覚的に均等に見えない。ColorBrewer RdBu に似たカスタム多項式カーブで明度を配分し、コンポーネントの状態遷移（hover で+1、pressed でさらに+1 のコントラスト単位——[[Color Tokens - Goldman Sachs Design]] の式と同型の発想）が色相を問わず一定の視覚的変化になるようにした
- 柔軟性とガードレール: 各色**14段階**を提供しつつ、「**700 番台は gray-100 に対し 3:1 以上、900 番台は 4.5:1 以上**」をコードで保証——インデックスがそのままアクセシビリティの約束になる
- レイヤリングは base / layer 1 / layer 2 の積層順命名（ユーザーに近いほど明るい）でテーマ非依存に。彩度は時代に合わせて向上（低彩度＝信頼というエンタープライズの古い記号は消えた。高彩度は色覚多様性における判別性も上げる）

## マルチブランド／ホワイトラベルのカラーシステム — Gaudiy Fanlink

以下すべて出典: [[IPの世界観に寄り添う、マルチブランドなカラーシステム設計論｜TORAJIRO]]（冒頭の免責:「このプロセスは多くの人にはやりすぎ。既存のカラーシステムやジェネレイターが最短最適」）

- 要件: ホワイトレーベルのプロダクトが「**IP の世界観に寄り添う**」ためにコミュニティ単位でプライマリカラーを切替え、**どのブランドカラーでも同じように知覚されるコントラスト**（Red500 と Blue500 が同等）を提供する。「ダークモードは色を反転するだけ」という期待は工数の過小評価で、実際は初期デリバリーに3ヶ月かかった
- **コントラスト厳格度は事業で決める**: 「公共性の高いサービスほど厳格に準拠すべき。toC では主観的・視覚的魅力を優先可能」——Gaudiy はグローバル展開と金融事業の計画から WCAG 2.1 準拠を意思決定した
- 直線的な明度スケールの3つの問題（コントラストを担保できない／State 変化の差分が激しすぎる／スケール間で見た目が異なる＝テーマを変えると別物に見える）に対し、ベースポイント（4.5:1）とエンドポイントを先に決め、**山なりの明度増減**（ベース付近ほど変化幅が大きい）で設計。Semantic 分類は Ameba Spindle の概念整理（Background / Surface / Text / Object / Border / Interactive / Third Party）をほぼ転用し Overlay を追加
- **State/ 分類の教訓**: 状態変化をコンポーネント側・開発者個人に委ねると実装箇所ごとに規則がズレる → hover / pressed 等を variables として定義しズレを構造的に防ぐ（Figma 上では `State/` で隠す）
- **Dark Yellow Problem**: 黄色を白文字でコントラスト担保すると濁って「もはや黄色ではなくなる」。一貫性重視のシステム（IBM）は Bright Color を除外し、色相数重視（Material）は非担保を許容するが、IP 要件では除外できない → Radix UI 方式で **Bright Color の中間ステップは前景を黒文字にする別ルール**を採用（`--text-on-accent` が `_bright` で分岐）
- **HSL の欠陥と知覚均等色空間**: HSL の数学的明度は知覚と一致しない（同じ明度値でも黄は青より明るく見える。Stripe の指摘）→ CIELAB/LCH ベースの **Huetone** で「知覚可能・再現可能か」「コントラストを満たすか」をリアルタイム可視化しながら設計（Spectrum v6.0 の CAM02 採用と同じ問題意識）
- **WCAG 2.1 の計算式自体の課題**: 計算は線形だが、人間は明るい色のコントラストを暗い色より高く認識する——「Good 判定より Bad 判定の方が読みやすく見える」逆転が起きる。WCAG 3.0 ドラフトの **APCA**（Advanced Perceptual Contrast Algorithm）では判定が入れ替わる。Huetone は WCAG / APCA 両対応
- 手作業 v1.0 への内省: 「チームメンバーが僕と同じく理解し運用するのはあまりにも困難」——**再現性のあるロジック**（ツールで視覚化された制約）に載せ替えることが持続の条件

## セマンティック層の実例 — Goldman Sachs

以下すべて出典: [[Color Tokens - Goldman Sachs Design]]

- カラートークンは意味的な名前を持ち、**1トークンに default と dark mode の2値**が割り当てられる（値の出所は共通のカラーランプ）
- 語彙の設計: surface 7種（コンテナ背景は必ず surface トークン）/ border / text（アイコンと共有）/ status 6種 × **bold / subtle / minimal の3段階の emphasis** / dataviz（色覚多様性でも判別できる色数を確保）。`warning-alt` のように「AA 準拠の前景が要る場合の代替色」も用意する
- elevation は8段階で、ダークモードでは影の代わりに**透明オーバーレイでサーフェスを明るくして**高さを表現する
- **インタラクション状態は式で導出**: hover = ランプ上で2段暗い色を 20% オーバーレイ、active = 同色を 40%。ダークモードでは方向が反転して2段明るい色を使う——状態色を個別に列挙せず、公式にすることでランプ全体へ一貫適用できる
- bold / subtle / minimal それぞれに default / dark の値規則がある（bold は 60/50、subtle は 20/80 など。黄だけは AA のため例外的にテキストを gray 110 にする）

## 意味層によるパレットの痩身

- 195個に膨張したカラートークンを **Target（何に塗るか）/ Role（何の意味か）/ State（どの状態か）** の3軸分類で25個へ削減した再建例。hover / pressed を **state layer**（オーバーレイ）として独立させ、状態ごとの色の列挙をやめる——Goldman Sachs の「状態は式で導出」（上述）と同じ発想（出典: [[The Aspirational Bloat Trap Why Your Design System is Failing]]）
- 利用者には色値ではなく役割で選ばせる: Yandex Maps は「Gray 50 を探す」体験をやめ、セマンティックロールから選ばせる形に整理した（don't make me think）（出典: [[Design Systems in Product Development]]）。意味層の設計原理は [[セマンティックトークン]] を参照
