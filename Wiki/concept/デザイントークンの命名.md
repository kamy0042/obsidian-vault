# デザイントークンの命名

## 概要

トークン名は「チームが共有する視覚スタイルの理解」を設計・コード・職種間ハンドオフを通じて維持する装置であり、ツールで探索・検索・認識・想起できなければならない。命名はチームの形成的な（しばしば熱を帯びる）活動である（出典: [[Naming Tokens in Design Systems]]）。名前がトークンの最重要部分という点は [[デザイントークン]] の解剖学も参照。

## Nathan Curtis のレベル体系 — 4グループ

以下すべて出典: [[Naming Tokens in Design Systems]]（[[Nathan Curtis]]。Discovery Education / Morningstar / REI / NetApp 等10超のシステムでの設計経験に基づく）

- **Base**: category（`color`）+ concept（`action`）+ property（`size`）——名前の背骨
- **Modifier**: variant（`primary`）/ state（`hover`）/ scale（`100`）/ mode（`on-dark`）
- **Object**: component（`button`）/ 内部 element（`left-icon`）/ component group（`forms`）
- **Namespace**: system（`esds` `slds`）/ theme（サブブランド）/ domain（事業部）

category / property の組（`$color-background`）だけでは一般的すぎて目的を語れず、concept（`feedback` `action` `visualization` `commerce`）と modifier を足して初めて「目的を持った決定」の記録になる。

- **category の代表例と同義語**: color、font（aka type/typography/text）、space（units/dimension）、size、elevation（z-index/layer）、breakpoints（media-query）、shadow（depth）、time（animation/duration）。チームは優先語＋同義語からなる**統制語彙**（controlled vocabulary）を育てる
- **scale の型**: 列挙（heading の 1〜5）/ 順序値（Material の 50〜900）/ 有界値（HSL lightness の `slate-42`）/ 比例（`1-x` `2-x` `half-x`）/ Tシャツサイズ（s/m/l…）。**size ≠ space** なので space には Tシャツより比例を推奨（Curtis が4年前の自説を撤回した点）
- **mode**: `on-light` / `on-dark`（+ `on-brand`）。**theme と mode は直交する**（Marriott の各ホテルブランドにもそれぞれライト/ダークが必要）

## 命名の原則

いずれも出典: [[Naming Tokens in Design Systems]]

- **同音異義語を避ける**: `type` はタイポグラフィの略とも「型」とも読め、`text` はコンテンツとも property とも読める。だから結局 `font` が選ばれがち
- **クラス内は同質、クラス間は異質**: `sale` や `clearance` をチャート用の `visualization` に押し込まず、意味が違うなら `commerce` として分ける
- **柔軟性 vs 特定性**: `$color-success` は多場面に使える分、text / background / border のどれに使うかを利用者の解釈に委ねる。精度が要るなら property を含めて `$color-background-success` にする
- **完全性を求めない**: 全レベルを含むトークンは存在しない。目的を記述・区別するのに必要なレベルだけ含める（`-default-on-light` / `-default-on-dark` の冗長な並列列挙は悪例）
- **順序に支配的標準はない**: Namespace が先頭、Base が中央の背骨、Modifier が末尾、mode は最後——というパターンは比較的安定している
- **ポリヒエラルキー**: 同じ「エラーの赤」が concept 系（`color-feedback-error`）と object 系（`ui-controls-color-text-error`）の両方の集合を完成させることがある。両方を残し、片方を他方への**エイリアス**にする——後で片方だけ値を変える変更にも耐える
- **ブランド名・色実体を意味層に焼き込まない**: `brand-blue-primary` 型の命名はリブランド／第2ブランド追加で破綻する——実例では find&replace に数ヶ月を費やし数百件のバグを生んだ。意味層の名前は色実体・ブランド固有名から独立させる（出典: [[Advanced UI Design Systems for Scalable Product Teams Working Across Multiple Brands]]）

## ローカルで生み、グローバルへ昇格させる

出典: [[Naming Tokens in Design Systems]]

- コンポーネント固有の決定（input の枠線色）は**グローバルトークンから始めない**。そのコンポーネントの仕様書や `input.scss` のヘッダなどローカルに記録する
- 3コンポーネント以上で共有されたら component group トークン（`$esds-forms-color-border`）としてグローバルへ昇格させ、ローカルトークンを置換・削除する
- **早すぎるグローバル化を避ける**: tooltip の影を popover が再利用「するかもしれない」段階で `notched-layers` などと命名すると、主観的な論争と名前空間の汚染を招く

## 実体の同定 → スケール → 文脈の段階的エイリアス

以下すべて出典: [[Component and token naming in Design Systems  by Nate Baldwin  Medium]]（[[Nate Baldwin]]）

- `primary: rgb(130,80,170)` のような「ゆるい意味論だけ」の命名は悪いアドバイス——何色かも、どういう設計意図かも答えられない
- 手順: (1) 色の実体名（`purple` `fuchsia`）→ (2) 明度の数値スケール（`purple100`〜`purple300`。具体値に縛られず増減だけ伝える）→ (3) 広い文脈のエイリアス（`primaryBackgroundColor: $purple200`）→ (4) 特定文脈のエイリアス（`primaryButtonBackgroundColor: primaryBackgroundColor`）。**広い文脈から狭い文脈へ**
- エイリアスは「意味論は時間とともに変わる」ことへの備え（future-aware）——どの文脈レベルでも太い筆致でシステムを変更できる
- コンポーネント命名: 表記規約（camelCase / ハイフン等）の全社統一は不要。各ライブラリが自分の規約を一貫させればよく、問題は同じコンポーネントに**別の名前**（Quick Actions vs Action Buttons）が付くこと。旧ライブラリとの衝突回避には接頭辞（`myDSButton`）が合理的
- 名前より重要なのが **Design API**: オプション名・型（boolean / 列挙）・組合せ可否・排他関係・デフォルトをプラットフォーム非依存の擬似 API として文書化する（Spectrum の Table of options）。各エンジニアリングチームによる解釈・発明を防ぐ
- 標語は「unity, not uniformity」（画一ではなく調和）

## 国内実例 — B/43 の命名体系

以下すべて出典: [[初公開！「家計簿プリカ B-43」のデザイントークンの設計 - inSmartBank]]（putchom。Curtis の Naming Tokens を参考に構築）

- 構造: **Domain**（`b43`——将来の複数サービスやコーポレートブランドに備える）/ **Category**（`reference` | `system` の2分類。M3 の定義を参考）/ **Type**（color / opacity / dimension / typography…）/ **Property** / **Theme**（`light` | `dark`。モードで変わる Color 型のみ）。例: `b43.system.color.impression.positive.container`
- コンポーネントトークンは不採用——「どのコンポーネントにどのトークンをアサインするかは [[Tokens Studio]] で Figma を見れば判断できる」ため
- **「B/43 において一般的な命名」を事前定義**して揺れを防ぐ: size は extraSmall〜extraLarge（xs / s / m は Don't）、width は hug / full、density は dense / normal / comfort、align は start / center / end
- [[DTCG]] Format Module と [[Style Dictionary]] の利便性の**間をとる**: 現状は SD でパースできる形式に合わせつつ、将来は文字列置換で DTCG 仕様へ寄せられるよう設計
- 効果は共通言語化（「薄い緑 #CFF4ED」ではなく「impression.positive.container」で意図が伝わる）。代償は**キャッチアップコスト**——前提知識がないと逆に伝わらない。シニア中心だから回っているが、オンボーディング用ビデオと隔週の仕様議論会で当事者化を図る

## 命名を運用する — Adobe Spectrum の教訓

出典: [[Garth Braithwaite on Design Tokens, Governance, and Scaling Spectrum at Adobe  Knapsack]]

- 命名とバージョニングは「デザインシステムの2大難問」。Spectrum ではデザイナーがトークンを命名・列挙し、エンジニアがガイドライン準拠を検証し、**コンテンツストラテジスト**が「正しい言葉の定義と議論のファシリテーション」を担う三者体制
- 名前という**文字列に意味情報を全部背負わせる構造は brittle**（typo・一貫性を強制できない）。メタデータを文字列から型検証可能なオブジェクトへ移す「anonymous tokens」構想が進む——[[Design Tokens Aren’t a Contract]] の「組み立て済みトークン名を持たない契約」と同型の発想。詳細は [[Adobe Spectrum]]
- Atlassian は Foundation / Property / Modifier のピリオド区切り（`color.icon.success`）で、「すべてのトークンに modifier が要るわけではない」と明記する簡潔な体系（出典: [[Design tokens - Foundations - Atlassian Design System]]）

## 抽象性と明確さの相反（PJ Onori）

以下すべて出典: [[デザインシステムにおける命名―そしてそれがなぜ最悪なのか]]（元 Pinterest Gestalt の PJ Onori）

- トークンは**設計上抽象的**（モードや文脈で値が入れ替わる）なので、命名の明確さと本質的に相反する。dark/light を positive/negative に置き換えるたび、柔軟性を得て明確さを削る（人は「positive」より「dark」を直感的に掴む）。「現実では椅子は常に椅子だが、デザインシステムでは椅子がソファにもテーブルにもフォルクスワーゲンにもなり得る」
- 相対スケール命名の隘路: small / medium / large は間に値を挟めず「**smedium**」問題と xxxx-small の X 増殖を生む → 数値ストップ（size-100 / red-150）は挿入問題を解くが、さらなる抽象化。「size-100 が何かは誰にも答えられない。ある意味、それが要点」——「トークンが未だに意味を成さないのは、鈍い命名規約による部分が大きい」
- **Gestalt「Matchacado」の後悔**: clever で fun で horrible な命名の代表例（筆者最大の後悔）。「緑を塗るたび Matchacado と打つの？ なぜ green じゃないの？」というエンジニアの問いに答えられなかった。「fun な名前は、名付けた本人が思うほど fun ではない」——統制語彙（Curtis）や実体名から始める段階的エイリアス（Baldwin）と同じ結論に向かう
- コンポーネント命名の経験則（1物1名・頭字語=失敗・音の分離）は [[コンポーネント設計]] を参照

## 機械のための命名 — 名前が振る舞いの仕様になる

- AI エージェントが命名から意図と構造的関係を推論する時代には、`blue-500` や `header-large` のような視覚的・曖昧な名前は「行動のコンテキストを与えず推測を強い、ブランド違反やコードの破損につながる」。`{category}-{role}-{variant}-{state}` の4部構成（例: `color-surface-danger-hover` ——ホバー状態の破壊的インタラクティブ要素にのみ適用、と人間の説明なしに読める）が2026年の標準とされる。「もはや人間向けに名前を付けるのではなく、その名前に基づいて推論を行う機械向けに名前を付ける。**命名そのものが振る舞いの仕様となる**」（出典: [[Design Systems in April 2026 The Infrastructure Is Here. Most Teams Still Aren’t.]]。詳細は [[AI時代のデザインシステム]]）——Curtis の統制語彙・Baldwin の段階的エイリアスが目指した「解釈不要の意味論」に、機械可読という強制力が加わった形
- 対極の簡潔な実務知: 「Web 上のほとんどのものには既に名前がある。**ARIA Patterns をデフォルトにせよ**。完璧な名前を思いついても加点はない。完璧な名前は存在しない」。API はその組織の言語を反映すべきで、Astro は `tertiary` を試したが説明が要るため `borderless` にした（出典: [[Design System Wisdom 2023]]）
