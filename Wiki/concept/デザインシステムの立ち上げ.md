# デザインシステムの立ち上げ

## 概要

ゼロまたは無法状態からデザインシステムを始めるときの実践知。共通する型は「**現状の棚卸し → 本当に要る最小構成 → 使われる場面から段階適用**」で、[[デザインシステムの過剰設計]]の処方箋（幅ではなく深さ・3〜5コンポーネントから）の事例編にあたる。立ち上げの契機はしばしば人の増加——1人の頭の中にあった「自分デザインシステム」が、2人目の参加で共有不能だと露呈する（出典: [[２週間で爆速整備したデザインシステムと運用ルールを公開｜株式会社カウシェ｜note]]）。

## 始めない判断 — 「構築するなフェーズ」

- 副業等で受ける「デザインシステムを作りたい」相談の多くは、実際には**構築するなフェーズ**にある。企業の初期フェーズやビジネスモデルが頻繁に変わる段階では DS がスケールの足かせになり、小規模・短期投入・低更新頻度・少ステークホルダーのプロダクトには「too much」。大半のケースで DS 以前に基礎整備（デザイン決定理由の明確化・レビュープロセスの確立・開発フローの整備）へ投資する方が価値が高い。始める場合も「デザインシステム」という言葉に囚われず、ブランドガイドライン→コンポーネントライブラリと**必要なものを必要なだけ**、ヒアリングと観察で課題を特定しながら作る（出典: [[デザインシステムは「手段」です！ 負のサイクルからの脱却、デザインシステムの今と最優先事項でない理由 ｜デザインを深掘り MdN]] = こぎそ。投資判断の枠組みは [[デザインシステムの投資対効果]]）
- **Button やトークンから始めるのは「ゲームをラスボスから始める」ようなもの**: 射程が広すぎるコンポーネントは早期に扱うべきでない。基盤（foundational）・アトミックなコンポーネントを最初の一歩にせず、3チームのパイロットで射程を意図的に制限して始める（出典: [[“The Sweet Spot for Design System Work,” an article by Dan Mall]]。詳細は [[デザインシステムの投資対効果]]）——m3.com の「使われる場面を徹底的に突き止める」と同じ思想の別表現。ただし対立見解もある: Lean 派は「完璧にするなら基盤（色・タイポ・スペース＝アルファベットの文字）を完璧に」とし、基盤とトークンこそ「利用チームが基盤を継承したまま自力で実験できる」ようにする遅いチームの戦略と位置づける（出典: [[How to create a Lean Design System 🙌🏼  by Freehand by InVision  Inside Design  Medium]]）。[[デザインシステムを育てていく]] も「デザイン原則とトークンは文化に近く、成熟後の導入の方が難しい」と早期整備を推す（詳細は [[デザインシステムの世代交代]]）
- **UI コンポーネントは表層的な解決手段**: コンポーネントは「事業目標 → プロダクトの価値 → 指標 → 意思決定」の積み上げの上に成り立つ。「プロダクトの価値」が明文化されていない状態で一貫性のあるコンポーネントを作っても、「一貫性がある」という良さだけでしか判断できない。PM とビジョン・戦略を明文化し、ストーリーマッピングでユーザーの成功体験を可視化するところから始める。ガイドラインも同様に、デザインドキュメントを書く習慣がない組織でいきなり書き始めるのは困難で、レビュー時に自身のデザインを言語化する基本から。「**一貫性のある UI ライブラリーより、メンバーの『良いプロダクト』への視点に一貫性があったほうが大きな力になる**」（出典: [[UIコンポーネント以外から始めるデザインシステム]] = [[長谷川恭久]]）

- **早すぎる標準化の機会損失**: 初期プロダクトに必要なのは一貫性より柔軟性であり、早すぎる DS は実験を阻害し「システムに仕えるチーム」を生む。「最高のデザインシステムは発明されるのではなく**発見される**」——確立したパターンの共有から始める（出典: [[The Hidden Cost of the Premature Design System]]。システム磨きが逃避になる「進捗の錯覚」は [[デザインシステムの過剰設計]]）
- **開始シグナルは「一般論」ではなく「特定の痛み」4つ**: 複数デザイナーの判断分裂／同一コンポーネントの再実装／リブランドの停滞／オンボーディングの長期化。始める場合も最小構成（トークンファイル1・コンポーネント1・置き場1）から製品開発を通じて育てる——「6週間の孤立構築」は完成時に半分が誤りになる（出典: [[When You Actually Need a Design System]]）

## 契機 — 暗黙のシステムが破綻する瞬間

- **カウシェ**: リリース後1年は複業デザイナー1人が「頭の中の自分デザインシステム」で作業。デザイナーが増えた途端、新メンバーの「これ、デザインシステム作った方が良くないですか？」の一言が発端になり、2週間で最小構成（デザインガイドライン＋デザイントークン＋コンポーネントライブラリ）を整備した（出典: [[２週間で爆速整備したデザインシステムと運用ルールを公開｜株式会社カウシェ｜note]]）
- **一休.com**: 契機は CTO の「デザイナーとエンジニアのコラボレーションが上手くできていない」という指摘。一休と Yahoo!トラベルのシステム統合で「機能は同じだが色が違うだけ」のコンポーネントが量産され、二重修正が発生していた。「感覚でデザインしていた部分を言語化・型化する」ためにデザインシステムを導入し、社内に知見がないため外部講師（池田拓司）を迎えた（出典: [[デザインシステム導入しました - 一休.com Developers Blog]]）
- **バイセル**: エンジニア約8人・デザイナー1人でルール不在。実装カラーコードを全部洗い出すと**31色**（モノクロだけで21色）が見つかり、11色へ削減。棚卸し（インターフェイスインベントリ）が出発点になった（出典: [[デザインシステムを導入してみて(導入編) - バイセル Tech Blog]]）。[[デザイントークン]]の「現状監査から始める」と同じ型

## 「使われるデザインシステム」の3原則（m3.com）

以下すべて出典: [[33万人以上の医師が登録する大規模サービス「m3.com」での、使われるデザインシステムのつくり方｜Cocoda]]（20年・20超サービス・医師33万人をデザイナー約10名で支える環境）

1. **作る側 vs 使う側の構図にしない**: 1人で作る方が速いが、現場の課題を掴めず運用に耐えない。課題洗い出しと価値観のワークショップで巻き込み、「自分ごと」になった参加者はレビューや利用のハードルが下がる。検討自体も担当サービスの違う5名で分担
2. **使われる場面を徹底的に突き止める**: 「今後のいろいろな場面に備えて」増やすと複雑化して誰も使えなくなる。色は用途を議論し尽くして5〜7段階に厳選、影はサービス特性（複雑な操作 UI が少ない）から**1種類に限定**。一方で世界観対応の色展開は「あえて余白を残す」——絞る所と残す所を意図的に分ける
3. **理想を追わず現実的な範囲で運用開始**: 全サービスがモダン環境ではないため Storybook ではなく **HTML/CSS 集＋Docusaurus**（デザイナーだけで運用できる）で開始。キャンペーン LP など切り出しやすい場面で最小要素から適用し、フィードバックで改善。結果、適用プロジェクト数は目標の200%に到達。「デザインシステムはチーム全員で使い、育てることで磨かれる」

## 型のバリエーション — 外注・箱なし・タネ

- **外部パートナー主導（三菱電機 Serendie × Takram）**: 宇宙から家電までの事業領域という高い適応性要求に対し、エンジニア主導のモノづくり文化を踏まえて**抽象（デザイン原則）ではなく UI コンポーネントなど具体性の高い要素から**開始（効果を実感しやすい所から）。3万人超の組織では UI/UX デザイナーの手が全事業に届かないため「**エンジニア主導でも一定のデザイン品質が担保できる**」ことを重視し、コピー＆ペーストで使い始められる画面サンプル（作例）を用意。部門間の距離と関係会社協業の多さから**成果物と設計思想をほぼすべて社外公開**（三菱電機のような企業体では国内ほぼ例なし）。「つくって終わり」を避けるため、プロジェクト初期から運用チームのリーダー（インハウスデザイナー）を置いた（出典: [[Serendie Design System  Takram]]）
- **「箱を作らない」戦略の失敗と再始動（Ubie Vitals）**: 当初はデザインシステムという箱を作らず必要なツール・ドキュメントを都度作成（低コスト狙い）→ 増えた結果「何がどこにあるか分からない」。箱として Vitals を作ったが Notion 管理が組織統廃合で複雑化し、**放置され形だけのドキュメントが残る停滞**に。再始動では (1) ドキュメントサイトを自作して公開（「公開できるものは公開することで運用への意識を高める」）(2) コンポーネントライブラリを**汎用＝OSS / ドメイン込み＝プライベート**に分離 (3) 失敗の反省から「作り込んで要件を満たしてから適用」方針へ（出典: [[Rebooting Ubie Vitals Design Systems]]）
- **「タネ」としてのマスターデータ（カナリークラウド）**: 急成長 SaaS（2年で利用者100万人）に専任デザイナー不在で溜まったデザイン負債に対し、「UI リニューアル」ではなく**負債の把握から**始める。入社1ヶ月・他施策アサイン前にリソースを集中し、**あえて現状の負債を残したままマスターデータ化**（理想のコンポーネントはすぐ実装に落ちず自己満足になる。現状マスターで効率化しつつ、改善箇所を可視化して機を待つ二段構え）。汎用コンポーネントは第一階層・パーツは Parts 階層に分離、Atlassian の Slot ＋ Swap instance で **Detach しなくても成立する設計**に。浸透は Slack での課題認識の共有と、「デザインがつくれるようになる勉強会」という参加したくなるコンセプト設計の Figma 勉強会で。「入社1ヶ月のオンボーディングとしても機能した」（出典: [[デザインシステムは「タネ」から育てる。「カナリークラウド」Figmaマスターデータ設計の裏側｜Cocoda]]）

## 方法論 — 採用ファーストの90日とリーン原則

- **Design System in 90 Days**（SuperFriendly = [[Dan Mall]] のワークブック、52アクティビティ）: 想定読者は「2度目・3度目の挑戦」中のエンタープライズ——初回は使われないライブラリ＝「**デザインシステムの墓場**」に終わりがち。鍵は「**初日から採用（adoption）に執拗にフォーカスし、全ステージに利用者を体系的に巻き込む**」こと。特徴的なアクティビティ: 既存パラダイムの監査と影響マップ／機能チームのロードマップ収集／パイロットチーム特定と3コンポーネントの選定（[[デザインシステムの投資対効果]] のスイートスポット基準と同型）／**デザイナーに HTML・CSS・Git・Storybook を、エンジニアに Figma を教える**／Hot Potato プロセスでの共作／共有語彙の用語集／カバレッジマップ／ステークホルダー定期アップデート。**デザイン原則の抽出は42番目**——先に仕事をし、実際のパターンから原則を抽出する（最初に理念を書かない）。名前・ロゴ・swag・Systems Week を経て90日目に v1.0.0（出典: [[“Design System in 90 Days,” a workbook from SuperFriendly]]）
- **リーン・デザインシステムの4原則**（InVision の Mark Boyes-Smith）: 前提は「先行投資も文化的投資も贅沢品」という現実。パレートの法則で最も効く20%に絞る——(1) **Find the fires**: UX 監査で最も重大な不整合（火事）を職能横断で特定 (2) **Don't reinvent the wheel**: Airbnb・Google・Atlassian・Adobe など公開システムのアーキテクチャを土台に借りる（MICIN・カウシェの公開ガイドライン活用と同型）(3) **Best of basics**: 基盤とトークンを磨けば、利用チームが基盤を継承したまま自力で新しい体験を実験できる——スピードで負ける DS チームの生存戦略 (4) **Win friends not battles**: 門番にならず「水門を開ける勇気」を持ち、コンポーネントを利用チームからクラウドソースする。「**デザインシステムはプロセスよりもパートナーシップによってこそ速く動き、関連性を保てる**」（出典: [[How to create a Lean Design System 🙌🏼  by Freehand by InVision  Inside Design  Medium]]。(4) は Dan Mall の水門を絞るパイロット論と真っ向から張り合う——チーム規模と成熟度が判断の分かれ目）
- **「いまやる事」と「将来やる事」を分ける**（コンセント小山直樹）: 現状のデザインプロセスを「何を良いデザインとするか／どのように実行するか／どのように運用するか」の観点でヒアリングしてギャップを顕在化 → ワークシートで解決策を整理 → 対応「〇」の優先度が高いものだけを「いまやる事」として最小構成で着手する。重要なのは最後に「**将来やる事**」（今の環境・条件では見送ったことに、どんな状態になったら取り組むか）を可視化すること——これがないと「デザインガイドラインを作ったに過ぎない」。仕組み化の構想こそが成熟したデザインシステムへの第一歩（出典: [[デザインシステムがなぜ必要なのか？ 〜共通言語のコミュニケーションで円滑なプロジェクト推進を〜  NIJIBOX BLOG]]）。同イベントの実務Q&A: 既存プロダクトがあるなら色から・ゼロなら原則から始める／メンバー10人超あたりから DS が必要になってくる／バージョンは上書きで良い（古い状態に戻すことはほぼない）
- 計画の網羅性チェックには公開チェックリストも使える: Design System Checklist はデザイン言語10・基盤26・コアコンポーネント166・メンテナンス28項目のオープンソースのチェックリスト（出典: [[Design System Checklist]]）
- **実践6手**（Design Executive Council 調査ベース）: 小さく始める／ビジネスの言語で語る／約10人のチャンピオンネットワーク／コードで定義する／段階的に測定する／AI に向けて文書化する（出典: [[Design Systems Are No Longer Component Libraries. They Are Strategic Business Infrastructure.]]）
- **プロセス・儀式も1コンポーネントのパイロットから段階展開**: 「5人で機能したものは15人で壊れる」——ワークフロー自体をスケールの各段階で作り直す前提を持つ（出典: [[Building Your Design System Workflow — Rituals and Templates]]。Dan Mall のパイロット選定基準と同型の水門思想）

## 立ち上げ期の実務ディテール

- **切り出し基準を先に決める**: コンポーネント化の判断が実装者の裁量だと再実装が起きる。バイセルは「**ページを跨いで同じデザインのものは切り出す**」という一行の基準で意見の割れを解消した。導入の最大の効果は「デザイナーとのコミュニケーションが密になり、チーム全体でデザイン意識が高まった」こと（出典: [[デザインシステムを導入してみて(導入編) - バイセル Tech Blog]]）
- **差分の可視化を第一目的にする**: 一休はガイドラインの目的を「一休とヤフトラの共通部分・差分の可視化」に置き、Variants の Service ステートで両サービスを比較可能にした。マルチブランド統合の第一歩は統一ではなく可視化（出典: [[デザインシステム導入しました - 一休.com Developers Blog]]）
- **Figma 運用の整備も立ち上げの一部**: カウシェはプロダクト別プロジェクト分割・トークン/OS 別のライブラリファイル分割・Master / Develop / Released のバージョン管理ファイルを設計（Develop 内は JIRA チケット単位）。コンポーネントの再構成・再接続だけで1週間溶けた——「二度とやりたくないが、あらゆるプロダクトが定期的にやっている」。命名は1階層限定（`/` 階層記法の管理コストを Sketch 時代の教訓で回避）、State 語彙は MDG を参考に統一（出典: [[２週間で爆速整備したデザインシステムと運用ルールを公開｜株式会社カウシェ｜note]]）
- **公式ガイドラインも書き写す**: HIG はデザイナー間で解釈齟齬が起きやすいため、カウシェは「ガイドラインに書いてあることも含めて」ボタンの Emphasis・配置・破壊的アクションのルールを自前資料化した（出典: 同上）
- **監査は技術作業ではなく外交**: 稼働中プロダクトの監査では本番に17種のグレーが見つかる——「誰の仕事が間違いか」ではなく「一緒に単純化しよう」の枠づけが要る。また新旧 UI が並存するハイブリッド期は事例記事の想定より遥かに長い（出典: [[Building a Design System for a Live Product The Challenges Nobody Talks About]]。buy-in の継続コストは [[デザインシステムの投資対効果]]）
- **v1 は網羅的ではなく「credible」であれ**: 実際のペインを解き・初日からトークンを敷き・信頼を裏切らない最小のシステム。逆張りだが効果が大きいのは**デザインより先にエンジニアリングの buy-in を取る**こと——「最小抵抗経路でないシステムはシステムではなく提案にすぎない」（出典: [[Building a Design System That Survives Contact with Reality]]。オーナーシップ・バージョニング・採用インセンティブの運用3要因は [[デザインシステムのガバナンス]]）
- **新規事業部での下地作り**: MICIN DTx は担当外プロダクトの開発 MTG に入って協業の課題を探り、事業部週次の知見共有枠でアクセシビリティ・デザインシステムの重要性を発信して理解度を高めてから、デザイナー3名の指針（アクセシビリティ・ライティング・イラスト）を策定。Ameba のアクセシビリティガイドラインや SmartHR のライティングスタイルなど**公開ガイドラインを土台に**医療独自の観点を足した。「まだ体系だったものではないが、デザインシステムとして育てたい」——最初からデザインシステムを名乗らない始め方（出典: [[DTx事業部のデザイン基盤整備のこれまでとこれから｜kay｜note]]）

## 2年がかりの立ち上げ工程 — ANDPAD Tsukuri

以下すべて出典: [[デザインシステム「Tsukuri」の立ち上げから現在まで〜取り組みとその成果〜 - ANDPAD Tech Blog]]（sizucca）

- 背景の3課題: 言語化されたルールの不足（既存 UI からルールを読み解く必要があり些細な改修に時間がかかる）／プロダクトごとの独自ルール・コンポーネント乱立（基準とすべき根拠が曖昧）／プロダクト増加スピード（コストが雪だるま式に増える）
- 工程: (1) **基盤づくり**——メンバー間の認識すり合わせ・最小必須要件の言語化・「ANDPADらしい認知パターン」のトークン再定義。「分かりやすいアウトプットが見えにくく停滞に映ることもあったが、重要なプロセス」 (2) アウトプットづくり——「最初から完璧なものは難しく、**リリース後の修正を前提に進めるべき**」へ考え方を切り替えた（初期の手戻りは経験として割り切る） (3) システム化——**開発部から専任エンジニアがアサインされて一気に進展**し、Storybook 移行で試用とフィードバックが増えた (4) **デザイナーによる民主化**——「デザイナーが GitHub で Storybook を更新するのは心理的ハードルが高い」という懸念を、勉強会とハンズオンのサポートで克服し全デザイナーが更新可能に (5) **全社総会で目的を再共有**——「守るべき法律」「絶対的なルール」という誤解が増えたため
- 成果: 生産性・品質向上に加え、**デザイナーのスキル向上**（横断的な情報設計とパターン抽象化の過程でドメイン理解が深まる）、**デザインシステム自体が社内アワードの評価対象に**（「横断的な開発」「効果の複利」が認められた）。「成果の出ない時期や停滞時に環境がサポートしてくれたことが、活用に至った要因」
- 導入初期の迷走（1年半の停滞→CSS共通化への目標縮小）は [[デザインシステムの過剰設計]] の ANDPAD 事例を参照——本記事はその後の成功譚にあたる

## 専任チームなしで作る — Foursquare の証言

以下すべて出典: [[翻訳記事：デザインシステムチームなしでデザインシステムを構築する｜Nobuya Sato]]（Foursquare「Cupcake」、Andrea Nguyen）

- 失敗モデル: デザイナー6人全員でボタンを監査し、全員が意見を言い、隔週会議でフィードバックを回した結果、**最も単純なコンポーネントであるボタンのデザインに3週間**。原因は (1) キッチンに料理人が多すぎる (2) フィードバックが隔週会議に限定 (3) 役割分担が不明確
- 改善: ポイントパーソン（設計・文書化・開発連携の責任者）＋アセット移植担当＋デザインマネージャー承認、という薄いガバナンスを敷いた。ただし**誰もフルタイムではない**。新コンポーネント要求には前提条件（既存で選択肢を使い果たしたか・他チームも恩恵を受けるか・テスト済みか）を課した
- それでも開発はボランティアエンジニア頼みで、ボタンのローンチに8週間超、半分だけ built のまま放置が発生し、リリース計画が立たなかった。プロダクトイニシアチブとして四半期計画に載せて部分的に改善
- 結論: (1) **売り込み（賛同獲得）の努力を過小評価しない**——PM・エンジニア・幹部との会議に膨大な時間がかかる (2) **最終的にリソースは必要**——「デザインシステムは専任の仕事であり、チームメイトにいつまでも時間をボランティアで提供してもらうことはできない」。40コンポーネント必要と判明した時点でこのワークフローは持続不能だった
- 訳者（Nobuya Sato）注: 専任リソースのない状況が国内企業の実情に近い。海外も大手以外は AOR のデジタルエージェンシーと共同構築が主流（Nike は R/GA → AKQA → Instrument）
