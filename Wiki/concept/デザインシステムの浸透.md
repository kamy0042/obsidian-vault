# デザインシステムの浸透

## 概要

「デザインシステムは、設計よりも浸透に時間がかかる」（出典: [[生き続けるデザインシステムの実現に向けたデザイナーの取り組み｜Goodpatch Blog グッドパッチブログ]]）。作った後に使われ続け、利用者が育てる側に回るまでの活動群——自分ごと化の仕掛け・オンボーディング・利用実績づくり・疲弊からの回復——を扱う。採用を強制でなく価値で勝ち取る原則は [[デザインシステムのガバナンス]]・[[デザインシステムと組織構造]] と地続き。

## 自分ごと化の仕掛け — enechain の「民主化」

以下すべて出典: [[デザインシステム浸透の取り組み：目安箱の運用とデザインシステム株主総会 - enechain Tech Blog]], [[デザインシステムの成長。そして、これからどう向き合うか - enechain Tech Blog]]（専任なしの有志チームが OKR「デザインシステムの民主化」を設定）

- **目安箱**（Notion）: 質問・機能リクエスト・提案をいつでも起票できる窓口。起票から一次回答・アサインまでを高速化し、**起票者がエンジニアなら「コントリビューターとして参加しませんか」と誘う**。結果、対応件数は目標の150%超、コアメンバー以外の PR が増え、リソース不足だった実装スピードが上がった
- **デザインシステム株主総会**: ステークホルダー向けの情報発信・意見交換の場。台本つきの総会スタイルは準備コストで持続不能と分かり、**ステークホルダーの元へ直接出向くカジュアルな対話へ方向転換**した
- **名称の全社募集**: コーポレート・ビジネス職からも案を募り、「誰かが作っている」ではなく「みんなで作っている」への転換を狙う
- 効果の兆候: 全社会議（All Hands）で自分たち以外の発信からデザインシステムが紹介され、ロードマップに組み込まれた——「会社としての自分ごと化」の実感
- 採用の計測: `component-rate =`（DS コンポーネント使用数）/（Chakra UI 直接使用を含む同名使用数）を計測し、「使われている」状態の改善活動へ繋げる。Yahoo! JAPAN の Riff も CI から利用側リポジトリへ集計スクリプトを実行して利用数・割合を定量測定する同型の実践を持つ（出典: [[フロントエンドから取り組むデザインシステムの改善 UI - Yahoo! JAPAN Tech Blog]]。詳細は [[コンポーネントカタログ]]）。KARTE Sour は TypeScript Compiler API による import 解析でモジュール×プロダクトの参照数を毎朝自動集計する（OSS 公開。破壊的変更・剪定の実務は [[デザインシステムの世代交代]] を参照。出典: [[ソースコードを解析して社内向けUIライブラリの使用状況を自動で集計する]]）

## 本番を証拠にする

成熟したレガシー製品では、カタログやFigmaだけでなく本番DOM・computed styles・実装参照をデザインシステムの入力として扱う。
本番要素を **DS準拠 / legacy variant / deprecated / unknown** に分類してカバレッジを観測すると、乖離の多い場所と統合価値の高いパターンを優先できる。
抽出・所在特定・比較は自動化できるが、同一パターンか、正当な差異か、廃止対象かの判断は人間に残す（記事自身が探索的構想と明記。出典: [[From UI Archaeology to Design System Infrastructure]]）。

## 利用実績から始める — kintone の「エベレスト」

以下すべて出典: [[デザインに関わる全ての人たちでエベレスト登頂を目指すために取り組んでいること｜amishiratori]]（[[kintone Design System]] チームリーダー）

- 「理想の Button のドキュメント」に2ヶ月かかった経験から、「**最初から完璧なデザインシステムは作れない**」——いきなりエベレスト踏破ではなく高尾山から。小さい山を登るうちに知識・装備・仲間が増える
- **「今」使えるものの提供**: 既存実装の共通コンポーネントを DS 管理下のリポジトリへ切り出して**そのまま**提供する。プロダクトとの差分ゼロなので導入障壁がなく、DS チームは「これから変えたいもの」を管理下に置ける。以後の改善は自動的に利用チームへ届く。ジャストインタイム提供と同時に「全体像を見据える人」を置いて方針ブレ・手戻りを防ぐ
- **Centralized → Federated への移行**（Nathan Curtis の Team Models 参照）がコントリビューター拡大の契機。運営理念（オープンなプロセス・制作物の公開・自由な利用「使い倒してください」・フィードバックの重要性・学びと共有)を最初に目につく場所へ置き、公開後半年でコントリビューター30名超（デザイナー・UX ライター・ローカライズ・FE・QA）
- **ワーキンググループ**（デザイン / アクセシビリティ / UX ライティング）: 有志が起案・議論・執筆し、DS チームがレビューして正式ガイドライン化。利用者が「本当に必要としていたもの」が集まり、DS チームに知見・工数が足りない仕事（類似アイコンの整理）も解決した。憲章で「アウトプット必須（参加していない人も利益を受けられる状態にする）・開催形式自由・参加離脱自由」を明文化
- **利用チームのエンジニアに PR を出してもらう**: 依頼を受けて DS チームが作るのではなく、必要としたチームが実装する。初期は勉強会・ペア作業で手厚くサポートし、慣れたら徐々にレビューだけへ
- 成果: PM がプロダクトロードマップに DS 投資を記載——経営陣・営業も見る文書であり「会社として投資を決めた」に近い。「専門領域は専門家に頼る。デザインシステムチームは**ビジョンと場所を提供する**（ルート調査と先導）」

## 疲れと再出発 — KARTE「Sour」

以下すべて出典: [[デザインシステム疲れからの再出発：持続可能な運用への実践的アプローチ｜ishigakijunichi]]（プレイド KARTE）

- 構築の高揚感から2年で「**デザインシステム疲れ**」により活動量が低下。理由: (1) React 前提で作ったが現実は Vue 主流で使える画面が少ない (2) 利用が始まると破壊的変更が難しく改善が進まない (3) デタッチ・亜種コンポーネントの発生 (4) **同じコンポーネントを使っているのに見た目も操作性も統一されない**——「これまでの努力は何だったのか」。さらに専任デザインエンジニアがアサインで不在になり、定例消失・モメンタム喪失
- 再出発の工夫（「疲れない」を第一に）: **番長&大臣制**（意思決定者を1人に。デザイン番長・実装番長＋大臣=CDO。[[Nobuya Sato]] が提唱した制度）/ デザイナー全員ヒアリングで課題をマインド・プロセス・成果物の3層に整理 / 大臣（CDO）から「**まずは Sour から始めよう**」を発信——ボトムアップ尊重の文化に対するトップの後押し
- **デザインパターンの充実**: コンポーネント提供だけでは同じ設計思想で画面は作れない。コレクション画面・レポート画面など**機能別の推奨組み合わせ**を定義し検討のスタートポイントに（コンポーネント自体は小さく汎用に保つ）
- **プロデザ定例**（隔週）: 進行中デザインの共有で、DS 観点のタイムリーなフィードバックと「Sour が使いづらい状況」の把握を両立。Notion に箇条書き＋スクショの省エネ運用
- ドキュメントサイトを Studio → GitBook へ移行し**月間 PV が20倍**（AI 検索・執筆協力のしやすさ・変更履歴）。「詳細が詰まっていなくても項目が存在することを良しとし、最初から完璧を目指さない」。AI 活用の深化にもドキュメントが重要
- Figma マスターファイルの「**治安**」: 説明テキストや試作インスタンスを一切残さない。「ゴミが一つでも落ちているとマスターファイルなのか疑い、利用が不安になる」（中途入社デザイナー談）。編集権限を限定しブランチで更新
- 教訓: 「Figma の外に目を向ける。『システム』だけでカバーしようとせず、『ルール』だけで回そうとしない。**作っているのは人**」

## 専任ゼロの持続術 — Gaudiy Design System

以下すべて出典: [[「専任ゼロ」でも育て続ける、Gaudiyのデザインシステム運用｜TORAJIRO]]

- 初期から専任者を置かず、**各自の開発チームミッション達成と事業推進を最優先**に置いた上で、プロダクトデザイナー3名＋FE 1名の横断プロジェクトとして運用。期によっては「最も重視しない」位置付けにしつつも、「プロダクトの品質担保責務」を職能機能として定義して継続する
- **デザインシステムスプリント**: 2週間ごと・目安6時間（週3時間）のタスクコミットで最低限の進捗を確保。横断的な取り組みも工数に反映して負荷を可視化
- **スコアリング**: 影響度 × 利用頻度 × 迷い度で優先度を客観化（SmartHR のイベントで見た評価軸を採用）。Figma の Library Analytics で実際の利用頻度や「detach されまくっているもの」を確認できる
- 起票ハードルを下げる **Slack → Backlog の絵文字連携**、Figma Slack App の Publish 通知、デイリー30分の相談会（ペアデザイン）、コンポーネント追加基準の明文化＋フローチャート
- 緊急度が低く柔軟に進められる DS タスクは**業務委託・副業と相性が良い**——社内で手が回らない専門性の高い課題まで進捗した
- **LLM でガイドライン作成を効率化**: テンプレート＋コンポーネントのスクショ＋参考デザインシステムを渡して「〇〇のガイドラインを記述して」で叩き台を生成し、「レビューして改善案を」で磨く——誰が書いても一定のクオリティラインを担保
- 内省: 「デザインシステムが許容できない＝実現を遅らせてしまう場合がある」「気を抜くと**つまらないデザインを生み出す要因**にもなる。エンタメ性や没入感が重要な toC では playability を忘れてはいけない」。属人化への警句——「担当者が抜けた後にすぐ廃れるのはよくある話。責務の前提共有や評価制度への組み込みを」

## 属人性からの脱却と、そもそも論

- MIXI: 横断組織で複数サービスの導入を支援してきた立場から「**自分がいなければ運用が回らない状態は健全ではない**」。ナレッジシェア・勉強会・育成で組織的に推進できる体制を作る。同時に「デザインシステムに正解はない」——整備より機能改善やプロトタイピングを優先すべき場面もあり、本質は一人ひとりが「なぜこのデザインであるべきか」を自分の言葉で語れること（出典: [[デザインシステムをチームの共通言語にするために、MIXIで取り組んできた試行錯誤｜Cocoda]]）
- Goodpatch（クライアントワーク）: ゴールは納品ではなく「**クライアントがデザインシステムを改善できる状態**」。設計の文脈を知らずにルールだけ受け取った側は、特例を「まあいいでしょう」と許すか、逆にルールに忠実すぎて検討が遅くなる——どちらも文脈非共有の帰結。巻き込みは (1) ドキュメントで（章立てから擦り合わせ、質問には該当ドキュメントを逐一返す）(2) 相談と議論で（ルールの余白を一緒に改変）(3) ペアデザインで（判断の相互言語化）。**最大の変数は相手側にデザインシステムオーナーになり得る人がいるか**——いなければ別の解決策を検討すべき。統一性は「結果」であり目的は判断スピード。「デザインシステムはインフラのようなもので、**負に気づいた時に初めて必要性を痛感する**」ため、唐突な提案は響かない（出典: [[生き続けるデザインシステムの実現に向けたデザイナーの取り組み｜Goodpatch Blog グッドパッチブログ]]）
- 同記事より: Schema by Figma 2022 の Sho Kuwamoto「ミスの可能性を減らすためではなく、**摩擦を減らして創造性を高める**」——「自由を作る制約」という捉え方。また「デザインシステム」という語は期待がばらつくため、導入意義に合わせた固有名称の方がよいという提案（enechain の名称募集・KARTE Sour とも符合）
- **負のサイクルの根因は「全員が優先して使うだろう」という誤った想定**: 現場にとって DS の適用はプロダクト改善の二の次であり、この現実を無視して定義どおりの UIライブラリ・辞書的ガイドラインを充実させても普及の妨げにしかならない。利用率が徐々に低下し改善サイクルについていけなくなったら、「私たちにとって本当に必要なデザインシステムとは何か」を問い直す。チーム間コミュニケーションに課題があるなら、DS チームが繋げ役としてサポートを充実させる方が利用の契機になる（出典: [[デザインシステムは最優先にはならないです]] = [[長谷川恭久]]。優先度の構造問題は [[デザインシステムの投資対効果]] を参照）
- **「警察になるな」より「フィードバックサイクルの中心に根づかせる」**（Web Designing 鼎談）: DMM 河西紀明は「デザインシステム警察」は発生するし必要でもあるとした上で、重要なのは組織全体が「より良い議論の基盤として DS を運用しよう」という志向性に至ること——そこが運用の第一歩。Figma Japan 谷拓樹は秩序のための自治機能と、制約がクリエイティビティを殺さない「**あそび**」を含めたガバナンス設計の両立を最難関に挙げる。DS をプロダクトと捉えるなら「**ユーザー（プロジェクト関係者）から愛されているか**」の評価が当然必要で、皆が進んで利用する状態こそが定着。三瓶亮は DS を「枠を規定する」ものではなく、最低限の土台でブランドを担保しつつ使い手の「**自由を支える**」プロダクトと定義——誰が無茶なアウトプットをしてもブランドが保たれ、デザイナーでない人から目を見張る成果物が出ることが真骨頂。谷は「DS が中心にあると、エンジニアも遠慮せず同じテーブルでデザインを議論できるようになった」経験を挙げる（出典: [[デザインシステムの構築と運用そしてその本質 - Spectrum Tokyo]]。Kuwamoto の「摩擦を減らして創造性を高める」と同じ系譜）
- 浸透の地道な定番手段: 活用事例（ケーススタディ）の作成による価値訴求・デザイナー以外（エンジニア/PM/セールス）への勉強会・経営層サポートの取り付け（予算・人員に直結）・ニュースレターや社内ポータルでの定期発信（出典: [[価値あるデザインシステムを構築するための7つのポイント｜こぎそ]]）
- **「みんなでデザインをやる」ためのメタ・コミュニケーションデザイン**（SmartHR パネル）: DS 運営は「1人になりがち」で、横断組織はリソースを「かき集めながら」運用しているのが実態。思想や「なんで作っているの？」を明示することが人を巻き込む——「デザインシステムに関わる人を巻き込むためのコミュニケーションデザイン」（putchom）。SmartHR は「デザインシステムという名前が付いていることで『デザイナーのもの』と認識される」壁を自己評価20点と見積もり、「**もっと血肉として使ってもらいたい**」と表現。ステークホルダーがビジネスサイドへ広がったのを機に、技術文書的なサイトから非技術者にも価値が分かるオンボーディング込みのサイトへリニューアルした（出典: [[「デザイナー以外にも、もっと血肉として使ってもらいたい」　SmartHRにおける、デザインシステムの理想と課題]]。詳細は [[SmartHR Design System]]）

## 構築より浸透 — Yahoo DS.DESIGN SYSTEM の3つの心得

以下すべて出典: [[デザインシステムを組織に浸透させる3つの心得 - Yahoo! JAPAN Tech Blog]]（水野直）および同氏の登壇録 [[デザインシステムがなぜ必要なのか？ 〜共通言語のコミュニケーションで円滑なプロジェクト推進を〜  NIJIBOX BLOG]]

- 「**デザインシステムの難しさは、構築することよりも、プロダクトの成長に伴走してシステムを運用し、機能させ続けることにある**」。DS.INSIGHT の DS 大規模改修（認知対策のトップページ刷新・肥大化対策の導入可否ルール・依頼ベース脱却の作成フロー・スタイル不一致対策の Design Token 導入の4本柱で「めちゃくちゃよかった」）を経ての総括
- **心得1 組織のフェーズを理解し、今必要な DS の形を見つける**: タックマンモデルで見ると、外部公開された洗練 DS は第5の「散会期」、自分たちは第2の「混乱期」——立ち上げ/成長フェーズでは完璧さよりスピード感を優先し、DS の役割を4つ（プロトタイピング・一貫した体験・改修スピード・大規模リファクタリング防止）に絞って再定義した。「DS はプロダクトに詰め込まれた努力を**次のフェーズに渡す存在**」であり、フェーズごとの役割定義が建設的議論の立ち返り先になる
- **心得2 プロダクトであり開発プロセスであると訴え続ける**: 改修完了時にプロダクトサイドの PM に「**何も変わってないじゃないか….！**」と言われた——改修完了＝作業終了と誤解させていた。工数の認識齟齬はその後の改善プロジェクトでも何度も発生。コンウェイの法則の通り、DS が機能しないのは組織のコミュニケーション構造の歪みの現れ。以後は「提案の段階で、リソース配分と、改修のメリット・なぜコストを割く必要があるかを丁寧に**繰り返し**訴える」。「デザインシステムは、開発プロセスに組み込み、コミュニケーションを展開して初めて機能する」——DS はプロジェクトではなく「もう1つプロダクトが増える」こと
- **心得3 ステークホルダーの声を聞き、対話する**（=「**対話とは我慢である**」）: 「工数がかかりめんどくさいと思われないかな」と提案が億劫になる一方、理にかなった提案はエンジニアから「この際やっちゃいましょう」と返り拍子抜けした。コミュニケーションを討論・議論・対話・雑談の4つに整理し、対話は「お互いの違いを理解するため」のもの——合わない意見に出会ったら自分を正当化せず一度我慢して異なる意見を知る。「**正しさだけでは人は動かない**」。相手の主張に耳を傾け何を大事にしているかを明らかにした上で信念を持って伝え続けると、相手は答えてくれるし知らない視点のアイデアをもらえる。フルリモートでは対話・雑談の機会が失われがちで、意識的な切り替えが要る
- 締めの証言: 「システムは開発フローに入れ込み、ともに作り上げていかなければ機能しない。**継続した周りの支援なしにはとても成し遂げられない**」

## 前提合わせとサポートの線引き — 長谷川恭久

以下すべて出典: [[デザインシステム浸透に欠かせないサポートについて]]（[[長谷川恭久]]）

- 「**少人数だと自然に合っていた前提は、人が増えることで次第に合わなくなっていく**。前提を合わせるための活動や仕組み作りが浸透には不可欠」。小さな組織では作る人＝使う人なのでガイドラインより UI コンポーネント・実装連携を優先する方が効果的だが、大きな組織では作り方の異なる複数プロダクト・外注・スキルギャップのある入社/異動者が混ざり、前提がまったく揃っていないことがある
- DS の「効率化」メリットは、DS の定義・品質保証の範囲・コンポーネント採用判断基準・**守ってほしいことと現場判断で進められるところの違い**・ツールやガイドラインの参照方法といった知識・スキルが利用者に備わっている前提に基づく。理解が乏しいと、完成度の高い UI ライブラリがあっても的外れなクレームが寄せられ、「信用を失い、わざわざ高いコストをかけて作る意味がないという判断が下される」
- **役割の明確化と線引き**: UI の質は文脈と形状の両方で決まり、UI コンポーネント（形状）だけでは担保できない。「使うことで何が保証されるのか」（例: コントラスト比クリア済みのコンポーネントのみ提供＝チェックの手間が省ける品質保証）を明確にしないと、サポートしきれない問い合わせが増える。「要件定義に関わる部分は関与しない」といった線引きをしないと仕事の範囲が際限なく広がり、本来の目的から遠ざかる
- **窓口は複数用意して敷居を下げる**（それぞれ一長一短）: チャット（敷居が低いが文脈把握に時間がかかり見逃しも起きる）／問い合わせフォーム（必要情報を確実に得られるが敷居が高く問い合わせが減る恐れ）／オフィスアワー（週1時間で可。書くのが苦手な人も会話で課題を明らかにできるが利用者が偏りがち）／勉強会（イベント化で人が集まりやすいが定期開催のコストが高い）。集めたフィードバックを分類して次の施策へ繋げるプロセスまで含めて設計する。[[デザインシステムのガバナンス]] のオフィスアワー・非同期チャンネル運用と同型
- 「**持続がすべて**」: 大きな組織でも最初から専属チームは作れないことがあり、業務の半分以上は DS 外の仕事。役割や範囲を明確にしないと「忙しくしているのに反発の声が出てしまう」。無理にならない線引きと分別で持続させる

## コミュニティとして運営する — チャンピオン・リズム・公開計測

- 「DS は内部プロダクトであり、コミュニティはそのユーザーベース」。システムオーナーの役割は「**gardener, not gatekeeper**」。ハブ&スポーク型でコアが SSoT を保ち、事業部ごとにデザイナー＋エンジニアの**チャンピオン**を指名する——「関係はスケールしないが、チャンピオンを通じてスケールする」。運営リズムは常設チャンネル・週次オフィスアワー・月次ショーケース＋ダイジェスト・四半期レビューの4層で予測可能に保ち、公開の称賛（recognition economy）を最安の関与レバーとして使う（出典: [[Your Design System Isn’t Just a Component Library. It’s a Community.]]。軽量 RFC・不可逆な決定のみのコア留保は [[デザインシステムのガバナンス]]）
- コミュニティ構築は採用の最大ドライバーなのに、業界調査で専任のコミュニティ役職を置くチームは1つのみ——投資の空白地帯。Twilio Paste は利用計測の公開追跡で1年で**7組織11リポジトリ→19組織60リポジトリ**へ拡大した（出典: [[Design System Mistakes That Cost Enterprises Millions in 2026]]）
- ワークフロー不在の人的コスト: 提案が止まり、信頼を失い、コアチームが燃え尽きる。Atlassian の State of Teams 調査ではナレッジワーカーは労働時間の**25%を情報探索に費やす**——ワークフローと文書の整備はこのコストの直接削減になる（出典: [[From Proposal to Release Designing Your Design System Workflow]]。ワークフロー設計の本体は [[デザインシステムのガバナンス]]）
- 計測を補う最良のシグナルは定性対話: 「システムで作ったもの」と「システムを**迂回して**作ったもの」を見せてもらう（出典: [[How Do You Measure Design System Adoption Effectively]]。指標設計は [[デザインシステムの投資対効果]]）
