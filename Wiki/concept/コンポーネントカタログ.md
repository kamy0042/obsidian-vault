# コンポーネントカタログ

## 概要

コンポーネントの実物を一覧・操作・検証できる場（[[Storybook]] 等）と、その先のライブラリ実装・配布の実務論。共通する主張は「**カタログは念のために作る展示棚ではない**」——目的（仕様の確認）を失った Story は腐り（出典: [[Storybookは目的を持って活用しましょう ~コンポーネントの「仕様」を考える~ - Qiita]]）、カタログ止まりの実装はデザインシステムの抽象を運べない（出典: [[React でデザインシステムを正しく実装する - コンポーネントカタログを超えて  Wantedly Engineer Blog]]）。設計論そのものは [[コンポーネント設計]] を参照。

## Story は「仕様の確認」のために作る

以下すべて出典: [[Storybookは目的を持って活用しましょう ~コンポーネントの「仕様」を考える~ - Qiita]]

- Storybook が腐るプロジェクトの共通点は「存在意義が見出せなかった」（テストとの二重管理が過剰・デザイナー協業が薄くカタログの意義がない・低頻度コンポーネントの Story は見返されない）。見た目は仕様の一部にすぎず、**見た目確認しかできない Story は価値が薄い**
- **仕様を言語化してから Story を作る**: 「任意の children をラップできる」仕様の Container は、実利用と同じ子を入れた Story ではその仕様を確認できない——実利用と違う子を入れて初めて「何でもラップできる」ことが示せる
- **動作を持たないことの確認にも価値がある**: TodoItem をクリックしても完了フラグが変わらない Story は「このコンポーネントは状態を操作しない」という責務の証明。List / Item 両方の Story が揃うと責務分担がソースを読まずに分かり、不具合調査の切り分けが速くなる
- 網羅率は「Storybook の存在感」のために重要（網羅が下がると存在を忘れられ「もう捨てよう」への滑り台になる）。hygen 等のジェネレーターで雛形を自動生成して100%に寄せるか、全員が目的を共有した上で意味のある取捨選択をするかの二択

## カタログを超える — 同じ抽象を持つフレームワーク（Wantedly）

以下すべて出典: [[React でデザインシステムを正しく実装する - コンポーネントカタログを超えて  Wantedly Engineer Blog]]（izumin5210、2021）

- デザインシステムは「共通の考え方とツール&アセット」＝エンジニアとデザイナの**共通言語**。その実装は単なるコンポーネントカタログではなく、**システムが定義するものと同じレベルの抽象を持つライブラリ・フレームワーク**であるべき——「デザイナと同じロジックでコンポーネントを作れること」。デザイナが指定するパラメタ（Shape / State / BackgroundColor / Elevation…）がそのまま React の Props に表出する
- 構成: Lv.0 Foundation（色・フォント等の Graphic Standards + Layout unit / Shape / Elevation / Reaction / Typographic scale という UI 原則）→ Lv.1 基礎コンポーネント → Lv.2 組合せ → Lv.3 機能コンポーネント
- Foundation の実装は「CSS プロパティの集合」（styled-components の css interpolation）だけでは足りず、**ロジックを含む原則はカスタム Hook** で配る（Reaction は対象物×アクション種別で変化パラメタが違うため `useReaction` に推定ロジックを隠蔽）。hover / focus 等の実装は React Aria を内部利用——「自分で実装するとアクセシビリティ観点などで考慮漏れするのが目に見えている」
- **TouchArea**: コンポーネントが持つべき最低限の余白もコンポーネントの一部として定義し、Apple / Google のインターフェースガイドライン準拠を内包する
- デザイナは「デザインシステムというフレームワークに乗ることで、細かいことを気にせずプロダクトの価値を生み出すことに集中できる」——Rails / Next.js のアナロジー。[[宣言的デザインシステム]] の「コレクションではなくシステム」批判への実装面の回答

## 静的 HTML でも成立するコンポーネント駆動開発（Shiftbrain）

以下すべて出典: [[静的なHTMLのためのコンポーネント駆動開発―その導入を振り返って]]

- コンポーネント駆動開発（CDD）は React 等の専有物ではない: Pug の mixin をコンポーネント定義に使い、自作パッケージ Storypug で Storybook に載せる。SMACSS / BEM が React 以前から CSS でコンポーネント概念を開拓していた系譜の延長（KSS 等の CSS ベーススタイルガイドは共有には十分だが、開発プレイグラウンドとしては難があった）
- JavaScript は「機能コンポーネント」（Atomic Design の organism 相当＝画像ギャラリー・フォーム・モーダルのような複合体）に収め、Stimulus のコントローラーをマップする
- Story はそのままスナップショットテスト（Jest）に流用できる
- Storybook の多面価値: バックエンド開発者には「コンポーネントのディクショナリ」であり「最終実装を検証するベンチマーク」／ステークホルダーには進捗の可視化（「シンプルだと*思われている* UI にどんな努力が要るか」を示す成果物）／Docs アドオン + MDX で本格的なドキュメンテーションツールにもなる（[[デザインシステムのドキュメンテーション]] と接続）

## 利用者環境を制限しない配布（Yahoo! JAPAN「Riff」）

以下すべて出典: [[フロントエンドから取り組むデザインシステムの改善 UI - Yahoo! JAPAN Tech Blog]]（2021）

- 社内横断デザインシステム Riff は狩野モデルの「**当たり前品質**」を担保する位置付けで、スタイルガイド / Design Token / Design Kit（Sketch）/ Riff React の4プロダクト構成
- **CSS-in-JS（treat）がビルド環境を要求した失敗**: 導入側で Next.js のバージョンアップや Provider 挿入が必要になり、CI エラー・デプロイ不能が続発して導入に約2週間。アーキテクチャ変更が難しい他サービスは導入自体を見送った。教訓を受けて**ビルド済み Sass の配布**へ変更——「デザインシステムはサービスのアーキテクチャにできるだけ干渉しない、独立したプロダクトである必要がある」
- アイコンも同じ原則で分離: デザインツールの書き出しに依存すると SVG 属性が環境で揺れるため、Sketch ファイルからスクリプトで**純粋な SVG を自動生成**して提供（Riff-Icon として独立プロダクト化）
- カタログ運用: Storybook + **Playroom**（コードを編集しながら試せる独立デモ環境——導入前の検証にも効く）、reg-suit によるビジュアルリグレッションテストで再利用部品の表示差分を機械検知
- コントラスト比 4.5:1 ルールを全テキスト色×背景色の組合せで機械計算し、OK / NG の一覧表として提供（詳細は [[デザインシステムとアクセシビリティ]]）
- 効果測定: アンケートの定性に加え、**CI から利用側リポジトリに集計スクリプトを実行**してコンポーネント利用数・割合を定量化——「新規に開発・運用せずに済んだ分」で業務効率化を示す（enechain の component-rate と同型。[[デザインシステムの浸透]] 参照）

## デザインツールとの接続 — Figma Code Connect

以下すべて出典: [[設計システムに適したコード  Figma ブログ]]（Code Connect ベータ発表、2024）

- Dev Mode に表示されるコードスニペットを、自動生成 CSS から**デザインシステムの実際のコード**に差し替える仕組み。開発者はモックをクリックするだけで、DS チームが公認・保守するコードサンプルと使い方を得る
- 動機は採用問題: 「作ったのに十分使われない」「使われても意図に沿わない誤用」。コード自動生成ではなく既存の承認済みコードの表示・配布であり、「**デザインシステムを最小抵抗の道にする**」ことで重複コンポーネントの発生と保守を減らす
- 図面と実装の対応が取れると、使用状況の自動監査・利用分析・コンポーネント更新の承認フローなどが将来可能になる（[[AI時代のデザインシステム]] の契約強制論と接続）

## 分散する真実の源

- 「**Figma は唯一の真実の源ではない**」——現実のコンポーネントの契約は Figma・コード・Storybook・テスト・ドキュメントに分散して存在し、それぞれが異なる利用者に異なる断面を見せる。単一ツールへの集約を前提にするより、断面間の同期をどう保つかを設計する方が現実的（出典: [[Most Design Systems Don’t Break Because of Buttons]]）。Code Connect（前節）はこの同期問題への Figma 側の応答と読める
