# デザインシステムの世代交代

## 概要

デザインシステムは完成しない——「ユーザーに一貫した体験を提供するための情報・仕組みの集まり」は組織とプロダクトの課題・フェーズと共に変わり続けるため（出典: [[デザインシステムを育てていく]]）、数年に一度、ライブラリ全体を刷新する「世代（generation）」の交代期がやってくる。[[Nathan Curtis]] はこれを Defining / Planning / Naming / Adopting / Retiring の5部作で体系化した（このうち Planning のみクリップ済み）。実例には10年ぶりの刷新となった [[Adobe Spectrum]] の Spectrum 2、疲弊からの再出発（KARTE Sour、詳細は [[デザインシステムの浸透]]）、迷走後の仕切り直し（ANDPAD Tsukuri、詳細は [[デザインシステムの立ち上げ]]）がある。エンタープライズの多くは「2度目・3度目の挑戦」からデザインシステムに本気になる——初回の産物は使われないライブラリ＝「デザインシステムの墓場」に終わりがち（出典: [[“Design System in 90 Days,” a workbook from SuperFriendly]]）。

## 世代のライフサイクル（Nathan Curtis）

以下すべて出典: [[Planning a Design System Generation  by Nathan Curtis  Mar, 2024  Medium]]

- ライブラリ全体の変更は数ヶ月〜1年超に及ぶ大事業。**Strategy →（Commit）→ Implementation（Alpha → Beta）→ Launch/GA → Deprecation → End-of-life** のライフサイクルをマイルストーンで橋渡しする
- **Strategy フェーズ**: 要求収集・ステークホルダーインタビュー・既存システムとバックログの監査（Discovering）／ビジュアル言語の進化案や技術スパイクによる PoC（Exploring）／誰が何をいつまでに作るか（Planning）／探索と計画への合意形成（Aligning）。完了の定義は**全ステークホルダーが計画にコミットすること**（"the Commit"）
- **Implementation フェーズ**は2期に分かれる: **Alpha**＝少数の機能（Color・Typography・Icon・Button…)で「どう作るか」を実証する段階、**Beta**＝早期採用者が本番投入できる品質・安定性で十分な数の機能が揃った段階。最短でも Alpha 1回＋Beta 3回、多くは9〜12ヶ月かけて増分デリバリーする
- **依存関係で作業順を決める**: ライブラリは小さいものから大きいものへ作る。`List Group` は `Checkbox` に、`Checkbox` は `Form label` に、`Form label` は `Tooltip` に、`Tooltip` は `Icon` に依存する——**多くの経路が Icon に遡るので Icon を最初のバッチに**。依存ツリー図は複雑化するので完璧を目指さず、スプレッドシートや Jira で管理する
- **担当割りは依存＋属性＋興味で**: 「フォーム担当デザイナー」のように属性の近い機能をまとめ、担当者間の依存コネクタを最小化して相互ブロックを防ぐ
- **品質・数量・安定性は異なる速度で上がる**: 品質は最初から高く保つ（ただし Alpha では完璧主義を抑える——「完璧は進歩の敵」。ベータが「本番投入を信頼できる」変曲点）。数量は S字カーブ（launch 前は テスト・文書化への シフト、大物コンポーネント、フィードバックによる手戻りで減速）。安定性は launch までに鉄壁になればよいが、**名前だけは導入時から安定させる**（プロパティ API・レイアウト・視覚詳細は動かしてよい）
- 進捗報告は **doneness matrix**（列=トップレベルタスク/成果物、行=機能を種別と Alpha/Beta マイルストーンでグルーピング）が最も具体的な単一ビジュアル
- **Launch/GA**: 重いコミュニケーション（メール・Slack・デモ・祝賀・移行トレーニング）と、短く濃い「保証期間」——採用者はトレーニング・問題解決・修正を強く期待するため、チームのキャパを一時的に「次のコンポーネント作り」から「サポートとコンサル」へ振り向ける。launch 期の終わりは実践が「通常運転（BAU）」に戻ったとき。そしてまた次の世代が地平線に現れる

## バージョニングと破壊的変更の作法

- 「**Don't move fast and break things**」——利用者はコンポーネントや API の命名を一貫させたいというあなたの動機に興味はなく、「アップグレードのために自分がやらされる作業」だけを気にする。アップグレードを痛みなくする投資（自動 codemod・ステップバイステップの移行ガイド）をし、「**何かが得られない限り誰もアップグレードしない**」ことを前提に置く。**API 契約を文書化し、何を破壊的変更と見なすかを明示的に定義して、容赦なく遵守する**——カラートークンの値変更は破壊的か？（誰かのコントラストを壊すかもしれない）といったニュアンスを事前に決める（出典: [[Design System Wisdom 2023]]）
- パッケージ境界で安定度を分ける設計が「契約の遵守」を実装レベルで支える: **core**（安定・厳格な semver）/ **product**（プロダクト文脈のラッパー）/ **experimental**（保証なし）にパッケージを分離し、「**デザインシステムの変更は API 変更である**」という規律で扱う（出典: [[Most Design Systems Don’t Break Because of Buttons]]。API 設計の全体は [[コンポーネント設計]] を参照）
- **「破壊・改変」の意思決定は症状と向き合ってから**: 「整理がつかなくなった」「古くなった」「担当者がいなくなった」という理由では表層的な反応にしか聞こえず誰も賛同せず、数年後に同じ問題が再発する。「なぜ整理がつかない状況が生まれたのか」に正直に答える——要因は特定の人ではなく、組織のインセンティブや開発プロセスにあることが多い（出典: [[デザインシステムに関する質問に答えました]] = [[長谷川恭久]]）
- 成熟度の段階論として Sparkbox の Design System Maturity Model（Building Version One → Growing Adoption → Surviving the Teenage Years → Evolving a Healthy Product）がある。Adoption 期のゴールはスケールではなく**成功事例づくり**（出典: [[デザインシステムの目的を考える｜seya｜note]] の紹介）
- **使用状況の自動集計が破壊的変更を可能にする**（KARTE Sour の sour-react）: ライブラリが浸透するほど破壊的変更は難しくなり、対応労力が大きいほどバージョンアップが滞って不具合が放置される——一方「影響を必要以上に懸念して、変更すべきものを変更せず誤魔化し続けるのも不健全」。PLAID は TypeScript Compiler API で全プロダクトのソースコードから named imports を抽出し、**どのプロダクトがどのモジュールを何箇所参照しているか**を GitHub Actions で毎朝自動集計して Markdown 出力する仕組みを構築（`yuheiy/internal-library-reference-stats` として OSS 公開）。活用例は**剪定**——特定プロダクトでしか使われない歴史的な特殊モジュールを、使用ゼロの確信を持って安全に削除できた（出典: [[ソースコードを解析して社内向けUIライブラリの使用状況を自動で集計する]]。採用計測としての同型実践は [[デザインシステムの浸透]]・[[コンポーネントカタログ]] の component-rate / Riff を参照）

## 世代を重ねる・完成させない

- デザインシステムは「作れば全てが解決する」ものではなく**完成することはない**。小さいプロダクトにはコンポーネントライブラリ不要でも、デザイン原則とトークンは早期から用意する価値がある——**原則は文化に近く、成熟してからの導入の方がハードルが高い**（出典: [[デザインシステムを育てていく]]。Dan Mall の「トークン＝ラスボス」論（[[デザインシステムの投資対効果]]）とは張り合う見解）
- 「デザインシステムという箱に何を入れるかは自分たちの課題次第」であり、課題を解くたびに必要になったルール・ガイドラインが集まった結果がデザインシステム（出典: 同上）
- フィードバックが集まる仕組みづくり自体がデザインシステムの役割の一部（出典: 同上。実践は [[デザインシステムの浸透]] の目安箱・プロデザ定例を参照）
- 世代交代の駆動力の実例: Spectrum 2 は「変化を管理することが目的」というマニフェストの体現（[[Adobe Spectrum]]）。KARTE は React 前提の初代が Vue 主流の現実に合わず、疲弊を経て「疲れない」を第一に再出発した（[[デザインシステムの浸透]]）
