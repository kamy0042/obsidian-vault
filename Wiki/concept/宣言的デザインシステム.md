# 宣言的デザインシステム

## 概要

Jeremy Keith が提唱した、デザインシステムへの2つの根本的に異なるアプローチの区別。**命令的（imperative）**アプローチでは「正しい」=「精緻」（精緻なスペーシング・数値・ピクセル）を意味し、**宣言的（declarative）**アプローチでは「正しい」=「弾力的」（柔軟なレンジ・柔軟な出力）を意味する（出典: [[宣言的デザインシステム（翻訳）]]。原文: Jeremy Keith "Declarative design systems"、訳: yuheiy）。

## 主要な論点

以下すべて出典: [[宣言的デザインシステム（翻訳）]]

- **「デザインシステム」という語の多義性**: ある人には「非常に精緻に統制されたコンポーネントのコレクション」、別の人には「コンポーネントを生成するためにあらかじめ用意された境界条件の集合」を意味する
- **コレクション批判**: 多くのデザインシステムはシステムというより*コレクション*。コンポーネントを生成する*システム*ではなく、生成済みコンポーネントの集積になっている
- 宣言的アプローチの核心: 事前にルールと比率を設定し、最終的な実装の詳細はブラウザの実行時に委ねる。例: 「ボタンのホバー状態では背景色の明度を5%下げる」という**ルール**を CSS カスタムプロパティ + `calc()` でエンコードする。出力例は理解を助けるためのもので、必要なボタンが無ければルールの範囲内で生成できる
- **採用問題との関係**: 上層部から降ってくる出来合いコンポーネントは「あなた方が適切な判断を下せるとは思えない」と過度に支配的に映る。宣言的アプローチは「コンポーネント作成に役立つルールとガイドライン」の提供であり支配性が低い。代償は精緻さの欠如と、ルールからコンポーネントを作る考え方・技能の習得コスト
- **ツールとの親和性**: Figma/Sketch などのグラフィックツールは精緻な数値を扱う命令型に合う。CSS はカスタムプロパティ・`calc()`・`clamp()`・`minmax()` によりルールを設定する宣言型に進化してきた
- どちらが正しいというものではなく組織次第: Figma ファイルが Source of Truth の組織には命令的が、HTMLとCSSの観点で考えるデザインエンジニアのチームには宣言的が合う（「デザインエンジニアリングマインドのための自転車」）

## トークン設計との接続

- Astorino の「全バリエーション・状態をトークン構造にエンコードすると『UI を可能にする』のではなく『**UI を記述**』してしまう」という警告（出典: [[The cost of over-abstraction in design tokens.]]）は、Keith のコレクション批判（生成済みコンポーネントの集積）とトークン層で同型。ルールを CSS カスタムプロパティ + `calc()` にエンコードする宣言的アプローチは、意味層を最小に保つトークン設計と親和する。詳細は [[セマンティックトークン]]

## 契約説 — 「ライブラリはスナップショット、契約がシステム」

以下すべて出典: [[Design systems are contracts, not libraries]]（Cristian Morales Achiardi、2026-05）

- コレクション批判の理論的深化: 「文書化されたコンポーネントライブラリがシステムだ」という通念は**正確に逆**で、ドキュメントが記録する「言語化された意思決定」こそがシステム。「システムがよく作られていればライブラリは再生成できる。ライブラリがよく作られていてもシステムがなければ、どのコンポーネントが何の決定をエンコードしていたか誰も知らないため、あらゆる変更が整合性を壊す」。**思考の単位はコンポーネントではなく契約（contract）**
- Donella Meadows のシステム定義（要素・相互接続・目的）に接地する: コンポーネントとトークンは**要素**、コンポーネントの合成・トークンの伝播・決定の適用を統べる契約は**相互接続**。「DSが劣化していると感じるとき、劣化しているのは要素ではなく相互接続」——関係の可読性が失われ、システムがシステムとして振る舞わなくなる
- 「**目的はレトリックからではなく振る舞いから演繹される**」: ドキュメントが『一貫性と再利用』を謳っていても、実際の振る舞いが『各チームがフォークしてライブラリを無視する』なら、そのDSの目的は後者。実際に生産しているものでDSを監査できる
- 契約 = 「この条件が現れたとき、これがシステムの正しい応答であり、これがその理由である」。**レシピの比喩**: 台所（ツール）や小麦粉の銘柄（フレームワーク）を替えても、レシピが同じなら同じ料理ができる。Muldoon の複雑性隠蔽6機構（間接参照・カプセル化・制約・意味エンコード・合成・慣習）はそれぞれ契約の一種（トークン=間接参照契約、コンポーネントAPI=カプセル化、バリアントセット=制約、destructive/affirmative=意味エンコード）
- **導出連鎖**: 言語化された目的 → 標準・定義 → 要求される振る舞い → 契約 → コンポーネント。各層は下の層から導出される。「コンポーネントから上向きに作るとライブラリができ、言語化から下向きに作ると耐久性のあるシステムができる」——チェーンが切れたコンポーネントは恣意的な好みに向かってドリフトする（この最上流が [[デザイン原則]]）
- HCI プリミティブ（入力・フィードバック・＋構造）が底にあり、Atomic Design はそのスケール階層の抽象。ほとんどのコンポーネントは**契約で束ねられた複合物**（リストアイテム＋チェックボックス、検索フィールド=3つの契約）であり、契約を取り去れば「関係の指定がない要素が隣り合っているだけ」になる
- 帰結: **コンポーネントは使い捨て**。フレームワークが変われば書き直し、ビジュアルが変わればリスキンするが、契約は保持される。Simon の「組織は最も希少な資源=人間の注意を節約するために存在する」を引き、DSの本質は「解決済みの問題から注意を再配置すること」（Muldoon の force multiplication）——「コンポーネントは簡単になった。難しかったのは常に推論の方だ」。機械が強制する時代への含意は [[AI時代のデザインシステム]]

## 実装面の回答 — 「同じ抽象を持つフレームワーク」

- Wantedly の React 実装論はコレクション批判への実装面の回答と読める: デザインシステムを「単なるコンポーネントカタログではなく、システムが定義するものと同じレベルの抽象を持つライブラリ・フレームワーク」として実装する。デザイナのパラメタがそのまま Props に表出し、ロジックを含む原則は css interpolation + カスタム Hook で配られる——生成済みコンポーネントの集積ではなく「コンポーネントを作るための原則」を配布する構図（出典: [[React でデザインシステムを正しく実装する - コンポーネントカタログを超えて  Wantedly Engineer Blog]]）。詳細は [[コンポーネントカタログ]]
