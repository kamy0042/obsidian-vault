# セマンティックトークン

## 概要

プリミティブトークンを参照し、使用文脈で命名された抽象層。「プリミティブは選択肢（options）、セマンティックは選択（choices）」という [[Nathan Curtis]] の定式化が広く引かれる（出典: [[When “semantic tokens” are no longer semantic]]）。how / where / when に答えることで広いユースケースカバレッジを持つが、その範囲の広さゆえに「どこまでがセマンティックか」の境界は曖昧で、抽象度の設計がトークン運用の中心的な争点になる。

## ゴルディロックス・ゾーン — 一般的すぎず、特定的すぎず

以下すべて出典: [[When “semantic tokens” are no longer semantic]]（[[Nate Baldwin]]、Intuit での経験）

- **一般的すぎる**: `element-spacing-small` は how/where/when に答えられず、「選択」を定義していない。アイコンとテキストの間隔を狭める意図で値を 8px→4px にすると、同じトークンに依存した無関係な padding まで一斉に変わる——**変更が意図と一致しない**。プリミティブ（`space-100`)を直接変えるのと大差なく、「選択肢のリスト」に退化している。「明確な意図を欠いたセマンティックトークンは、もはやセマンティックではない」
- **特定的すぎる**: `button-padding-top` `textfield-padding-top` …では、「中型コンポーネントの高さを 36px→32px にする」という1つの意図に多数のトークン更新が必要——**変更がスケールしない**。「広いユースケースにスケールしないセマンティックトークンは、もはやセマンティックではない」
- **ちょうどよい**: コンポーネント横断の**共通構造を抽象化**する。多くのコンポーネントは「テキスト＋隣接要素（アイコン等）」を持ち、内部要素と境界の間隔を持つ——この「コンポーネントテンプレート」から `text-to-element-sm` `edge-to-text-horizontal-md` のような集合を導くと、意図が明確なまま広くスケールし、サイズ・密度オプションにも展開できる。実例: Wise、Adobe Spectrum の layout トークン
- **詳細度を意図的に抑えた実例（DMM Turtle）**: タイポグラフィの Alias Token を heading / body / buttonText の3種に留め、Component Specific Token を定義しない。`label` のような名前は「入力欄のラベルか、必須マークの状態表示か」で迷いを生み、詳細度を上げるほどトークンが増えて**多サービス展開では提供側と利用側のギャップが一貫性を壊す**から。MUI 等の汎用 OSS を参考に低詳細度を選び、ベストプラクティスはコンポーネント側に集約、Alias は line-height + font-size をセット提供して微調整を考えさせない。Alias で足りない表現（ヒーローの装飾大型フォント等）には Global Token 直接使用の逃げ道を残す。15段階の Global スケール（0.624〜3.247rem、小数 px はサブピクセルレンダリングで問題なし）と clamp() によるレスポンシブタイポグラフィも特徴（出典: [[デザインシステムにおけるタイポグラフィーの試行錯誤 - DMM inside]]）

## Communication と Construction のセマンティクス

色は警告・成功・強調など**利用者へ意味を伝える**一方、spacing・sizing・radius はUIの**構築方法を伝える**。
同じsemantic tokenという語でも、前者は communication、後者は construction のセマンティクスであり、同じ命名モデルを当てはめると実務者の思考とずれる場合がある（出典: [[Design tokens need more than semantics]]）。

Spectrum はラベル・説明・visual・affordance・group・container・listなど、トークンとコンポーネントの中間に反復する構成を **structural templates** として形式化した。
構造・可変点・合成関係を先に定め、semantic layout tokensを後から導くことで再利用性を上げるが、既存コンポーネントの1〜4px程度の差異を標準化するため再構築が必要になる場合もある（出典: [[Design tokens need more than semantics]]）。

## 反対論 — 「デザイントークンはセマンティックではない」

以下すべて出典: [[The cost of over-abstraction in design tokens.]]（Mattia Astorino）

- 多くのデザインシステムがスケールで失敗するのは、トークン・ツール・文書の不足ではなく「**早すぎ・多すぎ・間違った場所での抽象化**」のせい
- トークンが「どう使われるか」を知った瞬間、それはトークンではなく**システムに埋め込まれた決定**になり、いずれ別の決定と衝突する
- 過剰抽象化は技術問題ではなく**認知問題**: 新規参加者が見るのはアーキテクチャ図ではなく名前。「subtle」に共有された客観的意味はなく、「primary と secondary の境界」は誰かの説明を要する。システムは複雑性を減らさず人の頭の中へ**移設**しただけになり、新規貢献者は減速し、少数だけが理解するシステムになる
- 提唱モデル: **Design Tokens（不変・非セマンティック・プラットフォーム非依存の生の定数）→ Theme Tokens（意味と文脈を持つマッピング層）→ UI**。px / rem / dp などの単位や形式は変換層（[[Style Dictionary]] 等）の責務であり、トークン自体には持ち込まない
- 全バリエーション・状態をトークン構造にエンコードし始めると「UI を可能にする」のではなく「**UI を記述**」してしまい、トークン空間は指数的に増え、変更は高価になる。「トークンがセマンティックなら、それはもはやトークンではない。すでに UI だ」

Baldwin と Astorino は用語法が対立して見えるが、実質は同じ警告を共有している: **意味層は最小限に保ち、構造・状態の全列挙をトークンに焼き込まない**。

## 悪いセマンティクスと規律 — 実務の失敗パターン

- token hell はセマンティック層の欠如からではなく「**悪いセマンティクス**」から始まる——名前が意図を裏切る意味層は、無い方がましですらある（出典: [[Most Design Systems Don’t Break Because of Buttons]]）
- 意味層欠如のコストの定量例: リテラル値で構築されたシステムがダークモード対応に**3ヶ月**を要した失敗談。セマンティックトークン層があれば意味のマッピング差し替えで済んだはずの作業が、全使用箇所の手作業追跡になった（出典: [[The Component Library Trap Why Your Design System is Failing Your Team]]）
- プリミティブ直接使用の典型症状は「`blue300` が5つの異なる意図で使われる」状態——変更時にどの用途が壊れるか誰にも分からない。Manychat は Core→Semantic→Component の3層再構築でこれを解消した（出典: [[How to Build an Agentic Design System People (and Agents) Will Actually Use (Part 1)]]）
- 運用規則は1つに絞れる: 「**コンポーネントは生の値（reference）を絶対に指さない**」。M3 の reference/system/component 3層はこの1ルールの上に成立し、既存システムの移行は lint で境界を封印しながら5段階で進める（出典: [[The Token Structure That Survives Five Products (Google Uses It Too)]]）
- 分類軸の実例: **Target（何に塗るか）/ Role（何の意味か）/ State（どの状態か）** で層を再設計し、hover 等を state layer として独立させることで、195個に膨張したカラートークンを25個へ削減した再建事例（出典: [[The Aspirational Bloat Trap Why Your Design System is Failing]]）
- 「役割で選ばせる」ことは don't make me think の実装でもある: Yandex Maps は「Gray 50 を選ぶ」のではなくセマンティックロールから色を選ばせる形へ整理した（出典: [[Design Systems in Product Development]]）

## マルチブランドと機械のための意味層

- セマンティックトークンは**マルチブランド構成の神経系**: ブランド横断で共有される意味の層があって初めて Brand Skin の差し替えが安全になる（出典: [[Advanced UI Design Systems for Scalable Product Teams Working Across Multiple Brands]]）。3層アーキテクチャは [[デザインシステムの階層化]] を参照
- **人間と機械の共通語彙**: AI がデザインシステムを消費する時代には、セマンティックトークンが人間とエージェント双方への意図の伝達路になり、AI 統合の前提条件とされる（出典: [[Building a Design System That Scales Creating Consistency for Humans and AI]], [[Design Systems as Machine-Readable Product Infrastructure]]）。詳細は [[AI時代のデザインシステム]]

## コンポーネントトークン — 最も特定的な層の損益

以下すべて出典: [[コンポーネントレベルのデザイントークン：価値はあるか？  Nate Baldwin  Medium]]（[[Adobe Spectrum]] での実装経験）

- **便益**: (1) デザインの保証——関心の分離の最終層として、選んだ値が意図通り実装されることを保証（Spectrum 初期に7+フレームワークの一貫実装を支えた） (2) パッチ更新がトークン更新だけで全フレームワークへ伝播 (3) セルフサービス——`button-cta-background-color-hover` は名前だけで「何を・どのコンポーネントの・どの状態に」適用するかを語り、地理分散チームが最小限のコミュニケーションで進めた (4) 自動化——コード生成・ビジュアルリグレッションテスト・lint の基盤（機械可読な全順列データ）
- **代償**: (1) 著述の爆発——全属性×全順列×全状態は指数的にスケールし、Style Dictionary / Theo では扱えず継承・条件式を持つ内製ツールが必要になり、その学習コストが貢献者を減らした (2) 出力の肥大——3バリアント×3サイズ×4状態×12属性で432トークン。**Spectrum はある時点で 210,180 トークン・18MB の JSON に達した** (3) 認知負荷——`spectrum-button-m-warning-quiet-overbackground-textonly-focus-ring-animation-duration` は語の対応が把握不能で、セルフサービス性を自ら殺した (4) **名前が API になる**——Tシャツサイズ導入時に語順規約のため全コンポーネントトークンが破壊的変更（`spectrum-button-primary-textonly-height` → `spectrum-button-m-primary-textonly-height`）となり、全フレームワークが置換作業を強いられた
- **全面採用が見合う5条件**（すべて満たす場合のみ）: 4+のフレームワーク実装 / 中央集権デザインチーム / 単一デザイン言語（1ブランド1スタイル）/ プラットフォーム均一性 / 専任のデザインツーリングチーム。ほとんどのチームは該当せず、**Spectrum 自身ももう該当しない**（各プラットフォームの「良き市民」へ進化中）。通常は「必要に応じた少数のコンポーネント固有トークン」で十分
- 将来像: コンポーネントトークンは静的な key-value ではなく「**正しいトークンへ到達するための指示**（instructions）」として存在すべき——軽量でシステム指向・相互運用可能な新フォーマットが要る
- 関連事例: M3 の Component Token を「参照が深く追いにくく、そこまでの抽象化は不要」として不採用にした判断（詳細は [[Material Design]]）。プリミティブ〜コンポーネントのカバレッジ逆相関の枠組みは [[デザイントークン]] を参照
