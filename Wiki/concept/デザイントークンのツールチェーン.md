# デザイントークンのツールチェーン

## 概要

トークンを「デザインツールで定義 → バージョン管理 → 変換 → 配布 → 文書化」するための道具立てと自動化の論点。ベストプラクティスは **Git リポジトリ（デザインツールではなく）を Single Source of Truth にする**ことで、双方向同期・検証・配布のパイプラインが核心になる（出典: [[トークンベースのUIアーキテクチャを設計する]]）。2022年の DTCG 第2編集者草案と「ツールメーカーへの実装呼びかけ」以降、ツールの状況は急速に進化した（出典: 同上）。

運用実態はベストプラクティスから遠い: Supernova の調査ではトークンガバナンスの **85.8% をデザインチームが保有**（開発チームは 9.9%）、**63% がトークンをバージョン管理しておらず**、**44% が手動同期**に依存する——「ツールの不在ではなくルールブックの不在」が課題（出典: [[Design Systems as Brand Ops Tokens, AI and Stopping Brand Drift]]）。
zeroheight 2026調査でもトークンを「含む」システムは84%ある一方、実運用のパイプラインを持つのは40%、コードからデザインへ同期できるのは11%だった。
**トークンの存在率と運用成熟度は別に測る必要がある**（147人の自己申告調査。出典: [[Design systems were already broken]]）。

## 配信パイプライン

以下すべて出典: [[トークンベースのUIアーキテクチャを設計する]]（martinfowler.com 掲載、Thoughtworks の実践）

- 完全自動（trunk-based）の構成: **Check**（トークンバリデータ / JSON バリデータで検証）→ **Build**（[[Style Dictionary]] 等で各プラットフォーム形式＋ドキュメント生成）→ **Test**（トークンファイル直接の検査＝コントラスト比など、生成コードは Storybook でビジュアルリグレッション / a11y / インタラクションテスト）→ **Publish**（npm 等へ。Conventional Commits + semantic-release でバージョニングとリリースを自動化）→ **Notify**（チャット / メールで新バージョンを通知）
- 成果物はライブラリとしてアーティファクトレジストリへ配布 → 利用チームは**依存更新のタイミングを自分で制御**できる（コンポーネントライブラリ経由の間接更新も）
- この構成で Thoughtworks は小さめのデザイン変更を**1日で複数フロントエンド・複数チームに展開**した
- 手動承認が要る場合はプレビュー環境（トークンをコンポーネントに統合した Storybook）＋ PR ワークフローまたは手動承認ステップ
- 原点の課題例: マイクロフロントエンドで各チームが z-index のマジックナンバーを使い、チーム横断の重なり順が壊れる——トークン化が横断標準になる
- **テーマはエンジニアリング成果物**: テーマ（トークン値のマッピング）を CI でコントラスト検証すべき対象として扱う——「色が合って見える」の目視ではなく、パイプラインが保証する（出典: [[Most Design Systems Don’t Break Because of Buttons]]）

## Figma 側の定義 — Tokens Studio と Variables

- **[[Tokens Studio]]**（旧 Figma Tokens）: トークン定義・JSON エクスポート・**Git との双方向同期**（GitHub / GitLab。trunk / PR 両ワークフロー対応）を提供するプラグイン。Figma 本体機能では全種のトークン定義や値のエクスポートができなかった時代の事実上の標準（出典: [[トークンベースのUIアーキテクチャを設計する]], [[デザイントークンって何？｜seya｜note]], [[Tokens Studio for FigmaとStyle Dictionaryでデザインの共通言語をつくる - 弁護士ドットコム株式会社 Creators’ blog]]）
- **Figma Variables**（Config 2023 発表）: Figma 内蔵のトークン機構（出典: [[【デザイン】新規サービス開発でデザイントークンを導入してみました！ Design - Qiita]]）
- **B-43（スマートバンク）の移行事例**（putchom）: Tokens Studio → Variables へ移行。理由は (1) プラグインはファイルごとに起動が必要で遅い——Variables は内蔵で「Figma を使える人なら誰でも」 (2) 一括変更でフリーズ / クラッシュ、Dimension 適用が不安定 (3) GitHub Personal Access Token の設定や独自トークン型の学習障壁（「プラグイン操作を覚えても将来役立たないかも」という心理的ハードルも）。移行後はデザイナーだけでなく PM・エンジニア含む全職種がトークンを扱えるようになり、動作も軽く安定した（出典: [[B-43のデザイントークンをTokens Studio for FigmaからVariablesに移行しました - inSmartBank]]）
- 同事例の落とし穴: Figma は **GUI での Variables JSON インポートに非対応**（REST API は Enterprise プラン限定）で、公式サンプル改変の独自プラグイン（[[DTCG]] Issue #210 提案フォーマットで light / dark を表現・更新対応・GitHub インポート）を開発する必要があった。Variables は当時 Typography / Gradient 型に未対応（Text Styles / Color Styles を併用）。Tokens Studio のメタデータを剥がすとスタイルごと消え、透明化したコンポーネントに Variables を当て直す高負荷作業が発生した（出典: 同上）

## 実例 — タイミーの DesignDataOps

以下すべて出典: [[タイミーでは先鋭的なDesignDataOpsを構築した｜Yasuhiro Yokota]]（少数精鋭のデザイナー組織）

- デザインデータのガバナンスと完全性の取り組みを **DesignDataOps** と呼び、「自動化・仕組み化できることは徹底的・先鋭的にやりこむ」——レギュレーションは増え続けるので、覚える・チェックする負担を仕組みで消す
- **トークン自動配信**: Figma Variables の JSON → 中間リポジトリ → GitHub Actions + Style Dictionary で Swift / Kotlin / TypeScript を生成し、**各プラットフォームのリポジトリへ PR を自動作成**（社内コード規約準拠の出力は開発者のフィードバックを受けて調整）
- **Variable Mode で OS 切替**: フレームの "os" モード変数（iOS / Android）でタイポグラフィ（ヒラギノ / Noto Sans JP）やネイティブコンポーネントの見た目が一括切替。「iOS だけデザインして Android へ変換」するワークフローで文言差分も防ぐ
- **Figma Normalizer Plugin**（自社製）: ボタン一発でテキスト余白調整・Auto Layout リネーム・旧スタイル/トークンの自動置換・スタイル未適用の赤字化・トークン外の色の紫化・**Notion のユビキタス言語 DB と照合する用語チェック**など11機能。「開発チームの完了の定義に DS 準拠を含めるハードルが下がる」
- **Figma → Notion の毎晩自動同期**: コンポーネント・画面の一覧（プロパティ・依存関係・Figma/GitHub の不存在フラグ）を Notion で俯瞰し、Slack 通知で変更を把握
- 洞察: 「**限界費用をゼロにできるがゆえに初めて運用可能になるレギュレーションがある**」——仕組み化はレギュレーション整備と同時に設計する。「仕組み化は早いほどいい」——少人数ほど、増員前・クレンジングが高くつく前に
- B-43（スマートバンク）の構成も参考になる: Style Dictionary で iOS / Android / Figma / Web(Sass) / Primer Prism の5系統へビルドし、更新頻度が低いため **Figma だけ自動配信**（GitHub Actions で build ブランチへ生成物をデプロイし [[Tokens Studio]] が参照）、iOS / Android はレビューを兼ねて手動同期という現実的な線引き（出典: [[初公開！「家計簿プリカ B-43」のデザイントークンの設計 - inSmartBank]]）

## ドキュメント化 — Storybook との連携

- microCMS: デザイナー組織の誕生を機に UI リニューアル。Figma Tokens → JSON → Style Dictionary → variables.css。Figma Tokens の GitHub 連携で PR が作られ、Netlify の **PR ごとのプレビューリンク**で Storybook 上のトークン反映をレビュー——開発サーバー不要（出典: [[Style DictionaryとStorybookを使ったデザイントークンの連携フロー  microCMSブログ]]）。hygen の対話式 scaffolding でフロントエンド以外のメンバーもコンポーネントを新規作成できるようにした（出典: 同上）
- storybook-design-token プラグイン（`DesignTokenDocBlock`）でカテゴリごとのトークンドキュメントを自動生成。`@tokens` 開始 / 終了コメントブロックを両方宣言するとプレビューが安定する（出典: [[Tokens Studio for FigmaとStyle Dictionaryでデザインの共通言語をつくる - 弁護士ドットコム株式会社 Creators’ blog]]）
- SD の `javascript/module` 形式ならメタ情報付きオブジェクトとして出力され、Storybook 上のトークンカタログを自作できる（出典: [[style-dictionary を使ってフロントエンドで利用しやすいデザイントークンを生成する]]）
- Figma 上のリファレンスも自動化できる: Tokens Studio の documentation tokens ＋ Automator プラグイン（出典: [[Tokens Studio for FigmaとStyle Dictionaryでデザインの共通言語をつくる - 弁護士ドットコム株式会社 Creators’ blog]]）

## 実例 — DMM Turtle の一元管理と Code Connect

以下すべて出典: [[入社10ヶ月で行った Turtle デザインシステムの開発と関連する取り組み - DMM Developers Blog]]（高井実 / debiru）

- 課題: `Blue100` の値が「Figma・React 実装・マニュアル」の**3箇所に重複記述**され、変更漏れ・書き間違いで整合性が失われる
- 解決: マスターデータを**スプレッドシート**に置き、GAS（Google Apps Script）で JSON として Web API 公開（GitHub でバージョン管理）。Simple JSON と JSON for Figma の2形式を出力し、3つの消費先へインポートする
- Figma への取り込みは自作プラグイン **Local Variables Manipulator**（既存プラグインは形式や使い勝手に難があったため。`$codeSyntax` や `$hiddenFromPublishing` を含む形式で Local Variables を入出力）
- React 側は単純インポートだと **JSDoc のコードヒントが失われる**ため、JSDoc・型情報を含めてメタプログラミングで実装コードに変換するライブラリを新設
- **Figma Code Connect** を全コンポーネントに設定（2024年10月）: デザインと実装で無駄に違っていたプロパティ名を統一した上で、「Figma からコピペするだけで実装できる」状態に。制約として Code Connect ファイルは実行されず文字列として解析される（ループや条件分岐で動的に構成できない）
- **リファレンスアプリ**（会員登録フォームのデモサイト）を Turtle 自身で構築するドッグフーディングにより、「実際に使ってみると不便な点が見つかる」を体系化した
- メルカリの事例: グループ全体で技術スタックがチーム判断に委ねられているため、React 限定を脱して **Web Components（Lit）を採用**し「真にスケーラブルな」Design System Web を再構築。React 向けには Wrapper を自動生成し、JSX の型で a11y 必須属性を IDE が教える構成（出典: [[新しいメルカリDesign System Web  メルカリエンジニアリング]]）

## トークンスコープ — public / private

- オプション（プリミティブ）層はデザイナーには有用でも、アプリ開発者には見せない方がよいことが多い。private（internal）/ public（global）の区別は [[DTCG]] 仕様に未収載だが、Salesforce Lightning はトークンごとのフラグを持つ。利点: 使うべきトークンへのガイドになる / 選択肢が少ないほど DX が良い / 出力サイズ減 / **private トークンは破壊的変更なしに変更・削除できる**。欠点: 開発者は「オプション→決定への昇格」をデザイナーに依存する（出典: [[トークンベースのUIアーキテクチャを設計する]]）
- 実装は SD の filter でファイル種別による除外（`*.options.json` を private に）またはトークンごとの `public` フラグ。Figma Variables 側は `hiddenFromPublishing` フラグ（出典: 同上）
- 国内実例: マイベストはプリミティブカラーを registerFilter で実装出力から除外し、実装にはセマンティック名だけを見せている（出典: [[【デザインシステム】デザイントークンをコード変換する Style Dictionary が超便利]]）

## ツール移行への保険と採用判断

- トークンが単一の情報源にあれば「Sass 変数 → CSS カスタムプロパティ」のようなスタイル技術の乗り換え障壁が下がる。Tokens Studio 自身も Figma 非依存のトークンマネージャー開発を表明している（出典: [[Tokens Studio for FigmaとStyle Dictionaryでデザインの共通言語をつくる - 弁護士ドットコム株式会社 Creators’ blog]]）
- 採用判断: マルチプラットフォーム / 複数アプリ・頻繁なデザイン変更・大人数・CI/CD に慣れたチームでは効果が高い（利点: デザイン変更のリードタイム・一貫性・実装は軽量）。小規模で変更速度や一貫性に課題がなければ管理オーバーヘッドが見合わない。デザイナーがある程度 Git に触れる必要と、標準化が途上である点が代償（出典: [[トークンベースのUIアーキテクチャを設計する]]）。過剰導入の力学は [[デザインシステムの過剰設計]] を参照
