# 連合型デザインシステム

## 概要

複数のプロダクトチームに分散したデザイナー・エンジニアがデザインシステムを所有・貢献する体制論。[[Nathan Curtis]] が2015年「Team Models for Scaling a Design System」で定式化した3チームモデル（孤立型 solitary / 中央集権型 central / 連合型 federated）に由来し（原典: [[Team Models for Scaling a Design System  by Nathan Curtis  EightShapes  Medium]]）、コミュニティで「目指すべき姿」として流通したが、**2024年に提唱者自身が「連合型を優先したことは間違いでした」と撤回した**（出典: [[翻訳記事：連合型デザインシステムの誤り｜Nobuya Sato]]、原文クリップ: [[連合型デザインシステムの誤り  ネイサン・カーティス  Medium]]）。Spotify の現場からは2度の失敗の詳細な証言があり（出典: [[翻訳記事 連合型デザインシステムが失敗し続ける理由｜nobsato]]）、両記事の結論は一致する——**連合型は完成されたモデルではなく、中央基盤の上に段階的に追加する進化の一側面**。

## 原典 — 3チームモデルの定式化（2015）

以下すべて出典: [[Team Models for Scaling a Design System  by Nathan Curtis  EightShapes  Medium]]（2015-09。のちに撤回対象となった原記事そのもの）

- 原体験は Sun.com のコンポーネントライブラリ（2006年頃）: 数千のコンポーネントバリエーションを1人の「ユニコーン的**オーバーロード**（絶対君主）」＋FE 開発者1人が作り、月次で予測可能にリリースしていた。「ライブラリの中身が気に入らない？ 我慢しろ。オーバーロードが決める」——しかし「**オーバーロードはスケールしない**」。数百人のデザイナー、コードを書くデザイナー・デザインする開発者の時代には「誰もそこまで遍在・全能・全知ではいられない。共により大きくまとまったものを作るしかない」
- **孤立型（Solitary）**: 1チームが自チームのニーズ最優先でシステムを公開する。Bootstrap は利用側デザイナーから見ればこのモデル。人材・キャパ不足のチームには「他チームの費用で維持される本番品質のコードベース」として価値があるが、「共有してもオーナーが自分の優先順位への**引きずり（drag）**を受け入れる義務は生じない——採用チームのニーズは彼らの使命にとって雑音」。部分的にしか解決されないチームは自作に向かい、発散が始まる
- **中央集権型（Centralized）**: プロダクトを作らない専任グループが決定と部品を作り広める。できること: 幅広いポートフォリオへの伝播・特定プロダクトのバイアスからの自由・機会の発見・検証プロセスの整備。欠くもの: **文脈**（実プロダクトの制約に間接的にしか接地しない解を標準化してしまう）・プロダクトデザイナーの参加や貢献を促す**力**・日々のプロダクト固有課題への**可視性**・プロダクトとシステムのトレードオフ判断への**影響力**。「その立場は不安定（tenuous）で、価値を証明したい欲求が、自律を保ちたいプロダクトチームへの奉仕をかえって損ないかねない」
- **連合型（Federated）**: 「最重要プロダクトの最高のデザイナーたちに、**本業を辞めさせずに**システムを策定させ、皆に広めさせる」。アーキタイプは Google Material の「committee-by-design」。代表性と権限のある一部デザイナーに**一定期間**システムの設計方向を委ねる——「全員参加のオープンシーズンではない」。決定は伝播し、他チームは「成果を活用するか、自らのリスクで無視するか」
- 2015年時点で既に記されていた連合型の困難: 料理人が多すぎる／各デザイナーはプロダクトチームへの忠誠を保持し、コミットが不安定になり「プロダクトチームを離れることへの正直で根深い**罪悪感**」すら示す——「まとまったユーザージャーニーのために**部族的所属を超越**できること」が参加条件／意思決定が廊下・ランチ・Slack に散逸し「誰もその決定へ至った経路を思い出せない」——「個々人がコントロールを手放すことが不可欠」（公開意思決定ログによる対処は [[デザインシステムのガバナンス]]）
- **連合チームの形成論5点**: (1) 重要なプラットフォームを代表させる——ウォールーム合宿の1週間で、Windows アプリの信頼された開発者が実コードで新デザイン言語を自アプリに適用してみせ、ポートフォリオの大半を占める懐疑的な Windows 開発者たちを転向させた（「実画面・実コード・信頼される人」）(2) 職能横断の専門性（UX / Visual / Interaction の見張り役＋Content Strategy = CIVX。内部では境界をあえて曖昧に保つ）(3) doer と director の混成（director は横断的な露出をもたらし、アイコン正規化のような短期集中作業へ遊休人材を提供する）(4) **中央での文書化・伝達への投資**——「リビングスタイルガイドは自らを構築しない」。決定を記録し続ける「**十分に献身的な中央スタッフという構成要素が連合チームには必要**」であり、それがなければスタイルガイドは10ヶ月後には「死んでいる——少なくとも意識不明」(5) **貢献と自治の互酬**——Material 形成期の Jon Wiley の証言: 周縁のデザイナーがミッションに関与するほど、コアチームは逸脱的なアイデアに寛容になった
- 歴史的な読み直し: 2024年の撤回は「孤立型を嘲笑し、連合型へ誤って橋渡しした」構成を自己批判したが、**原典は既に(4)で「連合型には献身的な中央スタッフが要る」と明記していた**。流通の過程で「連合型なら中央不要・無料」という部分（後述の6神話）だけが増幅された、と読める

## Curtis の撤回 — 「連合型の誤謬」（2024）

以下すべて出典: [[翻訳記事：連合型デザインシステムの誤り｜Nobuya Sato]]（原文クリップ: [[連合型デザインシステムの誤り  ネイサン・カーティス  Medium]]）

- 2015年記事は「孤立型を嘲笑し、中央集権型を考慮し、連合型を支持する」構成で、「中央モデルが合わない場合、より複雑な道を追求することになる…」と連合型へ誤って橋渡しした。Salesforce の Jina Anne（2015）から2024年まで18本超の記事がこの枠組みを参照・拡張し、ステークホルダー説得に使われてきた
- **連合型は選択肢（choice）ではなく側面（facet）**: 実際には決して最初に追求されず、中央投資なしには成立しない。ほとんどの場合は任意（optional）で、その結果は高価でフラストレーションを生むため追求に値しないことが多い
- 80超のデザインシステムコンサルティングで、中央にアロケートされた人なしに成功したシステムは「**ゼロ。ゼロ。ゼロパーセント**」（映画 The Big Short の Mark Baum の台詞を借りて）。ほぼすべての生産的成果は中央の人々が提供している
- 「連合のみ」が機能する例外は極めて稀な条件（傑出した個人の才能・権威、または小規模で協働の密なコーディング可能なデザイナー集団）に限られ、「進化する、理想的にはミラーリングされたデザインとコードのライブラリを、スケールする組織が依存する形で提供する」というデザインシステムの定義と整合しない
- **「または」ではなく「そして」**: 中央 vs 連合は誤った二項対立（白黒思考）。成功するシステムは常に中央チームを持ち、常に連合コミュニティからの参加（価値があれば貢献）を求める。空の Figma ライブラリ・空のリポジトリ・空の ZeroHeight を用意して「貢献者に好きにやらせる」のではなく、中央がアーキテクチャ・ツール・プロセス・プレイブック・プラットフォームサポートを整え、コアコンポーネントの作成・維持も100%中央が担う
- **選ぶのではなく、徐々に追加する**: 中央支援の取り組みに tiers や Figma 共有ライブラリ等で連合型の貢献を段階的に加える。コアが安定・完全なら中央投資を減らせる可能性もあるが、「過去10年でその条件が長く続いた例はほとんどない」
- 連合型は任意である証拠に、貢献に注力せず繁栄するシステムも多い。Atlassian はコミュニティ支援の Editor コンポーネント（メジャーバージョン197到達）をコアシステムの外に置き、コアへの貢献は修正のみに制限する——コミュニティが進化させるコンポーネントだからといって「デザインシステムに入る」わけではない

## 6つの神話 — アンカリングの害

ステークホルダーは3モデルの図を見た瞬間に誤った仮説を係留（アンカリングバイアス）し、後からの解体には「No」の連呼という政治的リスクが伴う。神話 vs 事実（出典: [[翻訳記事：連合型デザインシステムの誤り｜Nobuya Sato]]）:

| 神話 | 事実 |
| --- | --- |
| 誰もが貢献でき、すべきで、する | 意味ある新機能・改善を貢献する人はほとんどいない |
| 作られた全コンポーネントがシステムに入る | チームが作るコンポーネントのほとんどは共有ニーズがなく、システムに属さない |
| UI を作る人は誰でも貢献できる | 多くはシステム経験・当該アーキテクチャの知識を欠く。貢献の管理コスト（全参加者の労力+保守+機会費用）が利益（再利用資産+人材育成）を超えるなら悪い判断 |
| どの粒度のコンポーネントも歓迎 | コアは低レベルコンポーネント中心。button ひとつに数十〜数百の視覚属性・状態・挙動の作業が詰まり、そこにビジネス価値がある |
| 連合型貢献が主要な成功指標 | 外部貢献ゼロの中央製コアライブラリも極めて価値がある。年次計画で連合型貢献が主要目標になることはまずない |
| 連合型ならデザインシステムが無料で手に入る | プラットフォーム構築・連合人材のサポート・貢献キュレーションに資本支出+運用コストがかかる。特にデザイナーのシステム作業（共有ニーズの監査・API 考案・高品質 Figma アセットのテスト）は「通常のプロダクトデザイン」と別スキル |

神話の解体説明は冗長にならざるを得ず、上位者への反論という構図が苛立ち・退屈・軽視を招く。先手を打って合理的なケースを構築すべきで、後追いの「No」の繰り返しは避ける（出典: 同上）。

## Spotify の実証 — 2度の失敗（Shaun Bent）

Curtis 誤謬論の「実践編」。Spotify でデザインシステムとアクセシビリティを9年リードした [[Shaun Bent]]（[[デザインシステムと組織構造]] の3:1人員配置分析と同一人物）の証言。以下すべて出典: [[翻訳記事 連合型デザインシステムが失敗し続ける理由｜nobsato]]

- **約束1「分散型オーナーシップ」→ 所有権の空白**: 「誰もが所有しているものは、誰のものでもない」（Milton Friedman）。アーキテクチャ・スケーリングのプロセス・品質・インフラ・未知の課題、それぞれ「誰が責任を持つか」への答えが「誰でも」となり、すぐに「誰もいない」へ変わる
	- 1度目（小規模中央チーム+連合）: 組織が中央チームの目的と価値を理解できず「**無料のリソース**」として常に他プロジェクトへ引き込んだ。責任があっても時間が与えられず、システム運営の基本作業が実行されない。部門内で DS への感情が悪化
	- 2度目（中央チーム完全解散）: 移行計画なし、「チームが何とかするだろう」以外の戦略ゼロ。同じ混乱がより酷く再現された
	- バックエンド重視の組織は UI 開発の複雑性とスケーラブルな DS 運用の労力を単純化・過小評価しがち
- **約束2「チームの貢献」→ 再利用されない重複**: 質の高いコンポーネント作成（多様なユースケース・a11y・ローカライズ・一貫した API・ドキュメント・デザインとコードのパリティ・継続保守）は専門分野であり、「機能開発チームはこの訓練を受けていないし、率直に言って受けるべきでもない」
	- 1度目: 速度優先で重複を許容し「後で中央が統合する」賭けをした → 中央に時間が与えられず統合フェーズは実施されないまま、**1,500超のコンポーネント**に膨張
	- 2度目: ドメイン固有の分担（再生チームが再生ボタンを作る）としたが発見メカニズムがなく、**コンポーネント平均再利用1.2回 vs 中央型コンポーネント200回**。12ヶ月で約1,000個が新規作成（1度目の置き換えではなく全く新規）
	- 所有チームは他チームからの依存関係を拒み、再利用に反対した。機能チームが既存コミットメントと並行して「疑似プラットフォームチーム」化する軋轢は連合型に内在する。プラットフォーム思考（多くのコンテキストで十分に解く）と機能思考（単一コンテキストで完璧に解く）は別のマインドセットで、簡単には切り替えられない
- **約束3「中央チーム不要」→ 実際は高くつく**: この約束の根底は人件費削減で、運用の詳細から距離のある経営層から生じがち。スケール段階では連合型サポートの総労力が中央型を上回り、それを処理能力の低い複数チームに分散させた上で調整オーバーヘッドを支払う
- **デザインとエンジニアリングの分断は解決できず、悪化する**: 1度目はデザインだけ中央型（Figma 共有ライブラリ）で一致するコード実装が不在、2度目はコード実装だけでデザインへのマッピングが不在。パリティ（デザインとコードの等価性）が「絶対に譲れない」という共通認識が必要だが、連合型では各チームが担当範囲に孤立し誰も全体像を持たないため、同じデザインパターンの少しずつ異なる実装が量産される。現行システム Encore ではパリティを絶対条件にしてハンドオフを廃止した（エンジニアが Figma に、デザイナーがコードに携わる）——この文化的シフトは小規模集中チームなら可能だが、数百の自律チームには強制できない
- 失敗はデザインシステムというコンセプト自体の評判を（特にシニアリーダー層で）損ない、以後の投資確保を困難にする

## 機能する条件と実務指針

- Bent が挙げる前提条件: 実際に従われるガバナンスフレームワーク／サイロのない協働文化／発見（ディスカバリー）ツールへの投資／断片化を防ぐプロセス／品質への説明責任体制／専任のプログラムマネジメント、加えて成熟した DS 運用体制・調整コストを許容できる小さな規模・真に重複するニーズ・プラットフォーム作業への専任リソース・分散協調の文化（OSS の伝統が強い組織）。「ほとんどの組織はこうした環境が整っていない」（出典: [[翻訳記事 連合型デザインシステムが失敗し続ける理由｜nobsato]]）
- 核心の問い: 「**連合型を機能させるための投資を、適切な中央集権型チームに費やした方が、より良い結果が得られたのではないか？**」。正道は「堅牢な中央基盤 → 信頼構築・価値の証明 → 後から分散型の貢献パターンへ進化」。「連合型から始めることは、基本的なデザインシステムの問題を解決する前に、最も複雑な組織的課題を解決しようとするようなもの」（出典: 同上）
- 国内の成功例は前提条件込みで読む: [[kintone Design System]] は**専任コアチームを持った上で** Centralized → Federated へ移行し、半年でコントリビューター30名超・最終的に60名近い関与に至った。「ビジョンと場所を提供する」中央の存在が連合型の前提条件と読める事例（出典: [[デザインに関わる全ての人たちでエベレスト登頂を目指すために取り組んでいること｜amishiratori]]）
- 失敗側の追加証言: Cisco では専任エンジニア不在のまま連合型オーナーシップモデルが推進され続け、脱するのに3年を要した（詳細は [[デザインシステムと組織構造]]）
- 訳者 [[Nobuya Sato]] の観察: 日本では「連合型という名のもとに片手間でデザインシステムをやり、結果的に途中で座礁・頓挫するケース」が多く、やるなら中央型を意識すべき——ただし本業のプロダクト開発と内部向け作業の予算配分は難しく、一概には言えない（出典: [[翻訳記事：連合型デザインシステムの誤り｜Nobuya Sato]]）

## 用語

- 「連合型」の訳語は『デザインシステムの育て方』（🌴本）に合わせたもの。同書 P.131 に Curtis の連合モデル解説を含む「ガバナンスと貢献」章がある。訳者の Sato 個人は Central（中央集権）に対する Decentral（分散）の含意で「連邦モデル」の呼び方を好むとも（出典: [[翻訳記事：連合型デザインシステムの誤り｜Nobuya Sato]]）
- Bent 記事の訳では「中央集権型 vs 分散型（連合型）」の対で扱われる（出典: [[翻訳記事 連合型デザインシステムが失敗し続ける理由｜nobsato]]）
