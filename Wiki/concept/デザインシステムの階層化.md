# デザインシステムの階層化

## 概要

「唯一の・中央の・完璧な信頼できる情報源」という単一像を疑い、**最高品質のコアの下に柔軟な階層（tier）を設ける**アーキテクチャ論。構造の階層化（コア／共有／ローカル・ドメイン特化）と速度の階層化（ペースレイヤー: 遅いインフラと速いプロダクト）の2つの見方があり、どちらも「全部をコアに入れない・全部を同じ速度で動かさない」ことで実験と安定を両立させる。提唱の起点は [[Nathan Curtis]] の Design System Tiers（2019）（出典: [[Design System Tiers. Time To Mature Systems To Support…  by Nathan Curtis  EightShapes  Medium]]）。[[連合型デザインシステム]]（誰が作るか）と対をなす「何をどこに置くか」の議論。

## Design System Tiers — コアの下に階層を（Nathan Curtis）

以下すべて出典: [[Design System Tiers. Time To Mature Systems To Support…  by Nathan Curtis  EightShapes  Medium]]（2019）

- すべての機能が同じ価値・同じ品質・同じ関連度ではない。**上の階層ほど広く共有され、高品質が要求される**。アイデアは個人→隣の協力者→グループ→全員と「湧き上がる」ものであり、システムはその段階を反映できる
- 最上位に全員に関わる **core**（色・タイポグラフィ・アイコン・スペース＋Button 等の明白な共通コンポーネント）を分離し、責任を持つコアグループが集中管理する
- **Tier 2 は事業部内（within）と事業部横断（across）の2種**。事業部内の拡張キットは既に野良で発生している（Sketch キット拡張・独自コンポーネントコード）ので、システム側が型とツールを提供して統治する。横断型はリッチテキストエディタのような高コスト機能への共同投資で、**システムチームの全プロダクトへの可視性は強みではなく責務**——機会を見つけて繋ぐ「マッチメイカー」になる
- 25チーム規模の実例: `core-ui` の兄弟リポジトリとして `sales-ui` をインスタンス化。統制は緩く、カタログは急拡大し「散らかっている」と見る者もいたが、システムチームは**昇格候補の宝庫**と見た。lint・VRT などの品質ツールが定着し、営業チームは気づかぬうちに core を全面利用する「第二階層」になっていた
- **権限は「可視性は最大・編集は限定」**: 全キットをコミュニティ全員が見られるようにし（重複削減・実験への合流を促す）、編集権はその事業部＋コアチームに絞る
- **名前空間は中央でキュレーション**: `checkbox-button` と `action-button` と `box-with-checkmark-in-it-button` が転がる事態を防ぐ。後からのリネームは早期採用者にリファクタリングを強いるため、命名の審査者を明確にする
- **階層が上がるほど品質基準が厳しくなる**3段階の例: Within Group（ブラウザ確認・lint・関係者に必要な a11y・コアと整合するスタイル）→ Across Groups（＋レスポンシブ・BEM・semver・変更ログ・トークン依存のスタイル・ユニット/VRT・コミュニティ承認）→ Core（＋包括的 a11y レビュー・サイズ展開・背景対応・テーマ・分析・RTL 等の i18n）。IBM Carbon の「Experimental」表示や Atlassian Atlaskit のパッケージ群（`bitbucket` / `editor` / `search`）が実例
- 階層はコントリビューションの会話の足場になる: 「`editor` を**セット**として（What）／**tier 2** で（Where・How well）／**3スプリント**かけて（コスト）／グループ **A と C** のために（Who）作る」——貢献を「実験から広範利用への昇格」として設計できる（[[デザインシステムのガバナンス]] の3層コントリビューションモデルと相補的）

## Central と Local — kintone の実践（sakito）

以下すべて出典: [[Central と Local モデルで進化するデザインシステムの拡張と戦略｜sakito]]（Curtis の Tiers を明示的な下敷きに、階層の最上位を Central・下位を Local と定義）

- **Central**: 全プロダクト共通の要素（デザイン原則・ガイドライン・トークン・アイコン・基本コンポーネント＋ドキュメント）。品質が高く関係者が多い。専門のデザインシステムチームが管理
- **Local**: Central を利用しつつプロダクトに特化したもの（複合コンポーネント・プロダクト固有の機能）。プロダクトチームが管理し、複数階層になりうる。コンポーネントライブラリに近い性格
- Brad Frost の The Design System Ecosystem の5層（コアデザインシステム層 / テクノロジー固有層 / レシピ層 / スマートコンポーネント層 / プロダクト層）に対応させると、コア層が Central・残りが Local
- メリット3つ: (1) **すべてのパターンを網羅する必要がなくなる**——Central は共通に集中し、Local はヘッドレス UI（React Aria / Radix）＋ Central のトークンで独自性を出せる (2) **責任の分散**——DS チームとプロダクトチームの分業 (3) **成果物の移動が容易**——同じツール（Storybook）で揃えれば Local→Central の昇格がスムーズ
- [[kintone Design System]] の実践: ドメイン分割された4つの機能開発チームが Local を開発し、**他ドメインでも共通と分かったコンポーネントを Local から Central へ引き上げる**。プロダクトデザイナーが Central のトークンを持ち込み、デザインテクノロジストとエンジニアが実装・ドキュメント化して移動を支える。Federated チームモデル（[[連合型デザインシステム]]）が Central の成長を支える両輪

## ドメイン特化デザインシステム — Pennylane の事例

以下すべて出典: [[Our Core Design System was not enough  Why we built a Domain-Specific Design System (and how it made us scale)]]（Pennylane、会計 SaaS の税務申告ドメイン、2026）

- 「**速度の幻想**（The Illusion of Velocity）」: 出荷できていて画面も正しく見えるが、内部では崩壊が進む。数百種の税務申告フォームを扱う中、28フォームを調べると「同じ部品のはず」のセクションヘッダに**8つの異なる実装**が見つかった
- 崩壊のシグナル: **翻訳税**（Figma の「Table Title」がコードでは「Header Row」——ハンドオフごとに人間の翻訳者が必要）／**並行宇宙**（squad A がコンポーネント X を作り、B が同じ目的の Y を独自実装）／**80%一致**（デザインファイルは「なんとなく似ている」コンポーネントの墓場で、新人はパターンと負債を区別できない）／**偶発的標準**（急ぎの応急処置がコピペで新機能に増殖——設計ではなく前例の複製）。「1組のデザイナー・エンジニアが1機能を出荷することに最適化し、次に入ってくる50人を犠牲にしていた」
- **ドメイン特化 DS を検討すべき条件**: ドメインロジックがパターンに焼き込まれている／「レンガはあっても家は建たない」（Design Ops は色・タイポのレンガを提供するが、特定の家の建築は支援できない）／数百のフローを一貫して扱う「工場」が要る／所有者が不明確で全員が前例を複製している／**中央集権が速度の罠**（グローバル DS への長い貢献パイプラインはドメインルールの高速反復を殺す）
- 要諦: ドメイン特化 DS は**特化レイヤー**であり、「グローバルなプロダクト言語を汚染せずに、複雑なルールの上を高速で動く」ための構造。ロードマップを一時停止して監査し「1つのニーズに1つの解」を全員で選定、**Figma ライブラリをコードベースの双子として再構築**（React の `DeclarationCard` は Figma でも `DeclarationCard`）、見た目ではなく**振る舞いを文書化**
- 成果: 翻訳税の消滅（4日超→2日未満）、統一言語、**バックエンド専門エンジニアが単独で複雑な税務フォームを構築**（単純なフォームはワイヤーフレーム不要）、新人が数日で貢献者に（「例外のリストではなく言語を学ぶ」）、そして**上流パイプライン**——ドメイン内で証明されたコンポーネントが Core DS へ昇格し、ドメイン特化 DS の方法論自体が他プロダクト領域へ複製された。デリバリー速度は4倍
- 代償も明記: system-first 思考に傾き「システムで作れる十分解」をユーザー最適のカスタム解より選びがち／コンポーネント改善が他 squad を壊しエンジニアが萎縮／QA・「何をシステムに入れ何を squad 固有に残すか」・レビュー体制というガバナンスを後追いで学ぶ必要があった

## 3層＋イノベーションサンドボックス

出典: [[Design Systems at Scale How Skilled UXUI Executives Preserve Uniformity Without Inhibiting…]]（Akio、2026）

- 「要塞が牢獄に変わる」——一貫性のために作った DS が官僚主義的ボトルネックへ変貌する問題に対し、階層ごとに異なるガバナンスを敷く: **Core**（タイポ・色・グリッド・主要インタラクション要素。変更は困難・稀・広範な合意を要すべき）／ **Shared**（ナビゲーション・データテーブル等の複数プロダクト向け。厳格な強制より参加型ガバナンス）／ **Local イノベーションサンドボックス**（実験のための領域。「逸脱してよい、ただし独自解を記録し効果を測定する責任を負う」）
- **コントリビューション・フライホイール**: ローカルの成功した実験を Shared / Core へ昇格させる経路を制度化する。「あなたの優れた仕事は機能の中で生き死にしない。会社の新しい標準になりうる」というモチベーション設計。リーダーの役割は門番（gatekeeper）ではなく**庭師**（gardener）

## マルチブランドの3層 — Core Engine / Brand Skin / Product Context

以下すべて出典: [[Advanced UI Design Systems for Scalable Product Teams Working Across Multiple Brands]]（Akio、2026。上記サンドボックス論と同じ著者）

- マルチブランド DS は「色の差し替え」では成立しない。**無スタイルの Core Engine**（構造・挙動・a11y のみ）／**Brand Skin**（ブランド別の視覚言語）／**Product Context**（プロダクト固有の適応）の3層に分離し、構造の共有とブランドの独自性を両立させる。層間の結線は[[セマンティックトークン]]が担う——「マルチブランドの神経系」
- 昇格規範は **rule of three**: 3つのブランドが同じものを求めたら Core へ昇格させる（Tiers の昇格論・レシピ層の「卒業」と同型の経験則）
- 買収後のブランド統合（構造共有×ブランド自律の交渉）は [[ブランドとデザインシステム]] を参照

## 5層エコシステム — Brad Frost の「悪魔のレイヤーケーキ」

以下すべて出典: [[The Design System Ecosystem  Brad Frost]]（2023。[[Central と Local モデルで進化するデザインシステムの拡張と戦略｜sakito]] が下敷きにした原典）

- 成熟したエンタープライズDSの全体像を5層で描く: **コアデザインシステム層**（組織共通の構成要素）／**技術特化層**（任意。フレームワーク・ネイティブ実装）／**レシピ層**（任意。特定プロダクト文脈の合成コンポーネント）／**スマートコンポーネント層**（任意。ロジックを持つ即戦力部品）／**プロダクト層**（出荷される本物のサイト・アプリ——「全ての理由」）
- **ほぼ全ての層はオプション**であり、**Gall の法則**（動く複雑系は必ず動く単純系から進化したものであり、ゼロから設計された複雑系は動かない）に従って「必要になったときにだけ層を足す」。ごく一部の実装でも価値は出始める
- 資産の型: デザインライブラリ／デザインファイル／コードリポジトリ／フロントエンドワークショップ（[[Storybook]]）／コードパッケージ／リファレンスサイト（workshop と storefront の対）
- **コア層**: 「解決済み問題のライブラリ」「退屈なもの」（フォーム部品・ボタン・アコーディオン）。トークン（サブアトミック粒子・ブランド変数。**テーマ対応の3層トークンアーキテクチャが秘伝のタレ**で、トークンを独立した層に分離して独立バージョニングする）＋アイコン＋UIコンポーネント＋リファレンスサイト
- コア web DS の実装は **Web Components を強く推奨**（標準・どのフレームワークとも相互運用・テーマ可能・自己完結。Lit で執筆）。React 等での構築も可能だが「その技術と非互換なプロダクトには届かない」ことに目を開いておく。対して Astro DS の実務家は「Web Components には注釈が多い（Shadow Parts の DX は良くない）。HTML と CSS を好め」と証言しており（出典: [[Design System Wisdom 2023]]）、技術選定はここでも割れる
- **技術特化層**: `<ds-button>` を `<DsButton>` に包むフレームワークラッパー。存在理由は React のイベント処理の糊・既存ライブラリの「勝ち取った採用」の保護（中身だけ Web Components に置換）・API 命名の漸進移行・技術差し替え時の防波堤。ネイティブ（iOS/Android）は標準不在・OS 規約・ツール未成熟（「iOS の Storybook はあるか」と何度も聞かれる）・チームのサイロ化が課題。航空機シートバック・ATM・キオスク・医療機器 UI も同じ指針（専用リポジトリ＋レジストリ配布）
- **レシピ層は圧力弁**: 全 UI 判断を追いかけて会議を渡り歩く小さな DS チームはボトルネックと燃え尽きに至る。「DS は全 UI を所有する必要はない。**材料を提供し、チームがレシピを作るのを支援する**」。IBM Carbon はこの概念に寄った（Robin Cannon のハブ&スポーク論:「事業部はシステムを自分たちのドメイン向けに調整する追加能力を必要としていた」）。同じ材料（card・button・badge…）から EC チームは product card を、マーケは promo card を、分析チームは customer data card を合成する。成功したレシピをコアへ「**卒業**」させるインキュベーターにもなる
- **スマートコンポーネント層**: DS コンポーネントは意図的に「dumb」（ポータビリティのためビジネスロジック・バックエンド接続を持たない）。それをロジックで包み、フォーム検証・決済・タイプアヘッド・データテーブル・分析計装・CMS 対応などの即戦力部品として配る層。発展形は「トークン・コンポーネント・レシピ・フォーム配線・ルーティングまで揃った **NextJS ボイラープレート**」のような社内スターターキット。基盤サービスを持つチームが維持する
- 結語: 「デザインシステムは資産とその関係の話であるより、**人と人の関係の話**」。ペースレイヤー論（後述）は同じ Big Medium 系の時間軸バージョン

## その先の階層 — Global Design System 構想

以下すべて出典: [[A Global Design System  Brad Frost]]（2024）

- 組織単位の DS は個人の重複作業を解いたが、**組織間の重複**を生んだ——「今この瞬間も膨大な人々が、まったく同じアコーディオン・デートピッカー・タブを設計し、構築し、文書化し、維持している」。**メタデザインシステム問題**
- 品質の根拠: トップ100サイトで valid HTML は0件、WebAIM Million は「トップ100万ページ平均50件のa11yエラー」を毎年報告。「開発者にもっと大声で叫ぶ」戦略は機能していない——共通コンポーネントを世界で一度だけ正しく作る方が筋が良い
- 「なぜ Material や Bootstrap を使わないのか」への答え: (1) 特定組織の目的に調律されている (2) **既定の美観**が付いてくる（Material を採れば Google 製品の見た目になり、デフォルトと戦って混乱を作る）。headless UI / react-aria は精神は正しいが React に繋がれている。必要なのは「**美観・技術非依存で、堅牢な意味論と機能を提供し、美的自由度が高い**」ライブラリ（Web Components + 各自のテーマ = DS 版 CSS Zen Garden）
- HTML の上のレイヤーという位置づけ: HTML は IKEA の最小部品であり、必要なのはプレハブ部材。全ユースケースを負う HTML 仕様と違い 80/20 で保守的に絞れるのが利点で、レシピ→コア昇格と同様に**将来の HTML 仕様への孵化器**にもなる。W3C が最適な受け皿で、Open UI のコンポーネントマトリクスが下調べに当たる
- 実現すれば DS チームは component 生産から解放され、デザイン言語・ガイドライン・エコシステム編成・レシピのキュレーション・スマートコンポーネント・AI 自動化ツールへ集中する——「respect and human potential」の議論
- 階層化の文脈では、ドメイン特化DS（上）→ 組織コア → **世界共通層（下）**へと層が伸びていく構想と読める。エージェント時代の「共通カタログ」論（[[AI時代のデザインシステム]]）とも接続する

## ペースレイヤー — 遅いコアと速いプロダクト（Big Medium）

以下すべて出典: [[Ship Faster by Building Design Systems Slower  Big Medium]]

- DS チームの職業病は「自分たちは遅すぎる・ボトルネックだ」という実存的不安。しかし「**成功するデザインシステムは、支えるプロダクトよりゆっくり動く。それはバグではなく仕様**」
- 論拠はインフラ論: DS は組織全体の UI・UX・コードの「血流」に注入される重要インフラであり、「**血流に粗悪品を注入するのは悪い考え**」。プロダクト層では MVP のための近道・負債が commercial に正当だが、インフラ層の負債ははるかに高くつく——だから quality over speed
- 理論的土台は Stewart Brand の**ペースレイヤー**（『The Clock of the Long Now』1999）: 「**速い層は学び、遅い層は記憶する。速い層は提案し、遅い層は裁定する。速い層が注目を集め、遅い層が力を持つ**」。デジタルプロダクトでは外側から プロダクト（最速）→ プロダクトリサーチ → ビジュアルブランド → デザインシステム・標準・インフラ（最遅）。マルチブランド DS ではブランドより DS が長寿命なので、ブランドの方が速い層になる
- プロダクトが DS の提供を待てないときの答えは「急造品をライブラリに入れる」でも「プロダクトを待たせる」でもなく、**プロダクトチームが自分でレシピを料理する**: レシピ＝DS の材料（コンポーネント・トークン・アイコン・スタイル）から作る UI パターンで、DS エコシステムの独立した層。プロダクトチームが所有・ホストし、チームごとに「クックブック」（独自の Figma ライブラリ・リポジトリ）を持つ。Google Calendar / YouTube / Gmail が Material の上に維持する製品固有パターンが実例
- DS チームが将来ライブラリ化するつもりの機能も、間に合わないならプロダクトチームが**ファーストドラフト**を作り、DS チームは高レベルの API 設計だけ協調して（後で公式コンポーネントに差し替えやすくする）、バックログに載せて改善・正式収録する。レシピ方式は負債を生むが「プロダクト層の負債はインフラ層の負債より安い」——イノベーションのコストとして意図と透明性をもって使う
- 「**デザインシステムチームの仕事はイノベーションではなくキュレーション**」: 答えが DS に入るのは「問いがもはや面白くなくなったとき」（プロダクトで証明済みになったとき）。「最も刺激的なデザインシステムは退屈である」。系は [[宣言的デザインシステム]] のコレクション批判・[[デザインシステムの強制と例外]] のストライクゾーンと響き合う
- 成立条件は人間の調整: プロダクトチームは年次・四半期のロードマップ策定時に DS チームへ新機能ニーズを事前共有し、DS の計画に合えば DS が作り、合わなければ自作を計画する——「**サプライズなし**」。「最大の課題は技術実装ではなく人間の調整」「速さの文化を、遅く動くことで支えよ」
