# トークンベースのUIアーキテクチャを設計する 要約

ソース: [[トークンベースのUIアーキテクチャを設計する]]

martinfowler.com 掲載の、デザイントークンを UI アーキテクチャの基盤として設計するための包括的な解説。
後から変更しにくい3つのアーキテクチャ判断——トークンのレイヤー構成、公開範囲（スコープ）、配信の自動化——に焦点を当てる。
レイヤーは option（何が使えるか）/ decision（どう適用するか）/ component（どこに適用するか）の3種で整理し、2〜3層が大規模デザインシステムの主流、まずは2層で始めて必要になったら component 層を足すのが良いとする。
開発者に必要なのは主に decision 以降なので、option トークンを private にするスコープ分離が有効で、Style Dictionary の filter やスコープフラグで実装できる。
配信は Git リポジトリを Single Source of Truth とし、検証→ビルド→テスト→公開→通知のデプロイパイプラインで自動化することで、Thoughtworks では小さなデザイン変更を1日で複数フロントエンドに展開できた。
採用判断としては、マルチプラットフォーム・頻繁なデザイン変更・大規模チームでは有効だが、小規模プロジェクトでは管理オーバーヘッドが見合わない場合もあると結論づける。
