# Most Design Systems Don’t Break Because of Buttons 要約

ソース: [[Most Design Systems Don’t Break Because of Buttons]]

デザインシステムはコンポーネント不足ではなく「あらゆる場所で普遍的であろうとすること」で死ぬと論じ、スケール時の失敗パターンを実装コード付きで解剖する長編。
20個の boolean フラグを持つ Button は柔軟なのではなく「複数のコンポーネントであることをまだ認めていない」だけで、プロダクト文脈は基底コンポーネントではなく上位のプロダクト層ラッパーへ移すべきとする。
トークン地獄の原因はセマンティックトークンの欠如ではなく「悪いセマンティクス」（改名しただけのプリミティブ、コンポーネントトークンだけの巨大 JSON）であり、primitive / semantic / component の3層と CI でのコントラスト検証（テーマをエンジニアリング成果物として扱う）を処方する。
「見た目が同じでも変更理由が異なる UI は統合を急がない」という false reusability の回避、core / product / experimental のパッケージ分離、escape hatch の可視化（穴ではなく看板付きの扉）、props ではなく境界（いつ使わないか）のドキュメント化を提唱する。
結論として、スケーラブルなデザインシステムとはすべてが再利用されるものではなく、何を再利用し何を分離すべきかを全員が理解しているものである。
