# kintone Design System

## 概要

サイボウズ kintone のデザインシステム。kintone Design Team が構築・運用しており、「なぜデザインシステムを作るのか」を社内向けに説明するドキュメントを2023年9月に一般公開した（出典: [[「私たちがデザインシステムを作っている理由」のドキュメントを公開｜sakito]]）。ミッションは「kintone についてアウトプットする人たちが、一貫性のあるユーザー体験とデザインの品質をユーザーに提供できる状態を作る」。社内のデザインシステムの取り組みは2018年の勉強会に遡る（出典: [[kintoneデザインシステムの現在地｜Cybozu Product Design]]）。

## 成り立ちと構成

- 前身は kintone フロントエンドリアーキテクチャ（フロリア、Monorepo＋チーム単位オーナーシップ）を横断する「**ユーザー体験を最高にするチーム**」（後の Mantle）。チーム分割で失われがちな一貫性を守るため、開発中の画面から共通コンポーネントを集約することから始めた。「**コンポーネントライブラリは知識の翻訳の役割**」——更新の速い CSS や a11y の知識を、各チームが模索せずともユーザーに届けられる（出典: [[ユーザー体験を最高にするkintone Design Systemsをつくってます｜sakito｜note]]）
- 提供物: Figma と React のコンポーネントライブラリ＋全コンポーネントの仕様ドキュメント＋デザイントークン＋ガイドライン（フロントエンド向け・デザイン向け・ライティング）＋コントリビュートガイド。**Figma・React・ドキュメントの3点は必ず足並みを揃える**——「数ピクセル調整してください」というデザイナー・エンジニア間の往復を消すため（出典: [[kintoneデザインシステムの現在地｜Cybozu Product Design]]）

## 主要な事実

以下すべて出典: [[「私たちがデザインシステムを作っている理由」のドキュメントを公開｜sakito]]（kintone Design Team の sakito、2023-09）

- 構築する理由として3つを挙げる:
	1. **デザイナーが入れ替わってもデザインの歴史を継承できるように** — kintone は10年以上続くプロダクトだが、「なぜこのデザインにしたのか」という意思決定の言語化がないまま進み、あっても各所に散在・断片化していた。記録がなければ、視認性のために薄い青→濃い青へ変えた判断が、後任の好みで薄い青に巻き戻されうる（意思決定の手がかりなしのデザイン変更は危険）
	2. **デザイナーじゃなくてもデザインの意思決定ができるように** — ガイドラインとコンポーネントが揃えば、既存パーツの組み合わせによるページ作成は誰でもできるようになる。デザイナーは戦略や新機能デザインなど本質的な部分に思考を投資でき、少人数でも改善活動が回る
	3. **ベストプラクティスなコンポーネントの配布** — ガイドラインや a11y のドキュメント化だけではプロダクトで使えない。どのチームで使っても同じデザイン・操作体験になるコンポーネントを配布し、改善要望を一元化して各チームに恩恵を還元する
- 参照例として Salesforce Lightning・Adobe Spectrum・Shopify Polaris を挙げ、デザインシステムの一般的な構成要素をスタイルガイド / コンポーネントライブラリ / パターンライブラリ / ドキュメンテーションと整理している
- このドキュメントは開発チームの関係各所への口頭説明に使われており、継続的に更新される予定

## 体制 — Mantle チームと PO

以下すべて出典: [[デザインシステム構築におけるオーナーの重要性｜sakito｜note]]（2022-12）

- デザインシステムは「ユーザー体験を最高にする活動」を担う **Mantle チーム**が構築。kintone フロントエンドリアーキテクチャ（**フロリア**）プロジェクトの1チームで、1週間スプリントのスクラムで開発する
- チーム構成: PO（sakito）/ スクラムマスター / デザインテクノロジスト / デザイナー / エンジニア / アクセシビリティ / QA。副業メンバーも含み、非同期でバックログアイテムを渡す運用
- PO の実践: 目指す姿の明確化（「各アプリケーション開発チームが主体的に品質の高いアプリケーションを素早く開発できる」「一貫したユーザー体験と品質」——**含める/含めないの判断基準と根拠**になる）、1年目標→クォーター分解のロードマップ、バックログの作成と優先度
- **学習バックログ**: 「デザインシステムの本を読む」を最優先バックログにして全員で取り組み、チーム内の用語統一と理解の土台を作った。週1勉強会で職能横断のスキルシェアも行う
- 「デザインシステムを1つのプロダクトのように運営するオーナー」が持続的成長に不可欠、という結論。一般論としてのオーナー論は [[デザインシステムのガバナンス]] を参照

## 育て方 — Federated 移行とワーキンググループ

以下すべて出典: [[デザインに関わる全ての人たちでエベレスト登頂を目指すために取り組んでいること｜amishiratori]]（Design System チームリーダー Ami Shiratori）

- Design System チームは2021年12月結成。kintone 開発チーム（120人超）の中の kintone Design チーム（23人）のサブチームで、専任5名（デザインテクノロジスト4＋デザイナー1）＋業務委託・ヘルプの計7名
- 「理想の Button のドキュメント」に2ヶ月かかった経験から「最初から完璧なデザインシステムは作れない」——**エベレストの比喩**（いきなり踏破ではなく高尾山から）を運営理念として明文化し、最初に目につく場所に掲示
- **Centralized → Federated へ移行**し、運営理念公開後半年でコントリビューター30名超（デザイナー・UX ライター・ローカライズ・FE・QA）。「今」使えるものの提供（既存共通コンポーネントの切り出し）で利用実績を先に作り、**PM がプロダクトロードマップに DS 投資を記載**するに至った。連合型の一般論と成立条件は [[連合型デザインシステム]] を参照
- **ワーキンググループ**（デザイン / アクセシビリティ / UX ライティング）が有志で起案・議論・執筆し、DS チームレビューで正式ガイドライン化。類似アイコンの整理など、DS チーム単独では知見・工数が足りない仕事を解決。「デザインシステムチームはビジョンと場所を提供する」
- **Central と Local の階層化**（[[Nathan Curtis]] の Design System Tiers が下敷き）: DS チームが管理する Central（原則・トークン・アイコン・基本コンポーネント）と、ドメイン分割された4つの機能開発チームが管理する Local に分け、**他ドメインでも共通と分かったコンポーネントを Local から Central へ引き上げる**。プロダクトデザイナーが Central のトークンを持ち込み、デザインテクノロジストとエンジニアが実装・ドキュメント化して移動を支える。Federated チームモデルが Central の成長の前提。Cybozu Days の「ワンプラットフォーム」「エコシステム」構想が今後の拡張文脈（出典: [[Central と Local モデルで進化するデザインシステムの拡張と戦略｜sakito]]。一般論は [[デザインシステムの階層化]]）

## 運用哲学 — 「理想を押し付けない」

以下すべて出典: [[kintoneデザインシステムの現在地｜Cybozu Product Design]]（2024年12月のポッドキャスト、Ami × sakito）

- **理想を押し付けない**: 10年以上のサービスへの後付けなので綺麗な整理は不可能。今の kintone で使われているコンポーネント・色使いを DS に収納し、使ってもらった前提で改善する順番。「理想への一気の跳躍が『押し付け』であり、段階的接近の最初のステップを提示する」
- **フロントエンド刷新の波に乗った**のが加速要因: 作り直しのタイミングで「もう作ってあるコンポーネントがあります」と提示でき、利用範囲が刷新と一緒に広がった
- 「**使われていないパーツはほとんど存在しないが、穴ぼこはある**」いびつな形を肯定する——他社デザインシステムの真似で先回りすると走行中のサービスと不整合を起こす。「流れで使ってもらえそうな時に頑張って作り、作ったら必ず使ってもらう」
- **課題解決にあてがう**: 「デザインシステムを使ってください」ではなく「デザイナー・エンジニアのプロセス上の課題に、デザインシステムで解決できますよ、という持って行き方」。例:「コミュニケーションコストは DS で4割改善、Dev Mode フル活用であと3割」。ゼロイチなら Material Design や Bootstrap でも作れるが「それだけでは足りない」のが自作の理由
- 成果（2024年夏時点）: GitHub 上の直接コントリビューター45名、意思決定関与を含めると60名近く。発端はサイボウズのビジョン「チームワークあふれる社会を創る」——「チームでデザインシステムを作らないのは違和感」
- 展望: 新画面を kintone ブランドで作るハードルを下げる（現状は既存機能に合わせたコンポーネントのみ）、パートナー・制作会社など社外開発者への**外部公開**（「作ってる時からずっと言ってた。やっと現実的になってきた」）

## 啓発 — オンボーディングとリリースブログ

以下すべて出典: [[デザインシステム啓発のためのアプローチ｜kintone Design Systemのオンボーディング改善とリリースブログ｜トビ - KazuhiroTobita]]

- 社内向けドキュメントを Storybook で提供（GettingStarted / Contributing / Guidelines / DesignTokens / Components）。意義は「意思決定の歴史継承・共通認識・エンジニアの自律的判断」の3つ
- ドキュメント急増と利用者の多様化で「初見の利用者が必要な情報に辿り着けない」課題 → 利用者を**4属性**（コンポーネントを使いたい / ドキュメントを読みたい / トークンを使いたい / コントリビュートしたい）に分け、Introduction に属性別エントリーポイントを明記。各 README に「**体験の1本線**」（優先して読む順序）を引いた。新卒が研修から活用し、エンジニアのコミットと本質的な質問が増えた
- **毎月の社内向けリリースブログ**: 更新概要だけでなく修正背景と得られる恩恵を記載し、デモリンクを埋め込み、コントリビューターへ Special Thanks を添える。個別説明コストが下がり、kintone 本体開発に先んじた提供の進行状況が掴めるため各チームが戦略を立てやすくなる
