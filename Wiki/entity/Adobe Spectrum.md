# Adobe Spectrum

## 概要

Adobe のデザインシステム。主に社内向け（Material のような外部開発者向けプラットフォームではない）でありながら早期から公開されており、「公開が品質基準を自然に引き上げた」と当事者が語る。CSS 実装から始まり、React Spectrum・Web Components・iOS・デスクトップ・Android（構築中）の複数実装（implementations）を別々のチームが保守する（出典: [[Garth Braithwaite on Design Tokens, Governance, and Scaling Spectrum at Adobe  Knapsack]]）。

## トークンの3層と使い分け

以下すべて出典: [[Design tokens - Spectrum]]（公式ドキュメント）

- **Global**（文脈非依存の原始値。パレット・アニメーション・タイポグラフィ・寸法）/ **Alias**（文脈・抽象への紐付け。単一の意図が複数箇所に現れるときに意図を伝える）/ **Component-specific**（コンポーネントに紐づく全値の網羅的表現。alias を継承し、エンジニアが最大限特定的に適用できる名前を持つ）
- 使用指針: **Global は控えめに**（デザイン言語のロジックから最も遠く、alias がない場合のみ）。**Alias を使えるところでは常に使う**——Spectrum を理解する「ロゼッタストーン」であり、システムの進化に自動追従して将来の保守を最小化する。Component トークンは当該コンポーネント専用（派生関係がない限り他へ流用しない）
- サイズトークンは基準値へのパーセントで命名（`size-100` = 100% = デスクトップ 8px / モバイル 10px）し、**2つのプラットフォームスケール**を1つのトークンで自動切替する。境界線太さのようにスケール間で不変の値は `static-size` トークン

## 設計データの運用 — Garth Braithwaite の証言

以下すべて出典: [[Garth Braithwaite on Design Tokens, Governance, and Scaling Spectrum at Adobe  Knapsack]]（Lead Senior Staff Design Engineer、創設期からのエンジニア。デザイナー出身）

- パイプライン: デザイナーが Figma で著述 → [[Tokens Studio]] プラグイン＋独自ワークフロー → 公開 GitHub リポジトリ。転送形式は JSON で、**JSON Schema による検証**（強い型付けに近い運用）を通す
- 万能フォーマットの限界: 「デザインを完全に普遍形式へ蒸留するのは不可能」。フォント描画・ベースラインは自社タイプファウンドリ（Adobe Clean）を持つ Adobe でも「フルタイムの問題」。値はピクセルで提供して iOS がポイントへ変換し、**JSON だけでは「正しく見えるか」を検証できないため Figma アセットの併給が必須**
- 命名の運用: デザイナーが spec にトークンを列挙し、**デザイナー自身がチェンジログを書く**（コンポーネント単位のバージョンと変更の設計動機をサイトで公開。トークンのバージョン間 diff はスクリプトで生成）。エンジニアがガイドライン準拠を検証し、**コンテンツストラテジスト**が「正しい言葉の定義と議論のファシリテーション」を担う——「チームがある規模に達したら、次の採用はコンテンツストラテジスト」
- **anonymous tokens 構想**: 名前という文字列に意味情報を全部背負わせる現状は brittle（typo・一貫性を強制できない）。メタデータを文字列の外に出し、型検証できるオブジェクトへ移す。ただし「**トークンは流れ続けねばならない**」——消費側の互換を壊さず漸進する（1年かけた全面書き直しは選ばない）
- wayfinding 問題: 公開のトークンビジュアライザーを持つが、最悪ケースは「2px が要る → 2px に等しい最初のトークンを掴む」というセマンティクスの迂回で、後日そのトークンの値変更が予期せぬ破壊を起こす。**ハードコード値禁止の lint は「どれでもいいからトークンを掴む」へ押しやっただけ**で、本当に欲しいのは「より意味的な候補を提案する」linter。エンジニアを責めない——「彼らはトークンエンジニアではない」。オフィスアワーと、ドキュメントを読み込む AI ヘルプボット（初期段階）で支援する
- バージョニング: 命名と並ぶデザインシステムの2大難問。コンポーネント単位のバージョンを持ち、CSS 実装はコンポーネント別 npm パッケージで à la carte 更新できる（iOS はその流儀を好まない——文化とプラットフォーム特性）。デザイナーはルールを共同で作れば semver をうまく運用するが、**「デザインの破壊的変更」と「実装の破壊的変更」は一致しない**: 見た目が同じでも DOM 構造が変わる／新バリアントはデザインには minor でも実装には breaking／コントラスト比を保った色変更が未知の背景の上で a11y 問題を起こす
- **フロントエンド・マニフェスト（3箇条）**: (1) **デザインシステムはインフラ**（道路のメタファー: 全員が恩恵を欲しがり、誰も費用を払いたがらない。初日から全戸へ道路は引けず、「そのコンポーネントがリリースに必要なら自分で作って。正しく作る手伝いはする」——全プロダクトのクリティカルパスには載らない。Shawn Cheris の言に由来）(2) **デザインシステムの目的は変化し、変化を管理すること**（ゴールデンゲートブリッジの塗装——塗り終わる頃に最初からやり直し。完璧が不要になる分、自由でもある。現在 Spectrum 2 へ移行中）(3) **プロダクトオーナーへの価値を作る**（統一 UI を命令で強いると、エンジニアは黙って独自版を作り、全員が恩恵を失う。「デザインシステム警察にはなれない」。CSS は誰も書きたがらないため最初の価値提供点として最適だった）
- オープンソースの恩恵: 公開が品質を上げ、採用面接に「React Spectrum でアプリを作ってきた」候補者が来る。社内利用主体の DS では外部 PR は少なく**ガバナンス負荷は低かった**（懸念は杞憂）。副産物として React ARIA（Devin Govett ら。汎用 ARIA 実装として starter kit に同梱されるほど普及）や Leonardo（[[Nate Baldwin]] 作。コントラスト比を制約として入力しカラーシステムを生成）が生まれた

## Spectrum 2 — 10年ぶりのデザイン言語刷新

以下すべて出典: [[10年ぶりのデザイン言語刷新に乗り出すアドビ　担当者に聞く「Spectrum 2」誕生の経緯と目的｜Real Sound｜リアルサウンド テック]]（担当シニアディレクター Shawn Cheris へのインタビュー。「デザインシステムはインフラ」の言の主）

- 背景: 2013年の Spectrum 1 から10年で、非プロフェッショナルユーザーの増加・競合増・デジタル体験の進歩。「Spectrum 1 は少しミニマムすぎたかもしれない」——反省を踏まえ、デバイスのフィジカリティと3Dを活用する方向へ。理念はインクルーシブ・アクセシビリティ・エクイティ（「Creativity for all」）
- **動的パレット生成の構想**: Leonardo を「将来の Spectrum に搭載したい」——静的なカラーパレットではなく、ユーザーの環境や好み（ハイコントラストモード・色覚・視覚の多様性、さらに明るさ・フォントサイズ・濃度）に基づいて動的にパレットを生成する
- **OS ガイドラインとの関係を転換**: 「他で見た製品を“そのまま” iPad に押し込もうとしてきた」→ 今後は Material 等プラットフォームの規定を重視しながら必要なものを追加する方針（[[セマンティックトークン]] にある「Spectrum はもう全面コンポーネントトークンの5条件に該当しない＝各プラットフォームの良き市民へ」という Baldwin の記述と符合）
- 「**UI は言語**であり、できる限り“発明”をしない」——フロッピーディスクの保存アイコンは実物を見たことがない世代にも通じ、代替の意匠がいまだに現れない。Photoshop ユーザーは「良いものにしてほしいが、何も変えないでほしい」（900万人のディナー問題）
- 生成 AI: チャットのような馴染みある形式の先に「タスク実行時に必要なインターフェイスがリアルタイムで生成される」動的 UI の可能性を見るが、「**AI のための理想的なインターフェイスはまだ発明されていない**」

## React Spectrum — ロジックとUIの分離

- 2022年7月に公開された React 実装。特筆されるのは **ロジックと UI の完全分離**: `react-aria`（`onClick` をデバイス横断の `onPress` に統一する等、プラットフォーム差を吸収するカスタム Hooks）と `react-stately`（DatePicker・Table・Search・Toast・Virtualizer 等の UI 非依存な状態ロジック）を切り出し、**「ロジックだけ借りて自社のデザインシステムを作る」**使い方を可能にした。ロジック部分は cross-platform・アクセシビリティ・多言語対応を1年半以上かけて開発・テストしたもので、「多様なプラットフォーム対応のロジックを自作するのが辛い」チームの土台になる（出典: [[Adobe製デザインシステム「React Spectrum」がすごいので紹介したい - Qiita]]）。ヘッドレス UI として Central トークンと組み合わせる用法は [[デザインシステムの階層化]]、Wantedly の採用例は [[デザインシステムとアクセシビリティ]] を参照

## カラーシステム v6.0（2013年以来の大改定）

- 100超プロダクトを支える色を7ヶ月かけて刷新。静的スウォッチではなく「生成の制約を定義する」**アダプティブカラーパレット**方式で、知覚均等色空間 CIECAM02 と Stevens のべき法則に基づく再設計。**700番台=3:1、900番台=4.5:1 のコントラストをインデックスで保証**する。ツールは [[Nate Baldwin]] の Leonardo を要件に合わせて同時進化させた（出典: [[Adobe Spectrumのカラーバリエーションを再発明]]）。詳細は [[カラーシステムの設計]]
