# SmartHR Design System

## 概要

SmartHR のデザインシステム。スローガンは「だれでも・効率よく・迷わずに。」で、ウェブサイトとソースコードを一般公開している。**ブランドデザイン文脈**（ビジネスサイドのアセット、コミュニケーションデザイナー主体）と**プロダクトデザイン文脈**（UI・用字用語ガイドライン、プロダクトデザイナー・UX ライター主体）の2文脈で構成される（出典: [[SmartHRのプロダクトデザインの生産性を高める“デザイン”のためじゃないデザインシステムとは（Schema2022）｜wentz｜note]]）。

## 位置づけ — 「“デザイン”のためじゃない」

以下すべて出典: [[SmartHRのプロダクトデザインの生産性を高める“デザイン”のためじゃないデザインシステムとは（Schema2022）｜wentz｜note]]

- 「デザイナーの生産性を上げるツール」ではなく「**デザインとエンジニアリングが不可分であるプロダクト開発において、生産性を向上するための手段**」。デザイナーは各開発チームに所属する「開発者」であり、横断デザインチームが全プロダクトを見る体制ではない——デザイン業務だけの生産性向上は部分最適にしかならない
- 起源はデザイナー4名時代の危機感: スケールすると同期的な共有では認識のずれを埋めるコストが増える。「**非同期的に認識を揃える手段がなければ開発の障害になる**」
- 「**妥当な意思決定を早めるための補助線であって、法律ではない**」——“デザインシステム警察”は存在せず、従うかは開発チームの判断。提供スピードが犠牲になるなら「後から反映」「対応しない」も許される
- **オーナー不在**: 特定の誰かがオーナーシップを握らず、各担当者が課題ベースで検討・議論を主導して反映する。「強い気持ちで共通認識や概念を一般化しドキュメントにする、極めて地道な努力」
- 機能を価値ある最小単位で段階的にリリースする開発スタイルに合わせ、デザインシステムも最小要素から積み上げた（2020年6月に基本要素のみで公開 → デザイン原則の言語化 → a11y チェックリスト・ライティングガイド → Figma 版 SmartHR UI 一般公開 → ユーザビリティテストの手引き）。「最初から効果は出づらいが、後からどんどん効いてくる長期投資」
- 運用コストを下げる仕組み: ガイドラインの**テンプレート**（構成・書く内容の補足つき）、GitHub PR でのレビュー（外部からの PR も歓迎）、Figma の**ブランチ機能**による安全なライブラリ更新（手順自体もガイド公開——「特定の誰かがメンテナンスし続ける体制から自律自走への移行に役立つ」）、週次共有・Slack・SNS での更新周知
- **モブデザイン**: 開発チーム全員が同じ Figma に入り UI・文言のパターン出しを検討する。デザインの根拠が言語化され、非デザイナーがデザインを自分ごと化し、職能横断の観点が入る（文言の工夫で実装の条件分岐を減らせた例）。Slack の「用字用語リクエスト」ワークフローで UX ライターに非同期相談もできる

## SmartHR UI — 兼任が生むエコシステム

以下すべて出典: [[SmartHR UI を中心としたエコシステムのすすめ - SmartHR Tech Blog]]（uknmr）

- SmartHR UI は OSS の React コンポーネントライブラリ。目的の再定義: 「UI を揃える」は共通コンポーネント集が誕生した瞬間に達成されており、手入れし続ける理由は「**SmartHR というプロダクトの開発を最速で進めるため**」
- 開発姿勢は「**必要なものを必要なだけ作る**」——「隅々まで思想が行き届いた設計は美しいが、実際に開発で使われるかどうかは別問題」
- 4年以上**有志の兼任**で開発。各自が異なるプロダクトで SmartHR UI を使っているからこそ、週1時間の定例で「何をどんな場面でどう使い、何が課題か」を話せる。「課題感を感じている張本人が速度を保ったまま開発できる。専任チームなら課題感を伝えるだけで労力と時間を失う」（専任には固執せず、全体価値が上がるなら専任もあり）
- **エコシステム**: SmartHR UI ⇄ Design System ⇄ 数十の内部プロダクト＋グループ会社（Nstock・AIRVISA）＋サードパーティ（SmartHR Plus）。全プロダクトが同じコンポーネントを使うため、1つの課題解決が全体へ伝搬する——「たった1行の変更が、巡り巡って日本の社会を支えるかもしれない」。**貢献の第一歩は「使うこと」**
- 貢献の実践: 各プロダクトが `ui/index.ts` で SmartHR UI の使用を一元管理し、修正版コンポーネントを一時的に差し込んで「いつでも SmartHR UI への出荷を狙える」状態を保つ／課題を「SmartHR UI のもの」ではなく「発生したプロダクトのもの」としてスクラムに載せる
- **スマパタ**（SmartHR Patterns）: 頻出 UI の実装パターンを実コードと共に集めて展開する取り組み。コードと Storybook を公開

## ブランドデザイン文脈の運用 — 「かき集め」と WIP の精神

以下すべて出典: [[「デザイナー以外にも、もっと血肉として使ってもらいたい」　SmartHRにおける、デザインシステムの理想と課題]]（logmi パネル 2022、samemaru・sekig）

- 立ち上げの経緯: SmartHR UI は「スタートアップとしてカラーリングを揃えた」程度でブランドと一貫した思想はなく、「ブランドとして根拠のある見た目にしたい」という課題から samemaru がプロダクトデザイナーから部署異動して立ち上げを主導。2020年6月に最低限のロゴ・色を定義して公開し、2022年1月にサイトをリニューアル
- 運用体制の実態: コミュニケーションデザイン側は samemaru＋sekig＋アシスタント1名がメインで「運営自体は基本的に1人」「1人になりがち」。横断組織として対象領域が広く、DS に割けるリソースを「**かき集めながら運用**」（協力が得られないのではなく、全タッチポイント担当ゆえの構造）
- 「まずやる」施策ドリブン: 丁寧に設計を作っている間に状況が変わるフェーズのため、実利を伴うものを先に用意する。**WIP の精神**——書きかけでも載せて使ってもらい、改善のフィードバックを回すことを最重要視する
- 2022年サイトリニューアル: ビジネスサイド（営業資料のリソース利用）などステークホルダーが増え、「技術文書的な体だけだと利用者のニーズに添えきれない」仮説から、非技術者にも価値が分かるトップページ（アセットのアウトプット画像が差し替わる GOTCHA! ボタン）・サムネイル入りインデックス・問い合わせ先や規約の一元化・「コンセプト」というオンボーディングページを整備
- 到達度の自己評価は「20点」（低さではなく進捗の意味）: 「デザインシステムという名前が付いていることで『デザイナーのもの』と認識される」——残り80点は浸透であり、「**もっと血肉として使ってもらいたい**」
- 姿勢: 「デザインを推進する・統括するというより、**いかにみんなでデザインをやるかに注力する**マインドセット」（sekig、コ・デザイン）。putchom はこれを「デザインシステムに関わる人を巻き込むための**メタ的なコミュニケーションデザイン**」と評した——思想や「なんで作っているの？」があることで周りを巻き込める
