ジュニアとミドルはソフトスキル多めなのでフロントエンドエンジニアに限らなそうです

- 期待役割 … 該当ステップ内での TO BE
- できてほしい … 該当ステップ内での WANT (🔐は次ステップへ進む上では MUST)
- 次のステップへの期待 … 次のステップへ進む上での MUST
- 指示された小さいタスクをこなすことができる 
    - ~3人日くらいの影響範囲の閉じたタスクを想定
    - 仕様が決まっている、あるいは不明な場合は質問できる
- 実装するだけではない視点に立ってほしい 
    - 長期的にメンテナンスをすることを意識する
    - チームであることを意識する 
        - コミットをでかくしすぎない
        - PullReqをでかくしすぎない
- 自立的に業務に取り組むことができる
- 特定の機能の開発を主導することができる 
    - 自身の書くコードの影響範囲を理解することができる
- 小規模なタスクについて、自立的に見積もりから実装までを行える 
    - 見積もり時点での不明瞭点を早めに解消するように動ける
- 問題が起こり得ると感じたとき、適切にエスカレーションできる 
    - 進捗に不安がある場合に早めに報告できる
- コード中の課題に対して認識をし、自分なりの改善意見を持っている 
    - 先々の実装に影響しそうな箇所の目星が付く
    - リファクタ検討対象に対して、どのようにリファクタを進めるかを提案できる
- 既存の実装の意図を理解し、自分の意志を持ってコードを書ける 
    - 既存コードの良し悪しを判断せず、踏襲したコードを書いてしまわない
- HTTP リクエストがどのように行われているかを自分なりの言葉で説明できる
- 懸念すべきセキュリティリスクについて自分なりの言葉で説明できる
- 再レンダリングは何によって起こり何が起きているのかを自分の言葉で説明できる
- 非同期処理とは何が行われているかを自分の言葉で説明できる
- アーキテクチャ論に対して自分の意見を持っている
- 静的型のコストと有用性について自分の意見を持っている
- 根拠と意図を明確にした上で技術選定できる 
    - 技術選定の立場にない場合でも、現状のスタックの妥当性について説明できる
- 無根拠に提案しない、無根拠な意見を鵜呑みにしない 
    - Facebook が出しているので recoil は大丈夫です！とか言わない
    - ○○が良いと言っていたので、を理由にしない(自分で確かめて判断する)
    - 歴史的経緯や研究結果、あるいは原典にない、第三者の創作した概念を鵜呑みにしない
    - 権威のある概念でも、その考案に至った歴史的背景を現状と比較して判断できる
- ハードスキルを用いてプロジェクトの技術的意思決定を行う
- 継続的開発を見越した設計とリファクタリングの計画
- ビルド環境についての知識 
    - bundle ツールの違いがわかる(no bundle tool など)
    - chunk や minify 等の最適化ができる
    - 動作対象ブラウザを減らすことでバンドルサイズを削減できる
- パフォーマンスチューニング 
    - 早すぎた最適化でないかの判断ができる
    - 推測ではなく計測によってチューニングの意思決定ができる
- ソフトスキル的観点から継続的デリバリ関連の意思決定を行う
- リリースの延期を判断できる 
    - プロダクトチームの現状を踏まえ、必要に応じて要求 QCD を断ることができる
- 開発リソースの過不足を判断できる 
    - 要求 QCD に合わせリソースの調整を外部に働きかけることができる
- プロダクトの健全性を判断できる 
    - 要求 QCD とメンバーのスキルレベルや現在のコードベースの品質が釣り合っているかを判断できる
