# **この達成基準は、どうなっていたらクリアと言えるのか？**

デザイナー

- ユーザーが利用時に、機能が予測可能であることを保証する
    - フォーカスを受け取ったときにイベントを起動することのできるすべてのコンポーネントは、コンテキストを変化させてはならない
        - コンテキストの変化が予期せず起こる可能性を少なくすることによって、視覚障害、認知能力の低下、及び運動障害のある利用者に役立つ
        - コンポーネントがフォーカスを受け取った時に起きるコンテキストの変更の  例
![](https://pf-emoji-service--cdn.us-east-1.prod.public.atl-paas.net/standard/caa27a19-fc09-4452-b2b4-a301552fd69c/64x64/1f196.png)
            - フォームが自動的に送信される
            - 新しいウィンドウを開く
            - フォーカスが別のコンポーネントに変更される
- フォーカスはキーボード操作（例: コントロールにタブ移動する）又はマウス操作（例: テキストフィールドをクリックする）のいずれかを介してコントロールに移動させてもよい
    - スクリプトがこの動作を実装しない限り、コントロール上にマウスを移動しても、フォーカスは移動しない
    - 順番にコンテキストの変更を開始することのある一部の種類のコントロールでは、コントロールをクリックするとそのコントロール (例: ボタン) もアクティブにする場合がある

: 他ページに解説

- コンポーネント（この文脈では、としての補足）
    - ユーザインターフェース、ユーザインタフェース要素
    - ユーザインターフェースコンポーネント
        - コンテンツの一部分で、特定の機能を実現するための単一のコントロールとして利用者が知覚するもの
            - 複数のユーザインタフェース コンポーネントが、単一のプログラム要素で実装されることもある
                - ここでいう「コンポーネント」は、プログラムの手法と結びついたものではなく、利用者が別々のコントロールとして知覚するものを指す
            - フォーム要素、リンクだけでなく、スクリプトで生成されるコンポーネントが含まれる
        - アプレットには、コンテンツ内を行単位、ページ単位、又はランダムアクセスで移動するために用いられる「コントロール」がある
            - これらには、いずれも名前 (name) を割り当て、個別に設定できるようにする必要があるため、それぞれが「ユーザインタフェース コンポーネント」となる
- 支援技術：[1.3.1 情報及び関係性［A］ | 重要ワード](https://chatwork.atlassian.net/wiki/spaces/BRDG/pages/3646619782/1.3.1+A#%E9%87%8D%E8%A6%81%E3%83%AF%E3%83%BC%E3%83%89)
![](https://pf-emoji-service--cdn.us-east-1.prod.public.atl-paas.net/atlassian/check_mark_64.png)
    - この達成基準の文脈で重要な支援技術は以下
        - 画面拡大ソフト及びその他の視覚的な表示に関する支援技術
        - スクリーンリーダー
        - 音声変換ソフトウェア
        - 音声認識ソフトウェア
        - 代替キーボード
        - 代替ポインティングデバイス
- コンテキストの変化 (changes of context)
    - 大きな変化で、利用者が気づかないと、ウェブページ全体を一度に見ることのできない利用者を混乱させる恐れのあるもの
        - 以下の変化
            1. ユーザエージェント
            2. ビューポート
            3. フォーカス
            4. ウェブページの意味を変えるコンテンツ
        - 新しいウィンドウを開くこと、フォーカスを異なるコンポーネントへ移動させること、新しいウェブページへ移動すること（新しいウェブページへ移動したかのように思わせてしまうことも含む）、又はウェブページの内容を大きく再配置することなど
    - コンテンツの変化が、必ずコンテキストの変化になるとはかぎらない
        - アウトラインの展開、動的なメニュー、又はタブの切替などのコンテンツの変化は、それが上記のいずれか（例: フォーカス）を変更しないかぎり、状況を変化させるとは限らない

# **どう実装したらこの達成基準を守れるか？**

エンジニア

- 「〇〇をやりましょう」ではなく「〇〇をやらないようにしましょう」という内容なので、これといった実装方法は無し
- コンテキストの変化を引き起こす場合、`focus`イベントではなくボタンのクリックやキーの押下によって発火するように実装すれば良い

### リンクを別タブ / 別ウィンドウで開く場合

- 達成する上で必須ではないが、コンテンツをよりアクセシブルにするために、次の対応を検討することが望ましい
    - 対応することでコンテキストの変化を抑えられる / 変化がわかりやすくなる

### 必要なときにのみリンク先を新しいウィンドウ及びタブで開く

> 一般的に、新しいウィンドウやタブを開かないほうがよい。なぜなら、特に視覚的なコンテンツを知覚するのに困難を伴う利用者をはじめ、利用者にとっては混乱の原因となりうるからである。

- らしい
- とはいえ、アプリケーションから別ページに遷移する際は別タブで開きたい
    - おそらくWebページ前提の記述？
- 新しいウィンドウやタブを開利用者がセキュアなサイトにログインしていて、そのサイト外にあるページへのリンクをたどっていくとログインした状態が打ち切られてしまうくことが望ましい状況
    - フォームの入力のような、マルチステップのワークフローを著しく中断させることになる場合
        - ヘルプの説明文のような文脈依存の情報を含むページを開く
        - カレンダーベースのデートピッカー (日付選択) のようなフォーム入力代替手段を開く
            - 「同じウィンドウ内で開くと、入力中のデータが失われるから」らしい
            - 新しいウィンドウやタブでデートピッカーを開く…？
            - ポップアップを新しいウィンドウとして扱っている？
    - サイト外にあるページへのリンクをたどっていくとログインした状態が打ち切られてしまう場合
        - 外部へのリンクを別のウィンドウで開くことによって、利用者は元のウィンドウでログインした状態を保ちながら関連するリソースにアクセスすることができるようになる

### 新しいウィンドウを開くときに、利用者へ事前に知らせる

> リンクを動作させたときに自動的に新しいウィンドウを開くことは、もし事前にそのことを知らせていなければ、視覚的なコンテンツを知覚するのに困難を伴う利用者や認知障害のある利用者が混乱する原因となりうる。

- 利点
    - 事前に知らせることによって、利用者は現在のウィンドウから離れるかどうかを判断できる
    - 新しいウィンドウを開くことを選んだ場合にも、元のウィンドウに戻りやすくなる
    - ブラウザの [戻る] ボタンが使えないこと及び、直前まで自分がいた場所を見つけるためには元のウィンドウに戻らなければならないことを利用者が理解する手助けになる
- 実装
    - コントロールを説明するテキストに含める
        - `<a href="knitting.html" target="_blank"> All about Knitting (opens in new window)
</a>`
    - CSS を用いて、新しいウィンドウが開く前にツールチップを出す
        - [https://www.w3.org/WAI/WCAG21/working-examples/css-new-window-warn/](https://www.w3.org/WAI/WCAG21/working-examples/css-new-window-warn/)
        - マークアップ上存在しているものをCSSで非表示にしているので、スクリーンリーダーでも問題なく認識できる
        - `<a target="_blank" class="info" href="http://example.com/popup_advisory_technique.html"> <strong>External link</strong> <span>Opens a new window</span>
</a>`
