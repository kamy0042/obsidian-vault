# **この達成基準は、どうなっていたらクリアと言えるのか？**

デザイナー

- 視覚的に伝えられている情報及び関係性を、視覚情報以外の手段でも同様に得られる必要がある
    - 画面上の配置において、位置関係に依存しない表現をする
        - 右の図は、という表現は状況によっては下になったりする
    - 色を用いてもいいが、色以外でも情報を得られるようにする
- 視覚情報による情報の区別・有意差を、マークアップでも同等に（齟齬なく）表現できている必要がある
    - HTMLの標準「マークアップ」とデザインとの一致が必要であるため、マークアップ側のみに責任があるわけではなく、デザイン側でもマークアップの理解と構造化が必要
        - 見た目上にも一定の文書構造がある（見出しらしさ、段落っぽさ、リスト構造、特殊記述、テーブル形状……などの
    - `:before`や`:after`を利用して付加するような装飾にも注意が必要で、情報にアクセスできない場合がある
        - 意味を理解するために必要な情報にはきちんと意味を付加する必要がある
- 誤ったマークアップは使わない
    - 意味のあるタグ（`pre`など）を`div`のように利用してしまう
- 標準的なマークアップだけで解決できないことも、工夫で担保する
    - 例えば、赤い文字で（目立たせて）価格を提示している等の場合、スクリーンリーダーや点字ディスプレイなどでは「赤色である」という情報は得られないものの、価格の前に通貨表示を記載することで価格の情報であることを得ることができる
- そうはいっても、基本的にはマークアップで情報提供ができる場合には、マークアップ側で解決することが必要
    - マークアップできないものに飲み、テキストで補足することを求められている
    - ユーザーエージェントが、個々のユーザーのニーズに応じてコンテンツに適応できるようにすることが主目的
- ビジュアル化されていない情報をマークアップ「のみで」カバーするケースもある
    - フォーム（text field類のみならずcheckboxなども含む）に対しラベルを付け、支援技術が解釈可能になる
    - （HTML以外の）文書の書式マークアップが、標準書式になっており、プログラム側が読み取り可能になる

# **どう実装したらこの達成基準を守れるか？**

エンジニア

- 視覚的、聴覚的な体裁によって暗に伝えられている情報や関係性を、コンテンツの利用方法が変わったときにも同様に担保する必要がある。それを実現するために、情報及び関係性をプログラム側が解釈できるようにセマンテックな構造を提供すれば良い

### HTML

CSSによる表現、レイアウトによって情報やその関係性を表現した場合、スクリーンリーダーの利用者が知覚できなくなる。それを防ぐためにセマンティックなマークアップが必要となる

- 見出しに`hタグ`を用いる
- リストやリンクのグループに`ul,ol,dl`を用いる
    - リンクのグループをリスト化することで、スクリーンリーダーによるナビゲートが可能になる
- リンクのグループに`nav`を用いる
    - リスト化だけでなく`nav`を用いることでもスクリーンリーダーによるナビゲートが可能
    - 複数回用いる場合は、aria-label 又は aria-labelledby 属性を使用してナビゲーショングループを区別する。

### フォーム

- `label`によってフォームとテキストラベルを関連づける
- フォームで`label`を利用できないときに`title`属性を設定する
    - labelの代用にはなるものの、それに依存しない方が良い
        - [https://html.spec.whatwg.org/multipage/dom.html#the-title-attribute](https://html.spec.whatwg.org/multipage/dom.html#the-title-attribute)
            - > 多くのユーザーエージェントは、本仕様で要求されるアクセシブルな方法でtitle属性を公開しないため（例えば、ツールチップを表示するためにマウスなどのポインティングデバイスを必要とし、キーボードのみのユーザーや最新の電話やタブレットなどのタッチのみのユーザーは除外される）、title属性に頼ることは現在推奨されていない。
        - [https://developer.mozilla.org/ja/docs/Web/HTML/Element/input](https://developer.mozilla.org/ja/docs/Web/HTML/Element/input)
            - > すべての要素、すべての入力型で有効なグローバル属性で、所属する要素に関連するアドバイス情報を表すテキストを指定します。このような情報は、ふつうツールチップとしてユーザーに提示されますが、必ずそうとは限りません。 title は、フォームコントロールの目的の主たる説明として使用してはいけません。代わりに `<label>` 要素を使用し、その `for` 属性でフォームコントロールの `id` 属性を指すようにしてください。下記の[<u>ラベル</u>](https://developer.mozilla.org/ja/docs/Web/HTML/Element/input#%E3%83%A9%E3%83%99%E3%83%AB)を参照してください。
- 関連するフォームを`fieldset`と`legend`でグループ化する
    - 複数のフォーム＋ラベルを関連づけたい時は、`fieldset`で囲んで`legend`でそれを説明する
    - 特に、関連するラジオボタンやチェックボックスをまとめるときに重要となる
        - 複数のラジオボタンやチェックボックスに同じ`name`属性を設定している場合、１組のフォームとして扱われる
        - しかし、個々のラベルだとそのグループの文脈を十分に伝えれらないこともある
        - それを解消するために`fieldset`と`legend`を使う
    - `// この事例では、一つの質問に対して五つの解答の中からどれかを選べるテスト項目を示している。
// 解答はそれぞれラジオボタン (input type="radio") で提示されており、
// fieldset 要素に含めてある。テストの質問内容は legend 要素でタグ付けしてある。
<fieldset> <legend>The play <cite>Hamlet</cite> was written by:</legend> <input type="radio" id="shakesp" name="hamlet" checked="checked" value="a"> <label for="shakesp">William Shakespeare</label><br /> <input type="radio" id="kipling" name="hamlet" value="b"> <label for="kipling">Rudyard Kipling</label><br /> <input type="radio" id="gbshaw" name="hamlet" value="c"> <label for="gbshaw">George Bernard Shaw</label><br /> <input type="radio" id="hem" name="hamlet" value="d"> <label for="hem">Ernest Hemingway</label><br /> <input type="radio" id="dickens" name="hamlet" value="e"> <label for="dickens">Charles Dickens</label>
</fieldset>`
- `optgroup`によって`select`内の`option`をグループ化する
    - セレクトボックスの中に複数の選択肢グループが存在するときは`optgroup`によってグループ化できる
    - `optgroup`を入れ子にすることはできない
        - 先述された、「デザイナーもマークアップの理解と構造化が必要」というやつ
    - `optgroup` が提供するグループ分け情報をスクリーンリーダーが読み上げなくても理解可能なように `option` のラベルを定義するとよい。

### テーブル

- 表形式の情報をマークアップするために`table`を用いる
    - `caption`によってデータテーブルとキャプションを関連づける
    - `summary`によって概要をマークアップする
    - `scope`属性によって見出しセルとデータセルを関連づける
        - 下記のようなヘッダーが最初の行や列にない単純なデータテーブルの場合に推奨されている
            - `td` でマークアップしてあるデータセルが、行見出し又は列見出しとしても機能する場合。
            - `th` の代わりに `td` で見出しセルをマークアップしている場合
                - `th` の表示特性を避けるために `td` でマークアップすることがある。
        - `<table border="1"> <caption>Contact Information</caption> <tr> <td></td> <th scope="col">Name</th> <th scope="col">Phone#</th> <th scope="col">Fax#</th> <th scope="col">City</th> </tr><tr> <td>1.</td> <th scope="row">Joel Garner</th> <td>412-212-5421</td> <td>412-212-5400</td> <td>Pittsburgh</td> </tr><tr> <td>2.</td> <th scope="row">Clive Lloyd</th> <td>410-306-1420</td> <td>410-306-5400</td> <td>Baltimore</td> </tr><tr> <td>3.</td> <th scope="row">Gordon Greenidge</th> <td>281-564-6720</td> <td>281-511-6600</td> <td>Houston</td> </tr>
</table>`
    - データセルを見出しセルと関連付けるために、`id` 属性及び `headers` 属性を使用する
        - データセルを二つ以上の行見出し及び／又は列見出しに関連付ける場合に利用する
        - `th`のみ、または `th` に `scope` 属性を付けただけでは、データセルと見出しセルの関係が複雑すぎて定義できない場合でも、スクリーンリーダーは各データセルと関連付けられている見出しセルを読み上げることができる
        - `<table> <tr> <th rowspan="2" id="h">Homework</th> <th colspan="3" id="e">Exams</th> <th colspan="3" id="p">Projects</th> </tr> <tr> <th id="e1" headers="e">1</th> <th id="e2" headers="e">2</th> <th id="ef" headers="e">Final</th> <th id="p1" headers="p">1</th> <th id="p2" headers="p">2</th> <th id="pf" headers="p">Final</th> </tr> <tr> <td headers="h">15%</td> <td headers="e e1">15%</td> <td headers="e e2">15%</td> <td headers="e ef">20%</td> <td headers="p p1">10%</td> <td headers="p p2">10%</td> <td headers="p pf">15%</td> </tr> </table>`

### WAI-ARIA

- 基本的には、WAI-ARIAではなくセマンティックなHTMLを優先するべき
    - ARIA無しのほうが、悪いARIAよりも良い [https://waic.jp/translations/2019/NOTE-wai-aria-practices-1.1-20190207/#no_aria_better_bad_aria](https://waic.jp/translations/2019/NOTE-wai-aria-practices-1.1-20190207/#no_aria_better_bad_aria)
        - あくまでもroleを与えるだけであって、そのroleに期待される振る舞いをするわけではない
        - そのroleに準じた振る舞いが無い場合、特にスクリーンリーダーやキーボード操作時に混乱を生む原因となる
- アイコンフォントを意味的に識別するために role="img" を使用する
- ページのリージョンを特定するために ARIA ランドマークを使用する
    - ウェブページのセクションに対して、プログラムによるアクセスを提供する
    - banner: ページの主見出し又は内部タイトルを含む領域。
    - complementary: 主要コンテンツをサポートしているが、独立しかつ意味のある、文書の任意のセクション。
    - contentinfo: 著作権やプライバシーに関する声明へのリンクなど、親文書に関する情報を含む領域。
    - form: フォーム関連要素のコレクションを表す文書の領域であり、その一部は編集可能な、処理するためにサーバーに送信可能な値を表すことができる。
    - main: 文書における主要コンテンツ。ほとんどの場合において、一つのページは一つのみの role="main" を持つ。
    - navigation: 文書内の、又は関連する文書へのナビゲートに適したリンクのコレクション。
    - search: ウェブ文書の検索ツール。
    - `<div role="complementary" aria-labelledby="hdr1"> <h1 id="hdr1"> Top News Stories ... </h1>
</div>`
- 見出しに`role=heading`を使用する
- リージョンとランドマークに名前 (name) を付けるために、`aria-labelledby` を使用する
    - ランドマークとしてマークアップされたページ内のセクションと、そのセクションを分類するページ内のテキストを関連付ける
- ユーザインターフェース コントロール（フォーム等）の名前 (name) を提供するために、`aria-labelledby` を使用する
    - labelが持つ振る舞いは自前で再実装する必要がある
    - > 注: `label` 要素を使うことには多くの理由がある。利用者が `label` 要素のテキストをクリックすれば、対応するフォームフィールドがフォーカスを受け取るため、器用さの問題を持つ人に対してクリックターゲットを大きくすることができる。また、`label` 要素は常にアクセシビリティ API を介して公開される。[https://waic.jp/translations/WCAG21/Techniques/aria/ARIA16](https://waic.jp/translations/WCAG21/Techniques/aria/ARIA16)
- フォームをグルーピングロールによってグループ化する
    - role="group" もしくは role="radiogroup"
    - グループは `aria-labelledby` を使用してラベル付けできる
- `role="region"`によってページのセクションを特定できるようにする
    - 他のランドマークロールよりも汎用的な指定となる
        - 特定のランドマークを利用できないときに用いるべき
    - aria-labelledbyやaria-labelによって名前をつける必要がある
    - 使いすぎると、スクリーンリーダーの利用者にとって過度に冗長なページとなるので要注意
