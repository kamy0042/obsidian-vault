# **この達成基準は、どうなっていたらクリアと言えるのか？**

デザイナー

- 利用者側が、リンクを辿りたいかどうかを決められる
    - 関心のないリンクをスキップできる
    - 間違ったクリックによる無駄なキーストロークを回避する
    - 認知に制約のある人が、関心のないコンテンツへのナビゲーションの複数手段によって混乱することがなくなる
    - 視覚障害のある人が、リンクの文脈を探ることによって、リンクの目的を判断できるようになる
- 可能な限り、追加コンテンツを必要とせずに、リンクの目的を特定するリンクテキストを提供する
    - 支援技術はリンク一覧を利用者に提供することができるため、一覧から選択したい利用者の助けになる
    - 意味のあるリンクは、ページを理解するために複雑な戦略を必要とせずに選択に役立つ
- リンクのテキストまたは、リンクに関連付けられたテキストは、リンクの目的を説明することを意味する
    - リンクが利用者を文書またはアプリケーションへ導く場合、その名前はリンクの目的を表すものとして十分
        - ただし、文書またはアプリケーション名を使用することが必須という意味ではない
- [2.4.2 ページタイトル［A］](https://chatwork.atlassian.net/wiki/spaces/BRDG/pages/3877077620) で扱ったページタイトルも、目的を説明するのに十分
    - リンクとページタイトルが一致するまたは極めて似ていることは、グッドプラクティス
        - リンクのクリックと着地ページとの連続性を提供できる
- 場合により、リンクからフォーカスを移動させずにリンクの目的を特定させる
    - リンクと同じ文、段落、リスト項目、またはテーブルのセル、データテーブル内にあるリンクのテーブル見出しセル、リンクの説明を配置することで達成可能
    - あるいは、ARIA技術を用いて追加テキストをリンクに関連付ける
- コンテキストは、リンクの前にある場合に最も有用となる
    - 上から下に読むことを前提とする場合（スクリーンリーダーはとくに）リンクテキストが曖昧な場合にも先に説明がなされていることで理解を助けられる
- 同じ宛先へのリンクは、一貫したテキストがあることがベストプラクティスになる
    - [達成基準 3.2.4: 一貫した識別性を理解する](https://waic.jp/translations/WCAG21/Understanding/consistent-identification.html) で要件となる
![](https://waic.jp/favicon.ico)
- 適合している代替版へのリンクにおけるベストプラクティスは、その適合している代替版へのリンクテキストが、リンク先のページがよりアクセシブルなバージョンであることをリンクテキストの中で示すこと

## **重要ワード**

デザイナー エンジニア

![](https://pf-emoji-service--cdn.us-east-1.prod.public.atl-paas.net/atlassian/check_mark_64.png)

: 他ページに解説

- アクセシビリティサポーテッド
    - 利用者の支援技術だけでなく、ブラウザ及びその他のユーザエージェントにあるアクセシビリティ機能でサポートされていること
    - あるウェブコンテンツ技術 (又は、ある技術の機能) のアクセシビリティ サポーテッドな使用方法とみなされるためには、そのウェブコンテンツ技術 (又は機能) について、次の 1.と 2.の両方が満たされていなければならない
        1. そのウェブコンテンツ技術の使用方法が、利用者の支援技術によりサポートされていなければならない
        2. そのウェブコンテンツ技術には、利用者が入手できるアクセシビリティ サポーテッドなユーザエージェントがなければならない
    - 参考：[https://waic.jp/guideline/as/](https://waic.jp/guideline/as/)
        - アクセシビリティサポーテッド情報として、日夜調査が行われています（調査のためのWGがWAICには存在します）
- ほとんどの利用者にとって曖昧
    - リンク、及びリンクと同時に利用者に提供されているウェブページのどの情報からも、そのリンクの目的を判断できない
        - 障害関係ない
- 適合している代替版
    - 以下の事項を満たす版のことを指す
        1. 指定されたレベルで適合しており、かつ
        2. 同じ情報及び機能のすべてを同一の自然言語で提供しており、かつ
        3. 不適合コンテンツと同時に更新されていて、かつ
        4. 以下に挙げる事項のうち少なくとも一つを満たしていること:
            1. アクセシビリティサポーテッドな メカニズムを用いて、 不適合ページから適合版へ到達できる。もしくは、
            2. 不適合版に到達できるのは、適合版からのみである。
            3. 不適合版に到達できるのは、適合版に到達するメカニズムも提供している適合ページからのみである。
- 自然言語
    - 人間とコミュニケーションをとるために話される、書かれる、又は (視覚的もしくは触覚的な手段で) 手話にされる言語
- 支援技術：[https://chatwork.atlassian.net/wiki/spaces/BRDG/pages/3646619782#%E9%87%8D%E8%A6%81%E3%83%AF%E3%83%BC%E3%83%89](https://chatwork.atlassian.net/wiki/spaces/BRDG/pages/3646619782#%E9%87%8D%E8%A6%81%E3%83%AF%E3%83%BC%E3%83%89)
![](https://pf-emoji-service--cdn.us-east-1.prod.public.atl-paas.net/atlassian/check_mark_64.png)
    - この基準でより関係する支援技術は
        - 画面拡大ソフト、その他視覚的な表示に関する支援技術
        - スクリーンリーダー
        - 音声変換ソフトウェア
        - 音声認識ソフトウェア
        - 代替きーぼーど
        - 代替ポインティングデバイス

## **例外**

デザイナー エンジニア

- リンクの目的をウェブページ上にある情報からは判断できないリンク
    - そのような状況では、障害のある利用者が不利な立場にあるわけではない
        - リンクの目的を理解するために追加入手可能な文脈が一切ない
    - しかし、リンクの目的を解釈するために使用できるウェブページ上で利用可能ないかなるコンテキストの量であっても、達成基準を満たすためのリンクテキストで利用可能にされる、又はリンクとプログラム的に関連付けられなければならない
- リンクの目的が不明又は曖昧になることが想定できる状況もありえる
    - ゲームのドア 1、ドア 2、そしてドア 3 としてのみ識別されるリンク
        - リンクの目的がすべての利用者に対するサスペンスを引き起こすことにあるので、このリンクテキストは十分

# **どう実装したらこの達成基準を守れるか？**

エンジニア

- 基本的にはコンテンツの構成やリンクテキストによって解決することになる
- その上で、リンクテキストの操作やリンクと他のテキストの関連付けについて補足する
- ちなみに、`title`属性に補足情報を追加するやり方は非推奨
    - title 属性へのアクセス方法について、ユーザエージェントごとにサポートが大きく異なるため

### リンクテキストの差し替え

- リンクテキストにそのコンテキストを含ませた場合、テキストが冗長になることもある
- それによって使い勝手が悪化すると感じる利用者もいる
    - > WCAG ワーキンググループに支援技術の利用者から寄せられたフィードバックでも、どちらを好むかは意見が分かれている
- リンクテキストを差し替える方法を提供すれば、利用者は最適なアプローチを自分で選べる
    - 完全なリンクテキストを備える代わりにテキストが長いバージョン
    - テキストが短い代わりにリンク前後のコンテキストで目的を読み取る必要があるバージョン

### ページ先頭近くに、リンクテキストを変更するコントロールを提供する

- リンクテキストにコンテキストを含ませた代替版へ利用者を誘導する
- 代替版へ誘導するコントロールがリンクである場合、リンクテキストにその目的を含ませる
- この設定をサーバーサイドのデータもしくはCookieに保存すれば、再設定の必要が無くなる
    - それが望ましい場合もある

### スクリプトでリンクテキストを差し替える

- JSによってリンクテキストを拡張する
    - そのためのコントロールはページの先頭近くに配置する必要がある
- こちらも同じく、サーバーサイドのデータもしくはCookieに保存すれば再設定の必要が無くなる
- [https://www.w3.org/WAI/WCAG21/working-examples/script-expand-links/](https://www.w3.org/WAI/WCAG21/working-examples/script-expand-links/)

### リンクテキストの一部を非表示

- 機能を説明するテキストをリンクに追加する
- 追加したテキストをCSSで非表示にする
- それにより、リンクテキストが冗長になることを避けつつリンクの目的を十分に説明できる

### CSSの例

```plain text
.visually-hidden {
   clip-path: inset(100%);
   clip: rect(1px, 1px, 1px, 1px);
   height: 1px;
   overflow: hidden;
   position: absolute;
   white-space: nowrap;
   width: 1px;
}
```

- これを非表示にしたいテキストに設定すると、`overflow:hidden` と指定した1pxのボックス内に配置される
- 画面上には表示されなくなるが、スクリーンリーダーや点字ディスプレイなどの支援技術に対してはアクセシブルな状態を保持できる
- 支援技術に対してテキストを隠さないように注意
    - 意図せぬ影響が出る恐れがあるため、 `visibility:hidden` や `display:none`の使用は避ける
- 方法は、スクリーンリーダーの利用者や企業のウェブコンテンツ制作者の一部によって支持されている
    - 一部のウェブサイトにおいては効果があることも立証されている
- スクリーンリーダーの利用者やアクセシビリティの専門家の中には、一般的な達成方法としてこれを推奨していない人もいる
    - 説明が過度に冗長になり、経験豊富なスクリーン・リーダー・ユーザーが冗長さをコントロールする能力が制限される可能性がある
        - スクリーンリーダーの何らかの機能を阻害する？
- AG ワーキンググループは、隠しテキストエリアに繰り返しコンテンツがないウェブページに対して、この達成方法は有用であると考えている

### リンクと他のテキストの関連付け

- ページ上のテキストをWAI-ARIAによってリンクと関連づける
- それにより、そのテキストがリンクの説明だとブラウザや支援技術に解釈させる

### WAI-ARIAによる実装

- `aria-labelledby` 属性
    - `<h2 id="headline">Storms hit east coast</h2>
<a id="p123" href="news.html" aria-labelledby="p123 headline">Read more...</a></p>`
    - この場合、スクリーンリーダーは「Read more ...Stormshit east coast」と読み上げる
    - 読み上げ順序は`aria-labelledby`属性で指定した順序に従う
- `aria-label` 属性
    - `<h4>Neighborhood News</h4>
<p>Seminole tax hike: Seminole city managers are proposing a 75% increase in property taxes for the coming fiscal year. <a href="taxhike.html" aria-label="Read more about Seminole tax hike">[Read more...]</a>
</p>`
    - リンクを説明する可視要素（テキスト）がページ上に存在しない場合、`aria-label` 属性を使ってリンクにテキストラベルを付与できる
    - テキストが存在する場合は`aria-labelledby`属性を使う
    - `aria-label` テキストは、リンク内で与えられたテキストを上書きする
        - `aria-label` で使用されるテキストは、リンク内で使用されているテキストから始めることが推奨されている
        - それにより利用者間で一貫したコミュニケーションを取れるようになる

## **具体的なマークアップ方法例**

エンジニア

### リンクにコンテキストを与えるマークアップ

コンテンツの構造 = マークアップによってコンテキストを与える例をいくつか挙げる。

### リンクテキストとそれが含まれているリスト項目とを組み合わる

リンクを含んでいるリスト項目が、先祖要素であるブロックレベル要素の中で最もそのリンクに近い場合、リンクにコンテキストを与えることになる。

```plain text
<ul>
  <li>
    Check out the video report for last year's
    <a href="festival.htm">National Folk Festival</a>.
  </li>
  <li>
    <a href="listen.htm">Listen to the instruments</a>
  </li>
  <li>
    Guitar Man: George Golden talks about
    <a href="mkguitars.htm">making guitars</a>.
  </li>
</ul>
<ul>
  <li>
    <a href="tomb_raider.htm">Tomb Raider: Legend</a>
    <a href="tomb_raider_images.htm">See Images</a>
    <a href="tomb_raider.mpeg">(Download Demo)</a>
  </li>
  <li>
    <a href="fear_extraction.htm">F.E.A.R. Extraction Point</a>
    <a href="fear_extraction_images.htm">See Images</a>
    <a href="fear_extraction.mpeg">(Download Demo)</a>
  </li>
</ul>
```

### リンクテキストとそれが含まれている段落とを組み合わせる

リンクを含んでいる段落が、先祖要素であるブロックレベル要素の中で最もそのリンクに近い場合、リンクテキストだけでは不明瞭なリンクにコンテキストを与えることになる。

```plain text
<h3>The final 15</h3>
<p>Coming soon to a town near you...the final 15 in the
National Folk Festival lineup.
<a href="final15.html">[Read more...]</a>
</p>
```
