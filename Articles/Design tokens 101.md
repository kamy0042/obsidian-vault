## [UXコレクティブ](https://uxdesign.cc/?source=post_page---publication_nav-138adf9c44c-67023982f7e3---------------------------------------)

[![UXコレクティブ](https://miro.medium.com/v2/resize:fill:76:76/1*mDhF9X4VO0rCrJvWFatyxg.png)](https://uxdesign.cc/?source=post_page---post_publication_sidebar-138adf9c44c-67023982f7e3---------------------------------------)

私たちは、デザイナーは製作者であると同時に、考える人でもあると信じています。https [://linktr.ee/uxc](https://linktr.ee/uxc)

かつてWeb開発者は、すべてのスタイルデータをハードコーディングしていました。ボタンの背景色を青にする必要がある場合、ソースコードで直接背景色を指定していました。

```hs
.button { 
  background-color: blue; 
}
```

テーマレイヤーを必要とせず、頻繁な再設計も行わない小規模なシステムには有効だった。しかし、大規模な再設計が必要な場合は、この方法は苦痛を伴うものだった。

発明者

[ジナ・アン](https://medium.com/u/f5d1807b4e38?source=post_page---user_mention--67023982f7e3---------------------------------------)

[Salesforce Lightning Design System](https://www.lightningdesignsystem.com/design-tokens/) において 、デザイントークンは、色、フォント、間隔などのスタイル属性をあらかじめ定義された構造で保存するための手法です。これは、スタイルデータを直接ハードコーディングする代わりに、デザイナーや開発者が一貫性のある美しいレイアウトを構築し、迅速なデザイン変更を実現し、アプリケーションにテーマレイヤーを追加できるようにするものです。

デザイナーがFigmaを使用する場合、デザイントークンは次のように表現される可能性があります。

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*xC3D7kuog-c15wu2nXuYfw.png)

それらには、具体的かつ一般的な名前が付けられています。\`primary1\`に割り当てられた値を変更しても、意味は変わりません。

コード上では、これらのトークンは次のようになるかもしれません。

```hs
const theme = { 
  colors: { 
    primary1: "#07005B", 
    primary2: "#1D35AF", 
    secondary1: "#E34F30", 
    secondary2: "#3CA6E0", 
    secondary3: "#C17259", 
    secondary4: "#0E78B2", 
    secondary5: "#00875E", 
  }, 
};
```

これらのトークンは、私たちが利用しているスタイリングメカニズムによって読み取ることができます。例えば、\`styled-components\` で使用することができます。

```hs
import styled from “styled-components”; 
import { Button } from “@harrysforge/button”;const PrimaryButton = styled(Button)\` 
  background-color: ${( props ) => props.theme.colors.primary1}; 
\`;
```

## デザイントークンの使用レベル

私は様々なサイトで、デザイントークンの使用状況に3つの異なるレベルがあることを確認しました。

**1\. デザイントークンなし**

デザイントークンを使用していないサイトでは、スタイルデータがハードコーディングされています。スタイルデータを一元的に保存・管理する場所がありません。

**2\. 非構造化デザイントークン**

私の経験上、これはデザイントークンの使用において最も一般的なレベルです。スタイルデータは一元的に保存・管理されていますが、データ自体は一貫した方法で整理・命名されていません。

```hs
const theme = { 
  babyBlue: \`blue\`, 
};
```

**3\. 構造化設計トークン**

理想的なシナリオは、サイトに構造化されたデザイントークンが使用されている場合です。これは、デザイナーと開発者がトークンの形状と命名規則について積極的に合意している場合です。これにより、デザイナーと開発者間のコミュニケーションがより円滑になり、サイトのリデザインやテーマ変更がはるかに容易になります。

```hs
const theme = { 
  colors: { 
    primary1: “#07005B”, 
    primary2: “#1D35AF”, 
    secondary1: “#E34F30”, 
    secondary2: “#3CA6E0”, 
    secondary3: “#C17259”, 
    secondary4: “#0E78B2”, 
    secondary5: “#00875E”, 
  }, 
};
```

## 一般的なワークフロー

デザイントークンを使用することで、多くの一般的なワークフローを改善できます。デザイントークンを使用することで、デザインと開発者のエクスペリエンスが向上し、同時にビジネス価値も高まるケースは数多くあります。ここでは、こうした一般的なシナリオをいくつか取り上げ、デザイントークンを使用しないサイト、非構造化デザイントークンを使用するサイト、構造化デザイントークンを使用するサイトで、それぞれどのように異なるのかを見ていきましょう。

**1\. サイトの再設計**

**デザイントークンなし**

あるサイトのカラーパレットが主に青色だと想像してみてください。デザイナーが共有カラーライブラリをサポートしていないツールで作業していて、すべてのファイル内の青色の箇所をすべて更新したい場合、それは非常に困難でしょう。

コード面でも状況はあまり変わらないだろう。開発者は、その色がオレンジ色に変更されている箇所を示す個々のデザインファイルをすべて確認し、サイト全体でハードコードされた青色をオレンジ色に置き換える必要がある。

**非構造化デザイントークン**

次に、デザイントークンが活用されるものの、トークンには元々割り当てられた値に基づいて名前が付けられるというシナリオがあります。

```hs
const theme = { 
  colors: { 
    babyBlue: “blue”, 
  }, 
};
```

この場合、開発者は `babyBlue` オレンジ色に変更できます。

```hs
const theme = { 
  colors: { 
    babyBlue: “orange”, 
  }, 
};
```

しかし、現在のコードベースでは、このトークンを `babyBlue` オレンジ色を表すために使用しており、非常に紛らわしい状況になっています。そのため、開発者はデザイントークンの名前も変更する必要があり、それでは本来の目的が損なわれてしまいます。

**構造化設計トークン**

デザイナーがFigmaのような共有カラーライブラリをサポートするツールを使用している場合、\`primary1\`の色を青からオレンジに変更したい場合、\`primary\`の16進数コードを変更するだけで、すべてのデザインが自動的に新しい色に更新されます。

コード内では、デザイントークンは次のようになります。

```hs
const theme = { 
  colors: { 
    primary1: "blue", 
  }, 
};
```

この場合、開発者は色を `primary1` オレンジに変更するだけで、コードベース全体が自動的に適切な箇所で青色からオレンジ色に更新されます。

## 2\. デザイン／開発コラボレーション

デザイントークンには、デザイナーと開発者がスタイルを参照する際に共通の語彙を導入するという利点があり、これによりコラボレーションが向上し、やり取りの回数が減り、時間とコストの節約につながります。

- **デザイントークンがない  
	**デザイナーは静的なモックアップしか持っておらず、それらをすべて手動で更新する必要がある。コードベースにどんな色が使われているかさえ把握していない場合もある。コード側では、サイトに使われている色がデザインと一致しているかどうかを監査するのは困難だ。誰もが推測に頼らざるを得ず、UIの一貫性が失われる原因となっている。
- **非構造化デザイントークン  
	**デザイントークンは、デザイナーと開発者で異なる名前が付けられています。デザイナーは青色をblue1と呼び、開発者はbabyBlueと呼びます。変更すべき点について意思疎通を図るのは困難です。最終的には、彼らはそれを見つけ出します。
- **構造化されたデザイントークン  
	**デザイナーと開発者はどちらも青色を と呼びます `primary1` 。デザイナーがサイト全体のモックの色を更新したい場合、開発者に \`primary1\` を青からオレンジに更新するように指示するだけで済みます。

## 3\. テーマ設定

**デザイントークンなし**

私の知る限りでは、それは不可能です。

- **非構造化デザイントークン  
	**トークンに のような名前が付いている場合、 リブランディングで が赤に変わる `babyBlue` と奇妙になります。 `babyBlue`
- **構造化されたデザイントークン  
	**すべてのテーマがデザイントークンのルールに従っている限り、これは非常に簡単です。

## 4\. 一貫性のあるUIエクスペリエンス

- **デザイントークンがない。  
	**サイト全体でハードコーディングされた値を使用しているため、一貫性を維持することはほぼ不可能です。スタイルの数を制限する方法がなく、デザイナーと開発者の間で共通の言語もありません。
- **非構造化デザイントークン  
	**これはデザイントークンがないよりははるかに良いです！少なくとも開発者は適用しているスタイルの種類を把握でき、監査も非常に簡単です。
- **構造化されたデザイントークン  
	**これは理想的です。なぜなら、デザイントークンの構造は開発者とデザイナーの間で共有でき、サイトの再設計が簡単かつ一貫性のあるものになるからです。

## 共有設計トークン仕様

企業が成長するにつれて、複数のアプリケーションを同時に管理する必要が生じます。このような状況で発生する問題点のいくつかに対処するには、共通の設計トークン仕様を策定することが有効です。

共通の仕様に合意することで、企業は多くのメリットを享受できるようになります。

- テーマ設定可能なフロントエンドを標準搭載したサイト群
- 共有仕様を認識する要素を含むコンポーネントライブラリ。つまり、ボタンをブランドにドロップするだけで、デザイントークンに従って自動的にスタイルが適用されるということです。
- デザイントークンという共通言語を用いることで、デザイナーと開発者間のコラボレーションが向上する。
- Figmaからコードベースにデータを自動的に取り込み、フロントエンドのスタイルを変更できるスクリプト

ブレント・ジャクソンは、企業間でこの問題を解決することを目指した、 [Theme UI](https://theme-ui.com/) と呼ばれるオープンソースの共有スタイル仕様の開発に取り組んでいる。
