## スキル、ツール、環境をどのように整理して、拡張可能なAI設計ワークフローを構築したか。

*誰もがAIについて語っているけれど、私はどこから始めたらいいのか全く分からなかった。こうして私はツールの洪水に溺れることなく、ようやくAIの本質を理解することができた。*

![](https://miro.medium.com/v2/resize:fit:2000/format:webp/1*Z_6rX6AWI7nwz97z_HrRGw.png)

この記事を書くために、午前3時37分に起きました。

私が規律正しいからではありません。夢の中でそのことを考えていたからです。文字通り、寝ている間に文章を編集していて、目が覚めたら頭の中に一文が浮かんでいて、それが消えてしまう前に書き留めておかなければならなかったのです。

![](https://miro.medium.com/v2/resize:fit:1400/format:webp/1*LfU0u7A9bCrH7iFa69VgYA.png)

証拠

AIに対する不安は、まさに今、デザイナーたちにそんな影響を与えている。クロード・コード、カーソル、MCPサーバー、AIエージェントといった言葉を耳にし、自分もこれらを学ぶべきだと分かっている。同僚も話題にしているし、タイムラインもAI関連の投稿で溢れている。しかし、いざターミナルを開くと、まるで別の惑星に降り立ったような気分になる。週末のうちに何とか理解できるだろうと自分に言い聞かせる。ところが3週間が過ぎても、不安は募るばかりだ。心のどこかで、「 *もし自分がついていけなければ、真っ先に解雇されるだろう」という考えが頭をよぎるからだ。*

デザイナー仲間からしょっちゅう聞くのでよく分かります。「学びたいけど、時間がない」。学びたいという気持ちは確かにあります。しかし、人々を阻むのは壁なのです。そして、技術的な知識のないデザイナーにとって、その壁は確かに存在するのです。

私はプロダクトデザイナーです。普段はコードを書いて生計を立てているわけではありません。ですから、デザイン作業で初めてClaude Codeを使い始めたとき、正直言って圧倒されました。スキル、プラグイン、MCP、ターミナルコマンド、設定ファイル、シンボリックリンク、JSON設定など、どれも開発者の領域に属する概念ばかりです。どのチュートリアルも、私がシンボリックリンクが何であるかを既に知っていることを前提としていました。どのガイドも「MCPサーバーを追加するだけ」と、まるでそれが当たり前の文章であるかのように書いていました。そしてスキル自体は？あちこちに散らばっていました。デスクトップアプリにあるものもあれば、ターミナルにあるもの、手動で探さなければならないフォルダにあるものもありました。何が何に繋がっているのか、どのツールがどんな仕事をするのか、そして増えていく中でそれらをどのように整理しておけばいいのか、全く分かりませんでした。

もしあなたがデザイナーで、Claude Codeを眺めながら *「これは強力だけど、どうやってこれを全部管理すればいいのか全く分からない」* と考えているなら、まさに私も1ヶ月前はそうでした。

始める前に断っておきますが、これが唯一の正解だと主張するつもりはありません。AIツールは急速に進化しており、ここで紹介するのはあくまで現時点で私がうまくいっている方法の一例です。この記事を読む頃には、一部が時代遅れになっているかもしれません。しかし、その根底にある *考え方* 、つまりスキルをどのように整理するか、環境をどのように分割するか、設計知識をどのように構造化して拡張性を持たせるかといった部分は、今後も通用すると考えています。少なくとも、この記事が皆さんの出発点となり、どこから始めればいいのか分からず途方に暮れるような状況を避けられることを願っています。

ここでは、すべてが腑に落ちたきっかけとなったメンタルモデル、つまり構成要素、2つの環境が必要な理由、そしてそれらを整理し拡張性を保つためのスキルアーキテクチャについて説明します。

*意見は私個人のものです。*

## ステップゼロ：適切なメンタルモデルを構築する

設定を始める前に、実際に何を扱っているのかを理解しておくことが重要です。エージェント、MCP、スキル、プラグイン、プロンプトなど、多くの用語が飛び交っており、すぐに混乱してしまうかもしれません。しかし、重要なのは、まず3つの基本的な概念を理解するだけで良いということです。残りの概念は、使い続けるうちに自然と身についていきます。

こう考えてみてください。あなたの会社で全く経験のない、非常に優秀な新人デザイナーを採用したとします。そのデザイナーは頭が良く、仕事も速く、意欲的ですが、あなたの会社のデザインシステム、製品、理念、ツールについて何も知りません。彼らが実際に仕事に取り掛かれるようになるには、まず何を提供する必要があるでしょうか？

移転する必要があるのは2種類のものです。1つ目は *知識* 、つまりデザイン原則、ライブラリに存在するコンポーネント、ブランドボイスとトーンです。2つ目は *能力* 、つまり画面を批評する方法、PRDをデザインブリーフに変換する方法、FigmaでQAチェックを実行する方法などです。知識はデザイナーが頭の中に持っているもので、能力はデザイナーができることを指します *。* 優れたデザイナーにはその両方が必要です。クロードも例外ではありません。

まさにあなたが設定しようとしているのはそういうことです。

```hs
┌─────────────────────────────────────────────┐ 
│ あなた（デザイナー） │ 
│ │ 
│ 「知っておくべきこととやるべきこと」 │ 
│ │ │ 
│ ▼ │ 
│ ┌────────────────────────────────┐ │ 
│ │ 🤖 クロード │ │ 
│ │ │ │ 
│ │ スキル MCP サーバー │ │ 
│ │ （頭）（手） │ │ 
│ │ │ │ 
│ │ • 原則 • Figma │ │ 
│ │ • コンポーネント • Jira │ │ 
│ │ • 方法 • wiki │ │ 
│ │ レビュー • ... │ │ 
│ │ • 方法 │ │ 
│ │ 生成 │ │ 
│ └────────────────────────────────┘ │ 
│ │ │

```

そして、そこに至るために必要な概念はたった3つだけです。

**スキル** こそが、クロードを貴社で有能なデザイナーにするすべてです。スキルには知識（デザイン原則、コンポーネント仕様、コンテンツガイドラインなど）もあれば、能力（デザインレビューの実施方法、PRDからFigmaフレームを生成する方法、既存画面のUX問題監査方法など）もあります。このように考えてみてください。新人デザイナーが初日から「知っている」ことを期待できないことは、おそらくスキルとして身につける必要があるでしょう。

**MCPサーバー** （モデルコンテキストプロトコル）はツールへのアクセス手段です。Claudeが外部ツール（Figma、Jira、Wikiなど）と通信できるようにするコネクタのようなものです。デザイナーはあらゆる原則を暗記していても、作業を行うにはFigmaを開いておく必要があります。MCPはまさにそれ、つまりスキルに基づいて行動する「手」なのです。

**環境** とは、作業スペースのことです。デザイナーにとって重要な環境は2種類あり、それぞれ得意とする分野が異なります。まずはそこから始めましょう。

## なぜ2つの環境が必要なのか？（そして、おそらく両方が必要な理由）

セットアップの説明に入る前に、デザイナーとして毎日実際に何をしているかを考えてみてください。作図は仕事の30%程度でしょう。残りは？ PRDを読み、本当に重要なことを抽出したり、既存の画面をレビューして問題点を見つけたり、デザインの根拠を書いたり、自分の作品を原則と比較したり、ドキュメントでデザイン上の決定を主張したり、パターンを調査したり、批評を与えたり受けたり、仕様についてエンジニアと調整したりすることです。

==デザインとは、思考を要する仕事であり、時折ピクセルを生み出す仕事である。==

だから、AIツールを探していたとき、単に絵を描くだけのツールが必要だったわけではありません。 *思考を* 助けてくれるツール、そして必要に応じて絵を描いてくれるツールが必要だったのです。だからこそ、最終的に1つではなく2つの環境を作ることになったのです。

**Cowork（デスクトップアプリのUI）** は、思考作業を担います。ほとんどの人がそうであるように、端末に慣れていない人でも自然に使えるビジュアルインターフェースを備えています。私はここでFigmaのスクリーンショットからデザイン批評を行ったり、Chromeを使ってWikiページを閲覧・注釈を付けたり、デザインドキュメントやプレゼンテーションを作成したり、調査や分析を行ったりしています。私のような視覚的な思考を好む人にとって、デザイナーの1日の大部分を占める思考作業を行うには、ここがより直感的な場所なのです。

ここは私がクロードと一緒にスキルを作成する場所でもあります。つまり、AIにトレーニング教材の作成を依頼できるということです。AIに覚えさせたい内容を説明すると、AIがスキルファイルを作成してくれます。SKILL.mdファイルを一から作成する必要はありません。（詳しくは「開始方法」セクションをご覧ください。）

**Terminal Claude Codeは** Figmaとの接続を処理します。ここでは、カスタムFigmaプラグインを介してデザインシステムコンポーネントを使用してデザインを生成したり、Figmaノードを直接編集したり、Figmaデスクトップアプリへのリアルタイム接続が必要なあらゆる操作を実行したりします。

内訳は以下のとおりです。

## CoworkからFigmaへのレンダリングができないのはなぜですか？

最初は私もつまずいたので、説明しておきます。Cowork は、Mac 上のリモート VM 内で動作します。Claude がデザインを Figma にプッシュする必要がある場合、ローカル WebSocket 接続を介して Figma デスクトップ プラグインと通信します `localhost` 。しかし、VM の は `localhost` Mac の と同じではないため `localhost` 、Figma プラグインはデザイン データを受け取ることができません。

Terminal Claude CodeはMac上で直接動作し、 `localhost` Figmaと同じ環境を共有します。接続は正常に機能します。

CoworkからFigmaのスクリーンショットを撮ったり、メタデータを読み取ったりするのは問題なくできます。これらはローカル接続ではなくクラウドAPIを使用しているためです。Terminalが必要なのは、リアルタイムレンダリング（コンポーネントをFigmaにプッシュする）の場合のみです。

## 本当に重要な部分：スキルを整理して混乱させないための方法

2つの環境を設定することで接続は確立できます。しかし、私が本当に悩んだのは、 *スキルをどのように整理すれば拡張性を確保できるかという点です。*

初期の頃は、部品に関するスキル、レビューに関するスキル、トーン・オブ・ボイスに関するスキルなど、あらゆるスキルを無造作に持ち合わせていました。スキル同士が重複したり、矛盾したりすることもありました。クロードは間違ったスキルを読み込んだり、3つ同時に読み込んで混乱したりしていました。まさにカオスでした。

解決策は、スキルを設計システムのように扱うことだった。つまり、階層構造、明確な責任分担、明示的な依存関係を持つシステムだ。何度か試行錯誤を重ねた結果、3層構造のアーキテクチャにたどり着いた。

## レイヤー1：参照スキル（知識）

参照スキルは知識を保持するものであり、それ自体で作業を行うわけではありません。必要に応じて、能力スキルによって知識が蓄積されます。

これらを2つのカテゴリーに分けました。

**一般的な参考資料作成スキルは** 、すべてのプロジェクトで共通して求められます。

- **デザイン原則** ――デザインシステムの背後にある「理由」。評価フレームワーク、視覚的階層ルール、デザイン哲学。これこそが、クロードに *判断力* を養わせるスキルである。
- **コンポーネントとトークンの仕様** ― コンポーネント、トークン、アイコンに関する唯一の信頼できる情報源。レンダリングツールがデザインを生成する際に読み込む情報です。
- **コンテンツ戦略** ― トーンと表現のルール、UI要素ごとのコピーパターン、製品用語。
- **動作仕様** ― タイミングカーブ、持続時間、遷移パターン、マイクロインタラクション仕様。

**ドメイン参照スキルとは** 、特定の分野に特化した製品固有の知識を指します。例えば、特定の製品領域向けにデザインを行う場合、ドメインスキルには、その製品に特有のUXパターン、情報アーキテクチャ、インタラクションフロー、マイクロコピーガイドラインなどが含まれるでしょう。

私が発見した最も重要な違いは、コンポーネント／トークン仕様スキルと設計原則スキルは相互補完的な役割を果たすということです。一方は *正しいもの* （仕様、トークン、コンポーネント）を知っており、もう一方は *何が正しいか間違っているか* （哲学、評価、判断）を知っています。一方は実行し、もう一方は評価します。

**仕様書に質問する：** 「どのコンポーネントを使用すべきか？」「トークンは正しく適用されているか？」など、明確な正解がある質問。

**原則に問いかけましょう。 「これはこの状況に** *適した* コンポーネントか ？」「このデザインはユーザーのニーズを尊重しているか？」「視覚的な階層構造は効果的か？」「これはモバイル端末で動作するか？」「流れは論理的か？」など、判断を必要とするあらゆることについて問いかけましょう。

## レイヤー2：能力スキル（ワークフロー）

能力スキルはワークフローを実行します。つまり、ツールや参照スキルを連携させて設計タスクを完了させます。各能力スキルは必要な参照スキルをロードし、必要なツールを呼び出します。

私が培ってきた能力スキルは以下のとおりです。

**スタンドアロン（依存関係なし）：** `read-filter-prd` PRDからUI/UX要件を抽出します。 `create-design-ticket` 要件に基づいてJiraデザインチケットを作成します。 `define-flow` ユーザーフローとインタラクション状態をマッピングします。 `research` デザイン前のベンチマークと証拠収集を行います。 `sell-design-vision` デザインプロジェクトの提案と影響レポート作成を支援します。

**参照スキルに依存します:** `identify-ux-problems` 既存のデザインを監査します (原則を読み込み、オプションで仕様を読み込みます)。 `generate-design` 静的な高精細 Figma フレームを作成します (原則、仕様、コンテンツ戦略を読み込みます)。 `generate-prototype` インタラクティブなアニメーション プロトタイプを作成します (モーション、仕様、原則を読み込みます)。

**参照スキルと Figma MCP に依存します:** `design-review` ライブデザインのヒューリスティック評価を実行します (Principles、Specs を読み込み、Figma に接続します)。 `qa-signoff` 実装と Figma ソースを比較するビジュアル QA を実行します (Specs を読み込み、Figma に接続します)。

## レイヤー3：ツールとコネクタ

これらは、外部連携機能を提供するMCPサーバーです。具体的には、スクリーンショットやメタデータ用のFigmaのREST API、デザインをプッシュするためのレンダリングプラグイン、ノードレベルの編集を行うTalkToFigma、そして使用するあらゆるプロジェクト管理連携機能などが含まれます。

## 典型的なパイプラインの流れ

このアーキテクチャの強みは、スキルがパイプラインとして組み合わされる点にある。

**PRD主導型：** PRDの読み込み・フィルタリング → デザインチケットの作成 → フローの定義 → デザインの生成 → デザインレビュー → QA承認

**デザイン主導：** UX問題の特定 → リサーチ → デザインビジョンの提案 → フローの定義 → デザインの生成

**迅速な生成** （既に何が必要か分かっている場合）：レンダリングツールに画面を直接記述するだけで済みます。CLAUDE.md は原則が自動的に参照されることを保証します。

**デザインレビュー：** Figmaのリンクまたはスクリーンショットを貼り付けてください。クロードがあなたのデザイン原則に照らし合わせて批評し、注釈を加えます。

## どこから始めればいいのか（それでもまだ大変そうに感じる場合）

分かります。この記事には、レイヤー、パイプライン、2つの環境など、多くの概念が含まれていますね。重要なのは、初日にすべてを構築する必要はないということです。アーキテクチャはあくまで最終目標です。そこへは一歩ずつ進んでいけば良いのです。

もし今日からゼロから始めるとしたら、私は次の順番でやるでしょう。

**第 1 週:** Claude Code をインストールします。Figma MCP を接続します。デザイン原則を説明するスキルを 1 つだけ作成します。ここで最も恐ろしい障壁を取り除く部分があります。SKILL.md ファイルをゼロから作成する必要はありません。Claude に「デザイン原則を説明するスキルを作成するのを手伝ってください」と伝えて、会話を始めます。デザイン ガイドライン ドキュメントを貼り付け、重要な点を説明すると、Claude がスキル ファイルを作成します。確認して微調整すれば完了です。次にスクリーンショットを貼り付け、Claude にその原則に照らし合わせてレビューしてもらいます。「一般的な AI フィードバック」と「実際にシステムを理解しているフィードバック」の違いをすぐに実感できます。その瞬間があなたを虜にするのです。

**第2週：** コンポーネント/トークン仕様のスキルを追加します。シンプルなフレームを生成してみましょう。クロードが、実際のデザインシステムコンポーネントで構築された、編集可能なFigmaフレーム（画像でもワイヤーフレームでもなく、検査や修正が可能なフレーム）を初めてプッシュすると、この設定が最初の摩擦に見合う価値がある理由が理解できるでしょう。

**第3週以降：** 最初の能力スキルを構築しましょう。まずは設計レビューから始めます。これは最も価値が高く、リスクが最も低いワークフローです。次に生成、そしてプロトタイピングへと進みます。それぞれのスキルは、既に作成した参考スキルを基盤としています。

参照知識、機能ワークフロー、ツールコネクタといった階層構造こそが、システム全体の長期的な保守性を確保する鍵となります。設計原則を更新したり、新しいコンポーネント仕様を追加したりすると、それに依存するすべてのワークフローが自動的に更新されます。重複も、方向性のずれもありません。早期に組織化を進めることで得られるメリットはまさにここにあります。

1か月前、私は学生時代以来、端末を開いたこともないデザイナーでした。今では、私のデザインシステムをチームのほとんどの人間よりも熟知しているAIデザインパートナーがいます。すべてはわずか4週間ほどで起こりました。私の環境は完璧でしょうか？おそらくそうではないでしょう。数か月後には、これらのツールの一部が時代遅れになるかもしれません。しかし、重要なのは完璧なツールチェーンを持つことではなく、そもそも体系的な出発点を持つことだったの *です* 。
