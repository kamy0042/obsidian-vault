## プロローグ：AIの生成物は、「良い」が決まっていないと評価できない

AIで生成されたデザインをチームでレビューする際に、 **良いデザイン** が定義されていないと、市場に出して良いかの判断ができません。

![画像](https://assets.st-note.com/img/1787289773-inN2uga0vcCVUoIydxEMR5Le.png?width=1200)

その結果、「AIって実用的ではないよね…」と結論づけてしまいます。  
AIにUI を作らせること自体は難しくありません。  
生成は確率的で、品質評価は非決定的です。

![画像](https://assets.st-note.com/img/1787309382-ueGK1CHBErL4QmiND2hlFSR6.png?width=1200)

そこで、ヒントにしたのは狩野モデル（1984）、品質には種類がある、という考え方です。

![画像](https://assets.st-note.com/img/1787309436-CF9VuxZojiTNXH3qDY6PehGr.png?width=1200)

狩野モデル、 wikipediaから引用

> **当たり前品質** — あって当然、欠けると不満。車でいえば「エンジンがかかる」。満足度を上げはしませんが、欠けると致命的です  
> **一元的品質** — 良いほど満足、悪いほど不満。車でいえば「燃費」。競争力に直結し、継続的な改善が求められます  
> **魅力的品質** — あると嬉しい、なくても仕方ない。車でいえば「車内 Wi-Fi」。差別化や感動を生み、時間とともに当たり前へ変わっていきます

[wikipedia](https://ja.wikipedia.org/wiki/%E7%8B%A9%E9%87%8E%E3%83%A2%E3%83%87%E3%83%AB)

AIエージェントと共に開発をする上での、欠けると不満になる「当たり前品質」を定義し、決定的な評価軸とする。

そして、AIの責任を明確にすることで、AIの確率的な生成を決定的な評価軸で見ることができるのではないかと考えました。

そうすればAI生成のレビューは「好みの議論」から「定義の確認」に変わり、人は魅力的品質を作ることや一元的品質の改善に時間を使えるようになります。

![画像](https://assets.st-note.com/img/1787373112-sWwGqPltSgn09eMRTArpxNZL.png?width=1200)

三段論法

AIネイティブで目指したのは作業効率化ではなく、 **人が考える範囲を削り、人にしかできない時間を返すためのもの** でした。

## 定義を一箇所にまとめよう！

5月27日、リポジトリを作り、Figmaで整理したファイルを元にコード上でトークンの定義を始めました。

技術選定はTailwind CSS v4ベース、フレームワーク非依存のCSS配布にしました。

フレームワーク非依存にしたのは、6 年続く既存サイトに **段階的に導入する** ためです。React化のような書き換えを前提にせず、npmからCSSを読み込めばどのページでも今日から使える。チームは全員デザイナーなので、「HTML にクラスを書くだけ」で完結することも大事でした。そしてこれは結果的にAIとも相性が良く、MCP が返すHTMLスニペットが、環境を問わずそのまま貼れます。

Tailwind v4 を選んだのは、トークンの定義(@theme)がそのまま CSS 変数として配布物になるからです。トークンと実装が一体になり、 **定義はあるのに実装が違う** というズレが起きません。

角丸などのユーティリティを決まった6段階に絞ることで、外れた値をそもそも書きにくくしています。Tailwind を使わないプロジェクト向けには、CSS 変数だけのファイルも別途配布しています。

![画像](https://assets.st-note.com/img/1787374801-T05FBcoetWG84S1aJ6ri7XzR.png?width=1200)

角丸のユーティリティ

デザインシステムの構成は、一般に Foundation（色・余白・文字などの土台）→ Components（部品）→ Patterns（部品の組み合わせ）→pageの順に大きくなっていきます。

Figmaで整理したFoundation・Componentsをコード状に定義し、リポジトリに格納していきます。

![画像](https://assets.st-note.com/img/1787375241-rbWwaUCu14psV30XqYN2TjxJ.png?width=1200)

ボタンの規格を定義

hover時はカラースキームをひとつズラす（例：green/700→green/800）のような、状態を示す色の運用をシステム化する定義など、全てのコンポーネントで悩まずに運用できる基盤もこの時点で作ります。

![画像](https://assets.st-note.com/img/1787624355-VoiyuszDJAl5TqxFZdH72IU1.png?width=1200)

ボタンのプロパティ

また、各コンポーネントのNGパターンも可能な限り書き出していきます。  
運用しながら修正を繰り返すものなので完璧は求めません。

## AIの担当範囲を整理しよう

Foundation / Componentsをリポジトリに集め、最小限の整備が終わりました。  
次はAIに渡すための準備です。

最初に行ったのは大きく2つでした。

1つ目はDESIGN.mdです。  
relayのDESIGN.mdには大きく以下の3つが書かれています。

- **譲れない原則** — ハードコード禁止、余白は決まった9段階だけ、本文は16px基準、テキストリンクは常に下線、など
- **迷ったときの判断基準** — ゆったりとした余白、わかりやすい表現、明瞭な色使い、というrelayのデザイン原則
- **よく使う値のクイックリファレンス** — 色・余白・タイポグラフィの実値

になります。

そして、  
譲れない原則 **＝当たり前品質  
**迷った時の判断基準 **＝一元的品質  
**として整理しています。

![画像](https://assets.st-note.com/img/1787377183-AUNxygZBbVnFiHaEvr7hOjlY.png?width=1200)

「譲れない原則」に記載している内容は、AIエージェントに求める **当たり前品質** です。  
「迷った時の判断基準」は、完璧な表現は求めませんがあると満足する **一元的品質** として整理しています。

このように整理することで、生成物の評価を一定の基準でおこなうことができ、 **一元的品質に記載していたがチームから指摘が多い = チームの中で当たり前品質になったから言語化して譲れない原則に移動させよう** のような品質の移動をデザインシステムにフィードバックすることができます。

2つ目は **アクセシビリティ** です。

![画像](https://assets.st-note.com/img/1787378125-2jkABMEUzl8ytWswFdm3NH7h.png?width=1200)

なぜアクセシビリティから始めたのか。

relayの利用者にとってアクセシビリティは紛れもなく「当たり前品質」です。  
ドメイン特性上、事業を譲る方の多くは高齢です。小さな文字、薄いコントラスト、外れるタップ領域。それは特別な配慮ではなく、主要ユーザーそのものの条件です。  
しかも事業承継は人生に何度もない決断で、情報に辿り着けないことが、そのまま機会の損失になります。全国の自治体と組む以上、公共性の要求もあります。

そして、WCAG 2.2という物差しがあります。達成項目をゼロから決めなくていい。多くの達成基準は部品レベルまで分解できるので、デザインシステムとAIの担当を定義でき、約半分の項目は機械で判定できます。

さらに、アクセシビリティはAIが最も落としやすく、人のレビューでも最も漏れる領域です。当たり前品質は運用の中でなるべくコストを下げる方が吉です。

冒頭に述べた、「評価項目を定義しAIを評価し、人に時間を返す」に対応します。

![画像](https://assets.st-note.com/img/1787379761-QNefm1lwXIzM7pL4TODbnBxg.png?width=1200)

デザインシステム側の具体的な対応として、WCAG2.2チェックリストと各コンポーネントに、 **デザインシステムとプロダクト、どちらが責任を持つのか** を明記しました。

たとえば [アイコンボタン](https://relay-development.github.io/relay-design-system/icon-button.html?tab=a11y) を例に見てみます。  
部品レベルの「期待される配慮」を明記しており、さらに「デザインシステムが担保する機能」と「実装時に必須の対応」を記載しています。

![画像](https://assets.st-note.com/img/1787293659-VNLYAd1cKZ2ps4nBP7tUmgHv.png?width=1200)

アイコンボタンのアクセシビリティ対応

アイコンボタンの場合、実装時の責任としてaria-labelを付けること、などを明記しています。

![画像](https://assets.st-note.com/img/1787293879-BbAoDO8hRa5jT7NzstZyGuXK.png?width=1200)

アイコンだけのボタンには aria-labelをつける

![画像](https://assets.st-note.com/img/1787294088-VD5a9zGWnkF83rojwH7PZqxX.png?width=1200)

キーボードフォーカスは必ず可視化

「デザインシステムは〇〇まで守るので、AIエージェントは実装時にXXを守ってね」という担当範囲を決めることで評価する狙いです。

## AIに渡す

次はAIエージェントに渡すための道づくりです。

デザインシステムをAIに渡す手段として、skillsとMCPサーバーが候補になります。  
relay が MCP を選んだ理由は主に 2 つ。

- 会社全体でClaudeのTeamプランを使っているので、組織コネクタとして管理者が一度設定すれば、 **メンバーは何も設定せずに使い始められる**
- どのクライアントからでも呼び出せる

です。こちらに関してはXでポストした通りです。

![](https://x.com/i/status/2076884745452130710)

6月26日にstdioのMCP サーバーをデザインシステムに同梱し、3日後にはリモートMCPも建てました。  
MCPが提供するツールは8つあります。役割で分けると、3 つのグループになります。

**① 実装の土台**

```
get_setup — CSS の導入手順と確認方法。これを一番最初に呼ばせます。CSS が未導入のまま relay のクラスを書いても見た目が変わらず、AI がハードコードに逃げてしまうからです

list_components — 全 29 コンポーネントの一覧と概要。「どの部品を使うべきか」の相談窓口です

get_component — 個別の完全仕様。props や状態に加えて、コピペしてそのまま使える HTML スニペットと「使用法の OK / NG」を返します。AI はゼロから markup を組まず、これを土台にします
```

**② 値と規範**

```
get_tokens — 色・余白・タイポ・角丸・影の解決済みの実値。「だいたいこの緑」をなくすためのツールです

get_design_principles — 必須ルールと禁止パターン。憲法(DESIGN.md)の配信版

get_accessibility — WCAG 2.2の86基準と責任分界
```

**③ 補助**

```
list_assets — ロゴ・イラストの直リンク。独自ロゴを描かせないためにあります

search — 名前を知らなくても辿り着ける、横断のあいまい検索
```

ツール設計の考え方は、 **「目次 → 詳細」の 2 段構え** です。  
これはskillsで渡す際にも同じ設計にしている事例が多いかなと思います。

まず list_components で全部品の短い目次を読ませて、使う部品だけget_component で詳細仕様とスニペットを取りに行く。

最初から全部を渡さないのは、AI のメモリーを軽く保つため。そしてもうひとつ、「どの部品を選ぶか」という判断を、AI自身にさせるためです。

実運用を想定した時、プロンプトはおそらく意図レベルの指示になるはずです。フォーマットを決めても、デザイナーでなければコンポーネント名や使用法まで指示することはできません。

![画像](https://assets.st-note.com/img/1787380885-FQOzidx15IyqDN6nUKfHtpr4.png?width=1200)

意図レベルの指示

「案件が増えてきたので、ステータスがひと目でわかる一覧画面がほしい」のような意図レベルの指示でもAIが正しく汲み取り部品を組み立てる必要があります。

![画像](https://assets.st-note.com/img/1787380904-1YVySXPlCOoFi2kdBGDm4Q8H.png?width=1200)

一覧 → data-table、状態 → badgeの部品を正しく使って組み立てることができた

また、AIが部品選びを間違えたとき、悪いのはたいていAIではなく、デザインシステム側です。選ばせる構造にしておくと、「正しい部品に自力で辿り着けたか」があとから測れて、デザインシステムの穴が見つかります。

作ってみて学んだのは、 **「運ぶ」だけでは足りない** ということでした。実際に効いたMCPの設計は下記です。

- 接続した瞬間に常駐ルールを渡す **instructions** →ツールを呼び忘れて、記憶で書き始めてしまう AI への対策です
- **get_setup** を必ず最初に呼ばせる導線→「クラスを書いたのに効かないからハードコードに逃げる」という入口を塞ぎます
  ![画像](https://assets.st-note.com/img/1787381016-6hPQYFzq9KoBvesg17DNVlb3.png?width=1200)

instructions→全体→詳細

道が通って、AI はデザインシステムを参照し画面を組めるようになりました。

## チームは少しずつ変わってきた

余談ですが、この辺りからFigmaの役割が変わってきました。

relay のプロダクトチームは全員デザイナーで、正直「プッシュって何？PRって何？」というところからのスタートでした。

社内でGithub勉強会を実施するなどして、徐々にgithubへの理解も深まり、実際にAIでプロトタイプを作成し、開発環境にマージして確認するようになりました。

Figmaが要らなくなったわけではありません。  
正解を保管する場がリポジトリに移ったことで、Figmaは **最後の調整とデザイン探求の場** へと変わりました。

リポジトリを正本と定義し、Figmaでの完璧なデザイン作成はしません。

これは評価の前提条件でした。  
生成物を評価するには「何と照らして正しいとするか」の基準が一本化されている必要があります。正本が揺れているかぎり、ガードレールも試験も作れません。

## AIは当たり前を守り、人は魅力を作る

7月21日 **固定のお題をAIに解かせて生成物を採点する回帰テスト（evals）** を導入しました。

すでに導入していた機械チェック（hooks）は、アクセシビリティの対応やトークンがハードコードされていないかを見ます。これはチームで定義したAIエージェントに求める「当たり前品質」を守れているかの確認でもあり、100点を目指すのでLLMの外で、機械チェックでテストします。

**evalsはコンポーネント選定の適切さや表現の質を見ます。**  
意図レベルのお題を定期的に解かせ、AIが意図を汲み取ってどの程度の完成度で適切に生成したかを評価します。スコアが高ければ満足で低ければ改善していく、つまり **一元的品質の評価** です **。**

![画像](https://assets.st-note.com/img/1787382031-JIPHwufLa7FmkCKvezdVgj13.png?width=1200)

DESIGN.mdの評価対応表

どの層がどの品質を守るかを定義し、現時点のAIへの期待値を共通認識とします。  
実際のディレクトリ構成は下記で、hooks/ と evals/ が検査の置き場所になっています。

```cpp
relay-design-system/
├── DESIGN.md            … 1枚にまとめた憲法(原則・禁止パターン)
├── docs/                … a11yの契約書などの詳細ドキュメント
├── src/
│   ├── tokens/          … Foundation(色・余白などの値)
│   ├── components/      … 部品の CSS。先頭コメントが仕様の正本
│   └── mcp/             … 渡すための MCP サーバー本体
├── evals/               … スコアで測る層(一元的品質)
│   ├── cases.mjs        … お題の定義(意図レベルのプロンプト + 採点基準)
│   ├── run.mjs          … 試験のランナー(機械チェック + AI 審査員)
│   ├── review-log.md    … AI 審査員を人が監査した記録
│   └── audited/         … 監査した画面のスナップショット
└── .claude/
    └── hooks/           … 遮断する層(当たり前品質)
        └── relay-hardcode-gate.mjs
```

![画像](https://assets.st-note.com/img/1787383866-WzCkf8oFElgTxhpsKONAr34V.png?width=1200)

また、狩野モデルの性質として、品質は固定ではなく時間とともに段階を移動します。最初から当たり前で、動かないものもあります。relay のアクセシビリティがそれでした。

品質は勝手に動きますが、検査の置き場所は勝手には動きません。どの品質がいま、どの段階にいるのか。それを見極めて検査を動かす。この判断を人が握ることです。

## 削るためではなく、作るために

デザインシステムで最初に目指したものは、AIの自動運転ではなく、AIを助手席に座らせ周辺の安全を確認してもらうことでした。

そして、ここまであまり触れてこなかった魅力的品質は、AIで測りません。 **人が作ります。**

![画像](https://assets.st-note.com/img/1787383897-0EGurwKM4Oqxsz6niNteLFoZ.png?width=1200)

少し整理したいのは、この「魅力的品質」はrelayの利用者に向けたものです。また、AIが進化していく中で、ずっと人が手を動かすのか？に関しては正直答えは出ていません。

現在も「AIに何を任せて、人は何を作るか」の問いに向き合っています。  
AIの生成物は、チームの「良いデザイン」が定義されていないと評価できません。  
だから私は、狩野モデルをヒントに、当たり前品質から定義し、AI に渡し、破れない構造にし、実戦で改善し、測れるようにしました。

人が考える範囲を削り、人にしかできない時間を返すために取り組んできました。次は返ってきた時間をどう使うのかを考えなければいけません。

relayは7月で6周年を迎えました  
つまり6年分、ユーザーとの接点の中で作られてきたブランド価値があります。

![画像](https://assets.st-note.com/img/1787385506-EfPknup3x1NaYX7KQiFVt4qg.png?width=1200)

譲り手の不安に寄り添う文章の温度、地域ごとの物語の見せ方、実名で公開することの誠実さ、ユーザーとの接点のなかで、人が少しずつ積み上げてきた、まさに魅力的品質です。

AIはこの6年分を、それらしく再現できてしまうかもしれません。それでも、7年目の魅力を「誰に向けて、何を作るか」と決めることは、まだ人にしかできないと思っています。

だから、返ってきた時間の使い道は決めています。ユーザーの声を聞き、仮説を立て、次の魅力を作ること。  
それに、これまでの魅力もいつか当たり前になります。だから魅力は作って終わりではなく、ユーザーと向き合いながら言語化し、当たり前になったら仕組みへ引き渡していく。この繰り返しが、人の仕事になっていくのだと思います。  
当たり前品質を仕組みに任せたのは、そのためでした。

いつかAIが魅力まで作る日が来るのかもしれません。そのときは、また責任分界を引き直せばいい。そのくらいの気持ちです。
